# 0186. Writes to shared systems from the app need a person's confirmation

- Status: proposed (built from review round 48, the app server, 2026-11-08; for the product owner to accept)
- Date: 2026-11-08
- Builds on: ADR 0015 (the local server and its session token), ADR 0073 (the person's click is the approval), ADR 0097 (the app in a VS Code panel from the extension's files), ADR 0119 (the token is printed only for editors and with `--show-token`), ADR 0121 (the AI tab), ADR 0183 (Propose for review), ADR 0184 (the release PRs)
- Contracts: C4 (local API 3.0.0). Not additive: the session token alone no longer approves a write to a shared system. Adds `POST /api/confirmations` and a `confirmation` field on the writes' bodies. No catalog, rule or org-pack schema changes.

## Context

CLAUDE.md rule 6: a human approves every write to shared systems, and AI never pushes to protected branches. In the app, the person's click on Raise hand-off, Raise the release PRs, Sync and merge, Raise the task's PR, Send the digest, Propose for review or Run with a team's tool was the approval (ADR 0073), and the server took any call that carried the session token as that click.

Since ADR 0119, `atticus ui --show-token` prints the token "for an assistant or a script". Review round 48 showed what that allows: an assistant given the token can call `POST /api/changes/{id}/handoff`, `/release-prs`, `/sync` (which merged a ready PR), `/tasks/{task}/pr`, `/api/propose`, `/api/todo/{step}/run` and `/api/me/digest` with `send: true`. Each pushed, opened a PR, merged or posted as the person, with no person involved. The AI tab had the same gap: `PUT /api/settings/ai` took any `keyEnv` and any `baseUrl`, and Test then sent `Authorization: Bearer $keyEnv` there at once, so `keyEnv: GITHUB_TOKEN` and an address of the caller's choosing sent the person's Git token away.

## Decision

1. **A confirmation, not the token, approves a write to a shared system.** The server gives one only to the app's page: `POST /api/confirmations { write, target, pageKey }` needs the page key. The page key is a second secret, made new every start (or given by the editor that starts the server, `ATTICUS_UI_PAGE_KEY`, as `ATTICUS_UI_TOKEN` is). The server puts it in the app's page (`<meta name="atticus-page-key">`, beside the token's) and never prints it, `--show-token` included. Without it the answer is 403, and the message says to click the button in the app or run the command with `--approve`.
2. **One confirmation, one write, once.** A confirmation names the write (`handoff`, `release-prs`, `merge`, `task-pr`, `digest-send`, `propose`, `step-run`, `ai-model`, `ai-test`) and its target (the change, `<change>/<task>`, the step, the scope, `me` or `model`). It is used once, whether the write then works or not, and expires after two minutes. One for another target or another write, a replay and a late one are each 403.
3. **The writes that need one.** `POST /api/changes/{id}/handoff`, `.../release-prs`, `.../tasks/{task}/pr`, `POST /api/propose`, `POST /api/todo/{step}/run` and `POST /api/me/digest` with `send` take it as `confirmation` and answer 403 without a valid one. `POST .../sync` merges a ready PR only with one (`merge`). Without one it only reads the PRs and says what is ready, so a script can still follow a change. The service desk's File (`/api/service-desk/{id}/submit`) is left as it is: in the app it files through the manual desk, which only writes a step for a person into the metarepo.
4. **The page asks on the person's click.** Each of these buttons asks for its confirmation when it is clicked, then makes the write with it, with the same busy and error states as before. Propose for review keeps its Yes dialog, and a step run keeps its shown inputs: the confirmation is asked for on that Yes. Nothing new to read: the click was already the approval (ADR 0073), and now the server can tell a click from a script.
5. **Where the model's key goes is the person's.** `keyEnv` must name a model's key: a variable starting `ATTICUS_`, a model provider's own (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `AZURE_OPENAI_API_KEY` and the like), or a name the person kept in this machine's credential store. The providers apply the same rule when they read runtime.yaml (`readKey` in `@maycombhq/model-providers`): any other variable (`GITHUB_TOKEN`, `AZURE_DEVOPS_EXT_PAT`, `SYSTEM_ACCESSTOKEN`, `AWS_*`, `HOME`) is never read from the environment for a model, so a hand-edited file can't do it either. A save that changes the provider, `keyEnv`, an address or `caFile` needs an `ai-model` confirmation. Test needs an `ai-test` confirmation when runtime.yaml's model settings differ from the committed ones (HEAD), since committed settings were reviewed like code.
6. **The editors keep working.** IntelliJ's tool window and VS Code's framed panel load the page from the server, which puts the page key in it. VS Code's bundled panel (ADR 0097) builds the page from the extension's own files: the extension makes the page key, gives it to `atticus ui` in the environment with the token, and writes it into the page. The page's calls still go to the extension, which adds the session token. An older `atticus` that ignores `ATTICUS_UI_PAGE_KEY` keeps its own key, so in the bundled panel these buttons answer 403 until it is updated; everything else works.

## What it is not

The page key keeps a well-behaved assistant or script, using the token as documented, from writing as the person. It is not a wall against a program on this machine that sets out to act as the page. Such a program could also fetch the page, or run `git push` itself. The guard against that is the person's machine. Atticus's guard is that it never hands an assistant a way to write as the person.

## Consequences

- An assistant with the printed token reads everything and makes local changes as before. For a PR, a push, a merge, a message or a team's tool it gets a 403 that says what the person does instead: the app's button, or the command with `--approve` in their terminal, where the person-only list still refuses a Copilot session.
- Scripts that called these routes with the token now need the CLI with `--approve`, run by a person. This is why the API's version is 3.0.0.
- The AI tab refuses a `keyEnv` that isn't a model's key (422) and asks for the person's click when the key would go somewhere new. `atticus doctor` says when runtime.yaml names a variable the providers won't read.
