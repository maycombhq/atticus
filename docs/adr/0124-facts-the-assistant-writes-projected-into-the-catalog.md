# 0124. Facts the assistant writes, projected into the catalog; the verifier checks the claim on the line (C1 additive, C4, C5)

- Status: accepted (decided by the product owner on 2026-10-24; ADR text pending review)
- Date: 2026-10-24
- Amends: ADR 0074 (steps 1 to 3: the assistant reads first by default; the built-in readers become the optional cross-check; no scanner is generated), ADR 0080 (plugins stay as the escape hatch, not the path)
- Builds on: ADR 0074 (results per commit, a changed file invalidates only what cites it), 0082 (scan verify), 0089 (spec check's claim-on-line), 0103 (quotes forgiven at the ends), 0112 (a model limit every step honours), 0118 (the model searches the code), 0122 (files live in the metarepo)
- Design: "Atticus 2 — AI Reads, Code Verifies" (the product owner's design doc of 2026-10-24, reviewed by a separate session against this repo)

## Context

The built-in readers score 58% precision and 32% recall on the 22-repo public bench, 86% and 58% with the AI's scan settings and client base URLs (`bench/README.md`). Five layers patch the same problem (readers, dialect rules, framework models, repo types, scan settings, plus sandboxed plugins), and every new repo shape still needed an Atticus developer. ADR 0074 decided the direction: the AI reads, deterministic code verifies. This ADR fixes the shape of that, after a review found two faults in the first draft of the design:

1. Replacing catalog C1 (33 record kinds) with a six-kind schema would break every consumer of C1 (the index, the critic's checks, the planner's stages, the API, the app, the editors, the bench scorer) before anything new worked.
2. Having the assistant write a scanner, golden-tested against the facts it had just produced, is circular (it proves the scanner reproduces the assistant, not that the assistant was right), adds a third thing to be wrong, and commits assistant-written executable code to a metarepo on a laptop under a `vm` that is not a security boundary (ADR 0080).

## Decision

### 1. A facts file is the assistant's input format, not a new contract

The assistant reads a repo and writes **facts**: one JSON line each, in six kinds plus flows, every one with a citation.

| Kind     | States                                                               | Claim fields                                                                                     |
| -------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `entry`  | Something the repo answers to                                        | `method` and `path`, or `topic`, or `schedule`, or `screen` and `action`; `handler`              |
| `call`   | Something the repo reaches out to                                    | `method` and `path`, or `topic`; `host` or `base`; `from` (an entry id)                          |
| `store`  | A table, collection, bucket, queue or cache the code reads or writes | `store`, `name`, `op` (`read`, `write`, `delete`), `under` (an entry id)                         |
| `field`  | A named value crossing a boundary, and where it maps                 | `owner` (an entry, call, store or screen id), `name`, `type`, `mappedTo`                         |
| `deploy` | How and where the code runs                                          | `runtime`, `cloud`, `resourceType`, `resourceName`, `region`, `pipeline`                         |
| `config` | An external name the code depends on                                 | `key`, `value` or `source` (host, base URL, flag, secret name; a secret's value is never a fact) |
| `flow`   | An entry followed in order through calls and stores                  | `entry`, `steps` (fact ids), `outcome`                                                           |

Every fact carries `id` (a stable hash of kind and claim), `repo`, `commit`, `cite` (`file`, `line`, `value`, `quote`), `verified` (`line`, `sample`, `person` or `none`), `by` (`assistant`, `reader` or `person`) and `conf` (`declared` or `inferred`). The schema is zod in `packages/core/src/schema/facts.ts`, exported as JSON Schema beside C1's. A fact without a citation is not a fact; it is a question.

**Projection.** `projectFacts` in `packages/core` turns verified facts deterministically into C1 records: `entry` into `Endpoint` (or a `Capability` trigger for screens and schedules), `call` into `Interface` with its caller, `store` into `DataStore` access and `Table`, `field` into `Column`, `Schema` field or `FieldMapping`, `deploy` into `Deployment`, `config` into `Setting`, `flow` into `Flow`, and the repo's modules into `Component`. Every projected record keeps the fact's citation as its evidence and `by: assistant` as its source. Nothing downstream of C1 changes; rule 1 is met by this additive ADR with no schema bump.

### 2. The verifier checks the claim on the line

`packages/verify` is the deterministic layer. It never reads code to find facts; it checks the facts it is given.

| Check                            | How                                                                                                                                                                                                                                            | On failure                                            |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| The file exists at the commit    | `git cat-file` on the base clone                                                                                                                                                                                                               | Rejected: `no-file`                                   |
| The claimed value is on the line | `cite.value` (the route, topic, table, field, host or key) appears on `cite.line` or within one line either side, the `spec check` logic of ADR 0089, case-insensitively, with path parameters normalised                                      | Rejected: `value-not-on-line`                         |
| The quote matches                | After normalisation: whitespace folded, CRLF to LF, end punctuation and quote marks forgiven (ADR 0103), capped at 200 characters; a quote from a binary, notebook (`.ipynb`), or minified file (a line over 1,000 characters) is not required | Rejected: `quote-mismatch`                            |
| References resolve               | `from`, `under`, `owner`, `steps` name facts in the same file                                                                                                                                                                                  | Rejected: `dangling-ref`                              |
| No secret in a quote             | Config quotes are redacted by pattern (`password`, `secret`, `token`, `key=` followed by a value, private-key headers); quotes from paths on a deny-list (`.env*`, `*.pem`, `*.key`, `secrets/**`, `**/credentials*`) are refused              | Rejected: `secret-path`; or the quote stored redacted |
| Determinism                      | Facts sorted by id and written canonically; the same commit, the same facts file and the same answers give the same bytes                                                                                                                      | A diff on an unchanged commit is a bug                |

What the verifier proves: every fact rests on a real line that names the thing claimed. What it cannot prove: that the assistant understood the line. Precision comes from the assistant and is measured on the bench; the verifier blocks fabricated and misplaced citations.

**Coverage** is reported, not trusted: files the assistant cited, plus files it read through Atticus-routed tool calls (ADR 0118's `atticus context call`), count as read; every other source file is `unknown`, never "excused" on the assistant's word. Generated code committed to a repo is excluded by a rule the assistant proposes and a person accepts once (`org-pack/scan/<repo>.yaml`, ADR 0075).

### 3. The readers become the cross-check; no scanner is generated

The built-in readers stay in the build, as ADR 0074 already said: an optional fast path, and a cross-check where agreement confirms a fact and disagreement is a finding. They also stay because the `outline` tool (ADR 0118) and `namesInCode` use their parsers. Dialect rules, framework models, repo types and scan settings stop being the path to accuracy. The assistant does not write scanners; ADR 0080's reviewed, sandboxed plugins remain available to a team that wants one. Rescans invalidate only the facts that cite changed files and re-read those files (ADR 0074).

### 4. Three assistant tiers, chosen at init

Organisations sit on one spectrum of assistant capability, and Atticus works at every point of it without being told:

1. **Agentic.** The assistant opens files and runs commands itself (Claude Code, Cursor, Copilot agent mode with the generated prompt files). A map read is one session.
2. **Chat with a token limit and no file tools** (Copilot Chat through `vscode.lm`, about 8,600 tokens of room on GPT-4o mini, ADR 0112). The read runs as hand-off batches: Atticus slices the repo into file batches that fit the limit, hands each as a prompt, verifies each answer as it comes back, and continues until coverage is complete, as the knowledge scan does with `--batch-tokens`.
3. **Copy-paste only** (IntelliJ with Copilot, a web chat). The same batches as copy-ready prompts with a paste-back box.

A capability probe at `atticus init` (can the assistant open a named file on request, what is its token limit, can it write a file back) picks the tier and tells the person what the first read will cost in prompts and time. Every organisation gets the same product; only the speed of the first read differs, and that speed is measured per tier on the bench.

### 5. One home for the map

In a single repo the map lives in `.atticus/` (adopt in place, ADR 0038); in an estate it lives in the metarepo (ADR 0122). Nothing else is written into a product repo. `map.md`, `flows/`, `contracts/` (OpenAPI by default; a TypeSpec file is accepted as the authored target contract) and `questions/` are rendered there and reviewed as a PR.

### 6. The measure comes before the bar

No accuracy bar is set before one measured run of the assistant reading bench batch 1 (six repos) with the verifier on, recorded in `bench/README.md` with the model cost per repo. Today's references score serves, calls, stores and deploys; fields and config are added to five repos' references first so every kind is measured. The working targets are recall 85% and precision 95% on facts and 80% of reference flow steps in order; they move only with numbers.

## Consequences

- Everything built on C1 keeps working while the map's source changes from readers to the assistant.
- The deterministic layer shrinks to what code can prove completely: anchoring, references, redaction, coverage, determinism.
- A team never waits for an Atticus release to read a new repo shape; the assistant reads it, and a correction is a person-verified fact.
- CLAUDE.md rule 4 stands; rule 1 gains the facts schema as an additive contract. `README.md` no longer says scans never call a model.
- `docs/build-status.md`: I1 is done (decided here), groups C and D are superseded, group I's thirteen items are replaced by the Phase A tickets of the design.
- Open for the product owner: whether to publish the package (the `npx` path needs a public repo, decisions-pending 1); the legal sign-off on the embedding model stays owed and the model leaves the default bundle.

## Addendum (A3b): the facts become the catalog, and the map is rendered from it

- **`atticus verify <repo> --write`, not writing by default.** Verify is the inner loop of a read: the assistant runs it after every batch (and the hand-off tier of section 4 runs it per batch), so most runs check a read that isn't finished. Writing by default would replace the repo's records with a half-read projection on every pass and make a check change shared, reviewed files. With `--write` the person (or the skill, at the end of a read) says the read is done. It writes only when nothing in that run was rejected; otherwise it says so and writes nothing, so a half-fixed read never replaces what the catalog had. Without `--write`, verify prints the command.
- **What --write does.** The kept facts are projected (`projectFacts`; facts with no component take the manifest's component, and the manifest's system). Records whose evidence is all from the repo are dropped; records with evidence from it and from other repos (another repo's call into this one) keep only the other repos' evidence, a call into a dropped endpoint loses that endpoint, and a table drops the repo's old components as readers and writers. The rest of the catalog is kept as it is. The scan's own passes then build the catalog: `mergeEstate` (factored out of `scanEstate` into `packages/scanner/src/merge-input.ts`, so the hosts, modules, systems and patterns are the same), then the curated decisions with `applyCurated`. Endpoints take the merge's canonical ids, and the projection's ids that named them (schemas, schema refs, flow triggers and step refs) follow (`ProjectResult.ids`). The catalog is written with `writeCatalog`; flows go to `specs/<repo>/<id>.yaml` with `writeFlow` and a spec header (template `facts@1`, the commit, a hash of each cited file); flows an earlier write made that the facts no longer have are removed, drafted flows are left. Then the map is rendered. The write takes the scan's lock. Writing the same facts again changes no file; another repo's record files are byte-identical before and after (tested).
- **Loose calls become loose ends the merge can join, or questions.** A REST or SOAP call with no target but a host (or a base whose config fact is a URL) becomes an `http-call` loose end, so a host in the manifest joins it, and a host nobody lists is asked as ADR 0088's hosts question (`Which repo answers on <host>?`, rerun `atticus verify <repo> --write`). A publish becomes an `event-publish` loose end and a listener an `event-subscribe`, so the merge pairs them across repos. Any other call with no target is asked as a question of its own (step `facts-targets`): "Which repo or system answers POST /notify, which ledger-api calls?", with the other repos' components that serve that kind of call, the vendor systems, and "None of these". Its answer is read on the next write as the call's target, so the same facts and answers give the same catalog.
- **The map** (`atticus map render <repo>`, also run by `--write`): `map/<repo>/` in a metarepo, `.atticus/map/<repo>/` when adopted (`mapDirOf`, `mapRelOf`). Rendered from the catalog's records of the repo and its specs, never from the facts: `map.md` (a trust line from `<repo>.verify.yaml`; what it serves by component, calls by target with the calls not joined yet and the questions about them, stores with readers, writers and columns, where it runs, config that names other systems, flows, contracts, events, open questions; every fact line links to its file and line at the commit, through the manifest's clone URL, or relative into the clone), `flows/<flow>.md` (numbered steps with what, fields, refs, who confirmed, the cited line; error paths; a Mermaid sequence diagram from `flowSequenceView` in `packages/diagrams`, ADR 0092's lanes) and `contracts/<component>.openapi.yaml` (OpenAPI 3.1, path parameters from the path, bodies from the projected Schema records, keys in a fixed order). Events are listed in map.md, not written as AsyncAPI. The folder is rendered whole: a page nothing renders any more is removed. Golden files: `packages/verify/test/fixtures/map/`.
- **Not done here.** A scan still rebuilds a repo's records from the readers and so replaces what `--write` wrote; which source wins for a repo that has facts is for the product owner (below). Intake, features, glossary and federation aren't re-run by `--write`: their records stay as the last scan wrote them. ~~Per-commit invalidation (a changed file invalidates only the facts citing it) is not built.~~ (Built in addendum A-incremental.) A Schema field's `required` isn't in C1, so OpenAPI bodies list no required fields; a response body appears only when the facts name response fields.
- **Open for the product owner:** should `atticus scan` leave a repo that has written facts alone (the readers as cross-check only, as section 3 says), or keep rebuilding it?

## Addendum (A4): a claim built across lines

The measured run (bench batch 1) showed that many paths are not written on one line: a class-level prefix and a method's mapping, a client's base URL and its call, a context path in config, an MVC route template, a proto's package and service with its method. A fact could cite only one of them, so it was rejected, or the reader dropped the prefix to pass.

- `cite.with` (additive, optional, at most six): the other lines a path is put together from, each `{file, line, value}` with the part as written there. The verifier checks each line exists in the repo and names its part (within one line either side), and that every plain part of the path is written on the cited line or one of these (`partsNamePath`): a segment of a URL path, or a dotted piece of a gRPC `package.Service/Method`, each at the start of a word on some line. The files in `with` count as read for coverage.
- A route template written without its leading slash (`[HttpPost("uploadimage")]`, `[Route("api/v1/orders")]`) names the path `/uploadimage`, `/api/v1/orders`.
- A config key's last part is split on `.`, `:` and `__` (ASP.NET's `ConnectionStrings:Default`, `Logging__LogLevel`), for the claim and for the secret check; the secret check looks at whether that last part ends in a secret word (`ClientSecret`, `db.password`), not whether it mentions one (`TokenUrl`).
- A conventional MVC route (`{controller}/{action}/{id}`) is cited on the action, with the controller's class line and the route template in `with`; `partsNamePath` finds `Catalog` at the start of `CatalogController`.
- A config fact may carry `env` (additive, optional): the environment one file's value is for. It projects to the Setting's `env`, and the Setting's id becomes `<component>.<env>.<key>` so each environment's value is its own record.
- The protocol (`/atticus-map`) says when to use `with`, that a gRPC entry or call is `package.Service/Method`, that an event's path is its topic, that a gateway's route is an entry of the gateway with its target as a call, and that an entity's table is cited with its annotation in `with`, that a SOAP or WCF operation's path is `Service/Operation`, and that the questions a reader raises don't stop its verify loop: it shows them to the person once `atticus verify` passes. `atticus explain verify` (and `map`, `map render`, `change knowledge`) now explain; `map --estimate` says the tier is the org's runtime.yaml default and how another assistant reads the repo.

### A4, second round: what the revised reads showed

- The verifier: a `with` part may be named at a camelCase start (`Catalog` in `CatalogController`); `/{id}` verifies against `base + "/" + id`; `/` verifies as a conventional route's default action (a default route declared, its controller and action named); a claim written only in a comment (a commented-out example, a scaffold note) is rejected as `claim-in-comment`.
- The projection: a gRPC or SOAP call keeps `package.Service/Method` or `Contract/Operation` as its path, without a leading slash; an HTTP call's parameters lose their constraint and optional marker (`{brandId:int?}`) before the path is normalised.
- The bench matcher: a webhook receiver compares as a `rest` entry; a SOAP call from a facts file is scored as SOAP.
- The protocol: a route receiving webhooks is `rest`; a WebForms page is `GET /<path>.aspx`; an ASMX method called as JSON is `rest`; a conventional route keeps the template's parameters (`/Catalog/Edit/{id}`); a table in a schema is `schema.table`; a sequence is not a store; a gateway's call is the path the service receives; a call through a cloud SDK or auth middleware with no path is config, not a call; a load generator's or smoke test's requests are not calls; what a config fact is.

### A4, the held-out read (batch 2)

Batch 2 (16 repos) read once with the protocol frozen: 88% precision, 84% recall over serves to deploys (the readers: 57%, 33%); `bench/README.md` has the table. After it: the verifier derives a route from a page file's place (Razor Pages, WebForms, Next.js, `pages.ts`), matches a slugified segment against its name, takes a front end's root route (`path: ''`, `index: true`), puts no boundary after a value ending in punctuation, and doesn't read Netlify's `_redirects` rules as comments; a flag or mode value (`true`, `include`) is not a secret whatever its key; the bench matcher compares GraphQL `Query.field` with `field`, a platform without its cloud prefix, a websocket route as `rest`, and leaves scheduled jobs out (no reference lists them); the protocol covers file-place routes, slugs, GraphQL, scheduled jobs, framework docs endpoints, framework-created tables, generated clients, literal secrets, and a front end's calls that reach another service, and no longer asks for full coverage.

## Addendum (D-app): the app's six entries, the Trust tab and a change's knowledge in the app (C4 2.22.0, additive)

- **The six entries.** The app follows the Surfaces section of the design: Home, Map (Estate canvas, Flows, Contracts, Impact, Trust), Change (Feature design, Architecture, Stories, Tasks), Questions, Knowledge (items, sources, documents, search) and Set up (Repos, AI, Org pack). Existing screens are reused: the Estate canvas is the Architecture workspace without a change's step, the Change tabs are the stage pages of ADR 0084. A change's list, At a glance, its picture, Ask, a system's page, the words and the first steps are pages of the six reached by a link and Ctrl+K, not tabs. The pages the design names are behind `atticus ui --full`: with it every page is a tab (a change's grouped by phase) and Model runs, Prompt history, AI quality and Learning are a seventh entry, Atticus; without it they are absent from the menu, the tabs and Ctrl+K. No route is removed, so every old address still opens its page.
- **`--full` reaches the app through health.** `startServer({ full })` and `GET /api/health` gain `full` (a boolean; optional in the schema, so an older server's answer still parses). It changes what the app offers, never what the API does: every call answers with or without it.
- **`GET /api/trust`** (`TrustView`): per repo (the manifests' in their order, then any the facts name), read from files only: `facts/<repo>.jsonl` (count, the facts not verified, their commit), the verifier's `<repo>.verify.yaml` (kept, rejected, redacted, the coverage ratio, files read, not read and excluded, the first 50 unknown files, the commit), the checkout's HEAD read from its `.git` files (HEAD, a loose ref or packed-refs, a worktree's `gitdir:` and `commondir` followed; no git runs), whether the two commits agree, and how many of catalog/generated's records cite the repo from its facts (evidence with `by` and no extractor) and how many from the readers. A `state` (`not-read`, `unverified`, `rejected`, `stale`, `unwritten`, `unknown-files`, `trusted`) and the next command with its slash command; the app says the state in words from its copy file. A file that can't be read is a problem in the answer, never a failed call.
- **`GET /api/changes/{id}/knowledge`** (`ChangeKnowledgeView`): `knowledge.yaml` as the stages wrote it (Part 5), or `present: false` before any stage selected context; a file that isn't one is 422. **`POST /api/changes/{id}/knowledge/{item}`** (`SetChangeKnowledgeRequest`: `confirmed` or `excluded`) runs `setKnowledgeStatus`, the code `atticus change knowledge --confirm|--exclude` runs, on an item or a near-miss, and returns the view, the file and the `git add … && git commit …` command: the app writes metarepo files but runs no git. An item id may carry `:`, `/` and `#` (wiki and document sections), so it isn't held to a record id.
- **The server follows `facts/`** (ADR 0119's watcher), so the Trust tab updates when `atticus verify` writes.
- C4 gains these calls and one optional field; nothing existing changes, so no migration. `docs/api/openapi.json` is regenerated.

- **The Map with its evidence (F3, C4 2.23.0, additive).** Wherever the Map shows something a fact backs, its citation is a button: on the estate canvas's details panel (each box's evidence, and the links that start or end on it with theirs), each flow step and error path, and each contract's evidence. Hovering or focusing it shows the file and line, the quote the reader kept, who made each fact on the line and who checked it (the line check, a sample, a person, or nobody yet); the tooltip stays while the pointer is over it and Escape hides it (WCAG 1.4.13). Pressing it opens the facts on the line, the open questions that read it (with a link to answer), and Correct this. What the evidence lacks is a gap, said as every gap is, a shape and words and a dashed line, never colour alone: no fact verified from code on any of its lines (a reader's record, a read nobody verified, or a record of a kind the code shows that cites nothing), an open question on one of its lines, a correction that `atticus verify` hasn't applied yet. On the canvas these join each box's and link's gaps, so the outline says them too. A call the estate pass couldn't join keeps its own words (unjoined), as before. **`GET /api/facts/{repo}`** (`RepoFactsView`) gives each fact's citation and quote, a flow's steps and errors at their lines, the fields a person may correct (the fact's own string fields and the cite's value), the correction on file, and the repo's open questions.
- **Correct in place, as a file the verifier reads.** **`POST /api/facts/{repo}/corrections`** (`FactCorrectionRequest`: `wrong` with a reason, or `edit` with the changed fields and, optionally, the line) appends one line to `facts/<repo>.corrections.jsonl` (`.atticus/facts/` when adopted; `FactCorrection`, `schemaVersion: 1`, in `core/src/schema/fact-corrections.ts`): the fact's id and what it cited (kind, file, line, value), the action, the person (the Git user, ADR 0073) and when. Only the fields the person changed are kept; an edit that changes nothing, or makes no fact the facts schema accepts, is refused (422). The answer carries the `git add … && git commit …` command and `atticus verify <repo>`; the app runs neither. `atticus verify` and every `atticus map` batch read the file on every run (`applyCorrections`, before the check): a fact marked wrong is left out of the kept facts; an edited fact takes the person's claim and becomes a person's fact (`by: person`, `verified: person`, the narrowest place the verifier already kept for a person) and is still checked on its line, so a correction that the code doesn't say is rejected like any fact (and what names it with it). A correction meets its fact by id and cite, or by what it cited when a new read gives the fact another id, so it outlives the next read. An edit that meets no fact is reported as stale in `<repo>.verify.yaml` (`corrections`) and kept; a fact marked wrong that the read doesn't have is as wanted. The facts file's own contract doesn't change: the corrections file is new and separate.
- **A stage tab's findings with options and a comment box (B10, C4 2.23.0, additive).** Feature design, Architecture (for the change its address names) and Stories show the critic's findings of the stage's gate (its latest round, `review/<gate>/<round>/`), open first, blocking first, each with where, why and the fix, and only the options it allows: an issue's Make the fix and Not relevant, Waive where the rule is waivable and the finding blocking, a knowledge gap's Ask its owner. They are recorded through the existing `POST /api/findings/{change}/{finding}/action`, as `atticus finding` records them. Each finding has a comment box. **A comment is a question the person answered as they asked it** (ADR 0078: `questions/<id>.yaml`, step `change-<stage>`, its evidence the finding's file, answered in the person's words), and its id is added to the stage's loop file (`stage/<stage>.yaml`, ADR 0087's `questions`). That is how a stage already reads a person's answers: the next run sees an answered question it hasn't read, drafts again, and hands the comment to the drafter in its hand-backs data block ("Questions people answered"), then marks it read. A comment isn't linked to the loop's findings, so it never unblocks one by itself: the critic checks the next draft. A second comment on the same finding is a question of its own. A comment before the stage has run is refused (409), since nothing would read it. **`GET /api/changes/{id}/stages/{stage}`** (`StageReviewView`) gives the gate and round, the loop's state, the findings with their options and comments (and whether a draft read each), the stage's own questions (open ones answered in place with the Questions page's form), and the stage's command and slash command; **`POST .../stages/{stage}/comments`** (`StageCommentRequest`) writes the comment and returns the files, the `git add … && git commit …` command and the stage's command.

## Addendum (B-arch): the architecture stage's checks (planner stage files, additive; no C1 to C6 change)

The design's Part 2, stage 2: the architecture stage drafts target flows, contract deltas, data changes with their migrations and the deploy order across repos, and Atticus checks in code, before the critic sees the draft, that every delta cites a fact, that every breaking contract delta lists its consumers from the map, that every new table has a migration, a classification and a retention, and that the deploy order puts a callee before its caller and a migration before the code that needs it. A failing check goes back to the drafter as a stage issue (ADR 0087's loop), not to a person.

- **What was there.** The target flows (ADR 0087, 0095) already resolve every flow, step number, component, entry, table, column read and key against the specs and the catalog (ADR 0111), and a new table already needs its migration, each column's classification and a retention (ADR 0111 addenda A3, A5, A6). The contract deltas and data changes are read off the flow deltas, without AI (`interfaceChanges`, `dataChanges`). Nothing said whether a change breaks anyone, who that is, or in what order the repos deploy.
- **Breaking is a fact where the facts show it.** A change to a flow's entry breaks its callers when a field today's response returns is gone, the entry reads one field in place of another, the entry or response step is removed, or the flow is removed. A change to a table breaks its users when a column the catalog has is given another type (its Column record's `type`, compared with case, spaces and common spellings folded; a type change also needs its migration, and data.md says `change column x from A to B`). The drafter may mark a step `breaking` where no field is dropped (a field now required, a meaning changed): on a step that stores into a table it is the table's change, on any other the entry's.
- **Consumers come from the map, never from the draft's word.** An entry's callers: the `from` of Interface records to it, the components of spec flows whose call-out or publish reaches it, and its trigger's `caller.ref`. A table's: its `readers` and `writers` and the components of spec flows that store into it. The flow's own component is left out. A breaking change lists them under the delta's `consumers` (an entry) or the step's `store.consumers` (a table); one the map knows that the draft omits is `delta.consumer-missing`, an id the catalog doesn't have is `delta.unknown-consumer` (both blocking, drafting), and one the map doesn't show using it is a note (`delta.consumer-unseen`: a document may know more than the map). A breaking change to a flow whose trigger names no Endpoint is a note too (`delta.contract-uncited`): the map can't name its callers, so a person does. The architect's pack gets a `consumers` block (who calls the touched flows' entries, who reads or writes their tables), so the first draft can list them.
- **A call the map can't confirm is said.** A call-out or publish to a component or system the catalog has no Endpoint of, not marked new, passed silently; it is now a note (`delta.entry-uncited`), not blocking, because the map may not have read the callee (a vendor).
- **The deploy order is drafted and checked.** The architecture answer gains `deploy`: steps in order, each a repo's code or (with `migration`) a migration the target flows name under `store.migration`. The needs are read off the deltas: a migration before the code of every repo whose target flows read or write a table it changes; a callee's repo before its caller's when the call is new (`to.new`) or the callee's flow for that entry is in the change. Wrong order (`delta.deploy-order`), a repo or migration left out (`delta.deploy-missing`), and a repo or migration the change doesn't have (`delta.deploy-unknown-repo`, `delta.deploy-unknown-migration`) go back to the drafter. The order is kept in `stage/architecture-deploy.yaml` (as the flows read are in `stage/architecture-reads.yaml`), read back with the target flows, and shown in design.md under "Deploy order", with the breaking changes under "Breaking changes". The release plan (`atticus release plan`) still computes its own order from interfaces.md and data.md; comparing the two is left for later.
- **Blocking or not.** A draft without a deploy order gets `delta.no-deploy-order`, a note with an order that meets every need, not a blocking finding: every recorded draft predates the field, and recorded replays keep passing. It becomes blocking when Phase B re-records the stage fixtures, as `stories.no-error-case` does. The new consumer and deploy checks block, since no recorded draft has a breaking change or a deploy order. The fast path (ADR 0113) runs the consumer checks through `checkDeltas`; it drafts no deploy order.
- **Schema, additive.** The flow delta gains optional `consumers`; its steps gain optional `breaking` and `store.consumers`; the architecture answer gains optional `deploy` (`DeployStep`). Every file valid before reads the same, so, as ADR 0111's addenda did for `fields.as` and `store.keys`, `FLOW_DELTA_SCHEMA_VERSION` stays 2 and `STAGE_SCHEMA_VERSION` 1, with no migration. No frozen contract changes: these are the planner's stage files, not C1 to C6; the local API's target-flow view doesn't carry the new fields, so C4 stays 2.22.0.
- **Not done here:** the fields a call sends checked against its endpoint's Schema fields (a field the callee's contract doesn't have); consumers through a gateway route or a topic's subscribers; the deploy order compared with the release plan's; the deploy-order note made blocking.

## Addendum (A-probe): the tier is measured with the person's assistant (§4; no C1 to C6 change)

The product owner's decision of 2026-10-24: §4's capability probe asks the assistant to prove what it can do, instead of inferring the tier from runtime.yaml (A3a's passive probe, kept as the fallback).

- **`atticus probe [--assistant id] [--max-tokens n]`** (runtime.yaml's default assistant unless told another it allows; AI off has none to probe) writes `.runs/probe/challenge.md` (`.atticus/.runs/` adopted) holding an eight-hex-digit code it never prints, and `probe.json` beside it with the assistant, the code, when it started and a limit stated at the start. It prints what to do in that assistant: run `/atticus-probe` (an AGENTS.md tool follows `.atticus/prompts/atticus-probe.md`). A web chat with no command files answers `none --pasted`.
- **`/atticus-probe`**, a step command rendered for every assistant in the registry and the Claude Code plugin like the others, asks the assistant to open the challenge file, write the code and nothing else to `answer.txt` beside it, and run `atticus probe answer <code>` itself; one that can't run commands gives the person that line with `--pasted`; one that can't open files answers `none` and never guesses. It never states its own limit from memory: `--max-tokens <n>` only with the person's number. It is the one step command that doesn't start with the workspace check (`atticus assistant-files --check`), since that check runs a command and whether the assistant can is what it measures.
- **`atticus probe answer <code|none> [--pasted] [--max-tokens n]`** checks each capability by evidence, not by the assistant's word: `read` is the right code (it is only in the file); `write` is `answer.txt` holding the code; `run` is an answer not `--pasted`. Tier 1 needs all three (what `/atticus-map` does); tier 2 needs read and write (the hand-off: the person runs `atticus map <repo> --handoff`, the assistant reads each prompt file and writes the answer file); anything less is tier 3 (`--copy`). A wrong code records nothing and leaves the probe open; no probe, or one started more than 24 hours ago, is refused. A recorded answer uses the challenge up.
- **What it can't see.** Who typed the command: the probe trusts the person not to do the assistant's part. It is a measurement, not a security check, and nothing it records grants anything: every safety rule holds at every tier.
- **The result** (`ProbeResult`, `packages/assistant-files/src/probe.ts`, its own `schemaVersion: 1`): `assistant`, `measured` (ISO time), `tier`, `read`, `write`, `run`, `answered` (`command` or `pasted`) and `maxTokens` only when stated. Kept in `.atticus/probe/<assistant>.yaml`, one file per assistant, the newest replacing the one before. It is per machine and never committed (`.atticus/` is ignored in a metarepo; `probe/` joins core's `LOCAL_ONLY`, so an adopted repo's `.atticus/.gitignore` has it and `atticus upgrade` adds it): what one person's assistant can do is theirs, and a teammate's doctor says "from runtime.yaml" until they probe. A file that isn't a result, or is filed under another assistant's name, is said by doctor and left out.
- **Measured over inferred.** `assistantTier(runtime, { probes })` gives each allowed assistant its measured tier, else the one runtime.yaml implies, and says the lowest; at the same tier a measured assistant comes before one only implied, then the default, then runtime.yaml's order. A measurement of an assistant runtime.yaml no longer allows is left out, and AI off stays off. ## Addendum (C-join): the estate join from facts (Phase C; additive, no C1 to C6 change)

Phase C of the design: several repos' verified facts become one estate map. What was there before this addendum: `mergeEstate` joined a facts call to another repo only as a loose end the merge knows (an HTTP call whose host, or base URL from a config fact, a repo lists; a publish and a listener); a call whose `to` named a repo, rather than a component, became an Interface to a component that doesn't exist; a gRPC or SOAP call with no target, or an HTTP call with no host, became a targets question even when exactly one entry of the estate serves it; a joined Interface never cited the config that ties a base URL to its host; a call into a repo written later kept its caller only for Interfaces (an Unresolved call stayed loose, an event lost its pair). `joinEstate`, `estateFlow` and `fieldLineage` (ADR 0085) already followed flows across repos and a field to the column a write stores it in, from specs and the catalog. The deploy order was already computed and checked (addendum B-arch, `deployNeeds`; the release plan's own order).

- **The join is computed from the facts** (`joinFacts` in `packages/core/src/facts-join.ts`, pure): every call of the estate's facts, against every entry of another component. The callee is read, in order, from a person's answer (the facts-targets question); the call's `to` when it names a repo (all its components) or a component of the estate; a host, or a config fact's base URL, that a repo or module lists under `hosts:`, or whose first label is a component; else, when the call names nothing, the estate. A host no repo lists is asked as ADR 0088's hosts question and never guessed, even when an entry elsewhere has the path; a `to` naming something outside the estate (a vendor, a cloud service) is left to that name. Paths match as the estate pass does (parameters folded, a context or base path in front, a catch-all route), letter case aside, with the same method; gRPC and SOAP by `package.Service/Method` (or the short service and method); a topic exactly. With no target named only an entry of the same shape counts (no prefix or catch-all), and health and metrics paths join nobody. One entry is a join; two or more is a question (`ambiguous`) whose options are only those entries, in the facts-targets question's words, so its answer comes back through `targetsFromAnswers`; a named target with no such entry is a miss, said on the write. A publish joins every listener of its topic.
- **Two citations, and the tie.** A join is an Interface (`joinRecords`) whose evidence is the caller's call (`side: caller`), the config fact that gives the base URL (`source: config`, `side: caller`) when there is one, and the callee's entry (`side: callee`); verified when both facts are declared. Its id is the merge's (`interfaceId` of caller, callee, method and the entry's path), so a publish's Interface is the one the merge would pair. The REST endpoint is the merge's canonical one, a typed endpoint the projection's.
- **Field lineage, in C1 as it is.** For each join the fields that cross: a caller's request fields to the callee entry's, the callee's response fields back, a message's fields to the listener's, by name (last dotted part, case, `_` and `-` aside); and for a field the receiving side stores, the column (its `mappedTo`, else a column of that name a store under the entry writes). Each is a `FieldMapping` on the joined Interface (`sourceField`, `targetField`; a column's target is `table.column`), inferred by name and verified by `mappedTo`. A field sent that the receiver's facts don't take, or expected back that it doesn't return, is a gap, said on the write. No new record kind, no schema bump.
- **Written repo by repo, the same whatever the order.** `catalogWithFacts` takes the other repos' verified facts (`estate`; `estateFacts` reads `facts/<repo>.jsonl` of every other manifest repo, all verified, and their answered targets questions; one not verified is left out and said). The join's part about the repo (its calls, and the other repos' calls into it) replaces what those calls made before (an Unresolved, an Interface to the name the call gave, the joined Interface's old field mappings) and the calls' schemas follow their Interface (`applyFactJoins`). A placeholder component the merge made for a call into a repo not yet read, and the profile's systems, are rebuilt from the facts rather than kept, so writing three repos in any order gives byte-identical record files, and writing a repo again changes nothing (tested). The flows' call-outs name the callee and the entry it reaches, and a publish its first listener's Interface. `atticus scan` joins the repos it reads from facts the same way (A3c). `estateFromFacts` writes every repo in turn, for the bench.
- **A flow written before its callee was read** (its call-out names the repo, or the call's loose end) is joined by `joinEstate` through the Interface the callee's write made from the caller's components.
- **One cross-repo change end to end** (`packages/planner/test/estate-change.test.ts`): three Forge repos' facts (`fixtures/estate-facts/`: a web front end calling the customers API by a base URL from its config, the API calling the ledger over gRPC with no target named and publishing one event) joined, then a change across the three: the map names each changed entry's callers from the joins, and `deployNeeds` orders both migrations before their code, the ledger before the API and the API before the web.
- **The measure** (`scoreEstateFlows` in `packages/evals/src/estate-bench.ts`): a reference flow (bench/flows/) followed through the joins, the callee's steps inline at each joined call-out, matched in order against the reference's steps (a step matching as the spec scorer matches one, and in the same repo), and the fields at each crossing (the call-out's sends and the callee's returns) against what the estate knows there (the call-out's sends, the request and response schemas of the Interface and of its entry, the callee flow's returns). The start is the trigger rule's flow matching the most steps, else the trigger repo's flow matching the most (`best`); `strict` counts only the trigger rule's. A monorepo's `src/<folder>/` is the reference's repo (`monorepoPlace`). On the bench facts at `~/.cache/atticus/bench/facts/` (not edited), with the references as they are:

| Estate                     | Reference steps in order                             | Fields at crossings                 | Without the join (A3b, merge only) | Interfaces citing both ends |
| -------------------------- | ---------------------------------------------------- | ----------------------------------- | ---------------------------------- | --------------------------- |
| petclinic (angular + rest) | 25 of 87 (29%); 25 of 55 on the 5 flows with a start | 27 of 48 (56%); 27 of 29 on those 5 | 10 of 87; 21 of 48                 | 30 of 30 (0 before)         |
| microservices-demo         | 0 of 173                                             | 0 of 100                            | 0; 0                               | 29 of 33 (9 before)         |
| eShop                      | 9 of 163 (6%)                                        | 15 of 46 (33%)                      | 9; 15                              | 53 of 58 (16 before)        |

The exit bar (80% of steps in order, 90% of fields at crossings) is not met. What stops it is the facts' flows, not the join: the Angular facts have no flow for a page load (find owners, view an owner, the vets list), and the REST facts' flows are three steps (entry, write, respond) where the reference has eight; microservices-demo's facts have two flows (cartservice AddItem, checkoutservice PlaceOrder) and every reference flow starts in the frontend; eShop's have eight, and its references run to 79 steps. No start is by the strict trigger rule on petclinic: the facts cite a screen's route, the references the template's button. On petclinic's five flows that start and join, 27 of 29 crossing fields are found.

- **Not done here:** `atticus init --estate` and a `repos.yaml` of the design (the manifests and `atticus repos discover` stand in); the join's lineage and gaps in the rendered map (`map.md` lists calls and Interfaces, not FieldMappings); the release plan's deploy order computed from the joins (it still reads interfaces.md and data.md); a gRPC or SOAP call to a host nobody lists asked as a hosts question (only HTTP calls are); the bench CLI running the estate score (`scoreEstateFlows` is called from a script); reading more flows in the bench repos, which is the reader's work (A4) and what the bar now waits on.

## Addendum (A-incremental): a changed file invalidates only what cites it (§3; no C1 to C6 change)

Before this addendum a repo's facts file carried one commit. When the checkout moved, `atticus verify` rejected every fact as `wrong-commit`, a scan fell back to the readers, and the assistant had to read the whole repo again. CLAUDE.md rule 4 and §3 say a rescan invalidates only the facts that cite changed files and re-reads those files. This addendum builds that.

- **The diff comes from git.** `changedFiles(dir, from, to)` and `changesSince(dir, commits, to)` in `@maycombhq/workspace` run `git diff --name-status -M -z` between the facts' commit and HEAD in the checkout. They go through the git runner, so tests mock them. The diff is commit to commit: no working tree, no network. Renames are followed. A commit the clone doesn't have is `missing`, never guessed. One diff is taken for each distinct commit the facts name.
- **The split is pure.** `citedFiles(fact)` in `packages/core/src/facts-carry.ts` lists the fact's own cite, its `cite.with` parts and, for a flow, every step's and error path's cite and parts. `staleCite(fact, changes)` gives the first of those files that was edited, renamed (with `to`, its new path) or deleted. A file added or copied beside a cited one doesn't count. Each fact of an earlier commit is then one of three things:
  - **Still good.** Every cited file is unchanged. The fact is carried.
  - **To re-read.** A cited file changed. This holds even when the cited line didn't move, because the rule is "a changed file invalidates what cites it", not "a changed line".
  - **Of an unknown commit.** The clone can't compare that commit.
- **How a fact shows it was carried.** The facts schema doesn't change. `verifyFacts({ carry })` checks a still-good fact's claim, quote, parts and references against the checkout as for any fact, and keeps it with `commit` set to the commit verified. `VerifyReport.carried` records `{ id, from }`. `atticus verify` writes it as `carried: [{ from, facts: [ids] }]` in `<repo>.verify.yaml`, an additive field the Trust tab and the map's trust line ignore. The record belongs to the run that carried. A later verify at the same commit has nothing to carry and writes none. So the facts file still names one commit once verify passes, the Trust tab's same-commit test holds, and the catalog never says how a fact got its commit.
  - A fact to re-read is rejected as `cite-changed`, a new verifier code, additive like `call-out-no-call`. The message names the file, how it changed and what to do. The fact goes to `<repo>.rejected.jsonl` as it was read, at its own commit.
  - A fact of an unknown commit is `wrong-commit`, as before.
  - A fact naming a rejected one is `ref-rejected`, as before: it waits for the rewrite. A fact whose reference was dropped is `dangling-ref`.
- **The plan of a re-read.** `rereadPlan` (`packages/verify/src/carry.ts`) lists the facts to re-read with file, how and `to`, and counts the facts carried and already current. It also lists the source files to read: every file edited, added or renamed to, that is a source file under the coverage rule and not excluded, in reading order, each with the number of facts to rewrite that cite it.
  - `atticus map <repo> --estimate` prints the plan and estimates tokens and batches over those files alone. `--json` gains `reread` (with the whole repo's size), and `notComparable` lists commits it can't compare, for which it estimates the whole repo.
  - `atticus map <repo> --handoff` and `--copy` batch only those files. The facts to rewrite go back in the first prompt with their lines, as `cite-changed` rejections, under a re-read instruction: rewrite or leave out, don't write the carried facts again, add what is new. Each answer is verified with the carry. A fact to rewrite stays handed back until a batch rewrites it or the fix round leaves it out.
  - A re-read with nothing to read says to run `atticus verify`.
- **The protocol.** `/atticus-map` gains step 2: on a re-read, skip the outline, the whole-repo read and the unknown-files pass. Read the listed files, rewrite each listed fact under the same id at the new commit (a renamed file under its new path) or drop it, add the new files' facts, and leave the rest for verify to carry. `FACT_RULES` and `mapBatchInstructions` don't change. The re-read words are a prompt source of their own.
- **The scan.** `factsForScan` takes the checkout and a git runner. When facts are of an earlier commit, it runs the verifier with the carry over the checkout and uses the accepted facts at HEAD. Its note says how many were carried and how many were left out until the repo is read again. The readers stand in only when there is no checkout, a commit can't be compared, or nothing was carried. `@maycombhq/scanner` now depends on `@maycombhq/verify`, and there is no cycle.
- **Determinism.** The same commit, the same facts and the same answers give the same catalog bytes, whether the facts were carried or written at HEAD, and writing again changes nothing. `packages/cli/test/incremental-cli.test.ts` tests this on a temp Forge git repo whose commits the test makes, with a cited line moved, a file renamed, a file deleted and a file added. `packages/scanner/test/scan-facts.test.ts` tests the scan.
- **Not done here:**
  - A fact naming one to re-read is held back, though its own files are unchanged. The protocol rewrites the named fact first, so this happens only on a verify before the rewrite.
  - Uncommitted edits aren't diffed. The line check still catches a moved line.
  - Coverage's unknown list is still the whole repo's.
  - A renamed file whose content is unchanged (R100) is still re-read rather than having its cites rewritten.

  - ~~Screens and clients the facts have no field facts for still have no file step.~~ (B-places: the protocol asks for them, and a task names them; the bench repos' facts aren't read again yet)

## Addendum (B-places): the places a change goes into are in the map (no C1 to C6 change)

B-steps gave a story a step per place in the code, but three gaps kept its step coverage low (`docs/build-status.md`, B-places): a front end's model types, forms and displayed fields were not recorded as fields, so no task could name them; a step the change adds was cited at its neighbour's line; and no migration was known for any store, so a new migration could not be told from a schema file changed in place. - **A front end's places are field facts, in the shape the facts already have.** `FieldFact.side` already had `screen`, and `projectFacts` already made a Schema per owner and side: `<endpoint>.screen` for a screen entry's fields, `<call>.request` and `.response` for a call's, which follow the call's Interface when the estate joins it. So the narrowest shape is no new shape, only what the protocol asks for:
  - A model or client type's properties (a TypeScript interface, a class, a generated client's types) are the `request` or `response` fields of each call fact that sends or receives them, one field fact per call, citing the property's line.
  - A form's fields (form group controls, a zod schema's keys, a template's inputs) and the fields a screen shows are `side: screen`, owned by the screen's entry fact.

Without it the task is placed after the step before it, or the trigger, as before (`placed: neighbour` or `trigger`), and its prompt and story file say the target flow gives no place. The stories prompt doesn't change, so the recorded replays pass as recorded.
- **Migrations are facts, read off the citations.** A reader already cites a column where it is declared, often in the migration that adds it. `projectFacts` now recognises a migration file by its tool's naming (`migrationOf` in `packages/core/src/migration-files.ts`: Flyway `V<n>__*`, Liquibase changelogs, Alembic `versions/<rev>_*.py`, Prisma `migrations/<name>/migration.sql`, EF `Migrations/<timestamp>_*.cs` without its designer file, TypeORM and Knex timestamps, Rails `db/migrate`, Django `migrations/<nnnn>_*.py`, numbered `.sql` and `.up.sql`) among the citations of store facts and of the columns they own, and makes a C1 Migration record per file: `<store>.v<version>`, the tool (C1's enum: the others are `other`), the file, an operation per table with the columns it cites (`create` or `alter` only when a quote states it), and the citing facts as evidence. Chosen over a new fact kind because it needs nothing new from the reader, works on facts already written (the bench's), and stays an additive projection into C1's existing Migration kind; the cost is that a migration no fact cites is unknown, so the protocol asks for a column in the newest migration too.

  With the records, `migrationsOf` (architecture) gives the store's folder, newest and next name to the store-facts block, the name check and `migrationPath`. A Prisma migration is its folder. A migration the store already has is refused as the change's migration (`delta.bad-migration`, with the next name). So is a file out of their numbering (as before), or of another kind than theirs (a `schema.sql` beside Alembic's `.py` versions). A task no longer lists an existing migration as a file to touch, so the story's new migration is its own place. A store with no migrations is told so with the files its columns are declared in, changed in place, as B-steps did.

## Addendum (A-derived): names a framework derives (§2; no C1 to C6 change)

Batch 3's held-out read (`bench/README.md`) found true facts that couldn't verify because no line writes their name: the framework derives it. Hibernate's snake_case and join tables, Django's `<app>_<model>`, Devise's routes. The readers wrote the class name instead, or dropped the fact. §2's check stays: the claim rests on a cited line. What changes is that the line may declare the claim's source, and the claim is then the name the framework gives it.

- **One place, one rule per convention.** `packages/verify/src/derived.ts` holds the rules, each commented with the convention it follows. `derivedNamesAt` gives the names declared at the cited line or one either side, and at each `cite.with` part. The verifier accepts a claim that equals one of them: a table or worker name with letter case aside, a column as fields compare, a route with parameters in any style. A derived route may sit under a prefix that `with` parts write, such as Spring Data REST's base path. Its leading segments are then checked with `partsNamePath`, as any built path is. Nothing is fuzzy. A rule that can't settle a name gives none, for example when it can't find a target class or meets an enclosing block it doesn't know.
- **The rules:**
  - **JPA with Spring Boot's naming.** An `@Entity` without `@Table(name)` is its snake_case table. A `@OneToMany` without `mappedBy` or `@JoinColumn`, or an owning `@ManyToMany`, has a join table. Spring's form is `<owner table>_<property>` and JPA's is `<owner table>_<target table>`, both snake-cased. Its columns are `<owner entity>_<id>` (or `<inverse property>_<id>`) and `<property>_<target id>`. An `@ElementCollection` has `<entity>_<property>`. A `@ManyToOne` has `<property>_<target id>`. The target is found by its imports, its folder, or the one class of that name nearest the owner.
  - **Django.** A model class in an app's models module is `<app_label>_<model>`, unless it is abstract, a proxy or has `db_table`. The label is `Meta.app_label`, else the nearest `apps.py` up from it (its `label`, else its `name`'s last part), else the folder. Its `ManyToManyField` without `through` makes `<model table>_<field>`, and a `ForeignKey` or `OneToOneField` without `db_column` is `<field>_id`.
  - **Rails and Laravel.** A top-level ActiveRecord model is the plural of its underscored name, by ActiveSupport's default inflections. An Eloquent model is the snake_case of its plural. Neither applies when the table is set or the class is abstract. Laravel's `belongsToMany(X::class)` is the two snake_case names in alphabetical order.
  - **TypeORM and Prisma.** TypeORM's `@Entity()` is `snakeCase(class)`, and a nameless `@JoinTable()` is `snakeCase(<owner>_<property>_<target>)`. Prisma's implicit many-to-many, with list fields on both sides, is `_<A>To<B>` in alphabetical order, or `_<name>`.
  - **Routes.** Rails' `root` is `/` under its `namespace` or `scope`. Another enclosing block, such as `resources :x do`, settles nothing. Devise's `devise_for` gives the routes of the modules the model's `devise` call lists, with `skip`, `only`, `path`, `path_names` and the OmniAuth providers. Spring Data REST's `@RepositoryRestResource` gives `/<path>`, `/<path>/{id}` and its search methods. Without `path`, the path is the uncapitalized plural of the domain type, and nothing is given when `exported = false`.
  - **Workers.** An ActiveJob or Sidekiq class is named with its modules. A Celery `@shared_task` or `@app.task` without `name=` is `<module>.<function>`, the module running from the outermost package with an `__init__.py`.
- **A word put together from parts.** `partsBuildWord` in `packages/core/src/cite.ts` covers a word claim such as a rake `namespace:task` or a key a helper prefixes. Each `with` part's value must be in the claim as a whole piece, bounded by the claim's ends, a separator or another part. What is left, separators aside, must be written on the cited lines. Each part's own line is checked as before.
- **The protocol.** `FACT_RULES` gains one rule: a derived name is written as the framework makes it and cited on the line that declares its source, a name built from parts has them in `cite.with`, and a background job worker (Sidekiq, Celery, ActiveJob) is a `batch-job` entry named by its job. The entry rule adds that framework admin, health and ops routes (`/up`, `/admin`, a queue's web UI) are not entries unless the repo's own code handles them. Other rules were shortened so a tier 2 batch at 7,000 tokens still has room.
- **Checked on copies of batch 3's facts.** No original was touched. codetriage, django-styleguide and microservice-kafka verify as before, with nothing rejected. A copy with the names written the frameworks' way (and the join tables, Devise routes, root, workers and rake tasks the reads left out) verifies too. Without the derivations, 137 of its facts are rejected, most as references to a rejected store. Wrong names on the same clones are rejected: a plural join table, Django's label taken from a folder that isn't an app, a skipped Devise route, a singular Rails table. The bench isn't re-scored until the repos are read again.
- **Not done here:**
  - Tables of a third-party app that the repo doesn't declare (`django_celery_beat_*`).
  - Rails models nested in a module, `has_and_belongs_to_many`, Hibernate's naming without Spring's, and Devise's `path_names` for OmniAuth.
  - A class name written on the line still verifies as a table, as before. Precision there is the reader's.

## Addendum (B-place): where code goes, with the right verb (no C1 to C6 change)

A re-draft of a real change on the B-tasks build grouped 26 tasks into 15 and left no step without a file, but 9 of the 15 named the wrong one. Tasks told the developer to change shared code the new code should only call (a reader's method, a text helper, a shared page component), and put new logic beside unrelated files (a filter beside a helper, a document builder beside the model client, a page's states beside the web client). One printed "new code beside lines " with no line, from an `at` written as path:function. Three causes: the architecture format said a class a step calls counts as its `at`; the stories stage reads `at` as "the step's code goes after this line"; and `besideOf` gave a step with no place its neighbour's. Two steps that the existing client's call method already does (reserve and settle the model spend) got no "already done" note, and their tasks said to add the write after those very lines.

- **Three kinds of place** on an added step of a flow delta, each optional and additive (version 2 stays; the planner's stage file, not C1 to C6, per `docs/codebase-map.md`):
  - `at: path:line`: the code at that line changes. Only an edit there: a changed step, or an added step inserted into code the repo has.
  - `new: <path>`: the step's code goes in a file the change creates, named in the repo's own layout, in the folder of its nearest kin.
  - `uses: path:line` (one or a list): existing code the step calls or reuses. It doesn't change.
  - The format gives the three in place of the one `at` line, and one rule: give each added step `at` or `new`; a class or function it only calls is `uses`, never `at`; a step that code under `uses` already does needs neither.
- **The checks** (`placeIssues`, with `places.ts`), all blocking unless said:
  - An `at` must carry a line: path:function and the path alone are refused (`delta.at-no-line`), and `delta.at-function` goes with them. Its file must be the repo's (`delta.at-unknown`), the line within it (`delta.at-line`).
  - A call-out, publish, lookup or read whose `at` line is code it calls is refused with "use `uses:`" (`delta.at-calls`): another flow's step on that line that does a call or a read, or a method declared on that line in a file today's flow doesn't cite (`declaresMethod`, one line by pattern). Any other kind there is a note (`delta.at-shared`): keep `at` only if the change edits that method.
  - `at` and `new` together are refused (`delta.place-both`). A `new` file the repo has is refused (`delta.new-exists`), and so is one outside a folder the repo has (`delta.new-folder`). Without a checkout, a folder the catalog cites no file in is a note, since the catalog may not cite every folder.
  - A `uses` must name a file the repo has (`delta.uses-unknown`), with a line (`delta.uses-no-line`) the file has (`delta.uses-line`).
  - `new` on a changed or removed step is a note (`delta.new-not-added`), as `at` is.
  - An added step with neither `at` nor `new`, that existing code doesn't already do, is a note (`delta.no-place`). It is not blocking, so recorded drafts keep passing.
- **The stories stage says the verb.** `besideOf` is removed: a step with no place is "new code — place not given", never a neighbour's file. A modify flow's step with no place is still "not said by the target flow; after the step before it", as B-places had it. The story file, the task prompt and the implementation steps say "change `<file>:<line>`" (`placed: given`), "new file `<path>`" (`placed: new`, `newFile`), each with "(uses `<file>:<line>`)". "Files to touch" never lists `uses`, which is a line of its own, "Code it calls (unchanged)". The stories prompt's task lines name a new file and the code a task calls only when there is one, so the fraud check's prompt is unchanged.

## Addendum (C-join, the fallback): a relative call whose target names nothing (no C1 to C6 change)

A trial on one repo holding a React single-page app and the Spring API it calls joined 0 of 467 call-outs. The app's calls are relative (`fetch("/api/...")`), so the reader set each call's `to` to its guess of the API's name; Atticus named the API's component after the repo. `joinFacts` left a call whose `to` names nothing in the estate to that name (as for a vendor), and `joinEstate` stopped at "<name> isn't a component in the catalog" for 417 of them. Renaming `to` by hand joined 411.

- **The rule.** A call with no host (none written, none from a config fact's base URL) whose `to` names nothing in the estate, or that names no target, joins by method and path (gRPC and SOAP by name), only to an entry of the same shape (no prefix or catch-all), health and metrics paths aside: the one entry of the caller's own repo that serves it, else (none there) the one entry of the estate; never the caller's own component. Two or more entries where it looks (its repo, or the estate) is a question, never a guess. A `to` naming an outside system (an org pack profile's vendor, by id, name or alias: `outsideSystems`) keeps its name, and so does a `to` with a host nobody lists, as before. Before this, a call naming no target already joined the one entry of the estate; it now looks in its own repo first.
- **Marked inferred.** `FactJoin.inferred` (`{ within: repo | estate, named? }`) is on every join by path. `atticus verify <repo> --write` says how many of the repo's calls joined so, and where (`--verbose` lists each, with the name the call gave). The Interface keeps the merge's confidence rule (verified when both ends are cited): `mergeEstate` already resolves a relative URL to the one endpoint of the caller's system and marks it verified, and the join doesn't override it.
- **The question.** A call that names a target the estate doesn't have and that two or more entries serve is asked with the facts-targets question (`targetQuestionDrafts`, offering only those entries' components), and its answer is read back by `targetsFromAnswers` as for a call with no target.
- **`joinEstate` (specs) does the same** for a flow written before the fallback, so `atticus join` works on specs as they are: a step whose `to.component` is no component or repo in the catalog, nor a System, is read as a loose end (an Interface from the caller to a component of the catalog stands for it), else joins the only entry point that serves its method and normalised path exactly, the caller's own repo first, then the estate. Each such join is in `inferred` (`within: repo | estate | interface`, with why) and is printed "(by method and path, inferred)"; estate.yaml's schema has no field for it, so the file says `how: path`. Two or more components is an `asks` entry, raised as an `estate-targets` question (one option per component, then "None of these"); the next join reads the answer back and joins that component.
- **The protocol.** `/atticus-map`'s call rules say what `to` is for a call with no host: left out, or the id of the component that serves it when known; never a guessed name (one sentence; the rules' hash in `map.test.ts` re-pinned).
- **Fixtures and tests.** `fixtures/estate/relative/` (specs and catalog: own repo first, then the estate, two components asked, a loose end), `fixtures/estate-facts/relative/forge-notes.jsonl` (an app and its API in one repo, end to end through `catalogWithFacts` and `joinEstate`); `packages/core/test/facts-join.test.ts`, `packages/scanner/test/estate.test.ts`, `facts-estate.test.ts`, `packages/cli/test/estate-cli.test.ts`, `map-render-cli.test.ts`. The golden `fixtures/estate-facts/expected/join.yaml` gains `inferred: { within: estate }` on its one join by path.
- **Not done here:** the trial's own metarepo wasn't re-run. A relative call whose path a gateway rewrites (the app calls `/api/x`, the API serves `/x`) joins nothing by the fallback, which needs the same shape; naming the component in `to` still joins it.

## Addendum (A-big): a big repo's first read (§4; no C1 to C6 change)

A first read of a large Java and React monorepo (about 4,900 files) estimated 31.8M tokens, where its code was about 1.5M: coverage counted every JSON, HTML and XML file as source, including translation bundles, research tables of several MB, docs folders and a library's vendored source. The person found the data folders by hand, and the reader split the 1.5M tokens across sub-agents with no guidance.

- **Not product by default** (`packages/verify/src/not-product.ts`, used by `isSourceFile`): JSON, YAML and properties files under a locale folder (`i18n/`, `l10n/`, `locale(s)/`, `lang(s)/`, `languages/`, `translation(s)/`) and Android's `res/values*/strings.xml`; a JSON or XML file over 2,000 lines or 200 KB, unless it is a build, config, API or migration file (`pom.xml`, `package.json`, `tsconfig*.json`, `appsettings*.json`, an OpenAPI or Swagger file, a MyBatis mapper, anything under `config/`, `db/`, `migrations/`, `changelog/`). 2,000 lines is well past hand-written config that isn't a build file; 200 KB catches minified data. YAML isn't sized (a big one is a manifest or a spec). Coverage, the batch plan and the re-read apply the same rule.
- **Vendored code is proposed, not ruled.** A folder holding its own LICENSE could be a workspace package (which has its own build file) or a library's source dropped in; telling them apart by rule would be too clever, and a wrong rule would hide product code.
- **`atticus map --estimate` proposes exclusions** (`proposeExclusions`, `packages/verify/src/read-plan.ts`): the outermost folders holding at least 10,000 tokens and 2% of the repo, of which 90% are data (a structured file whose path says no kind, A-lean) or docs (a top-level docs or site folder) with no build, deploy or config file among the rest, and folders holding a LICENSE and no build file. Up to 10, biggest first, with their tokens, the tokens before and after, and a ready `exclude:` block for `org-pack/scan/<repo>.yaml`, each entry citing its biggest data file or its LICENSE. Atticus never writes it; a person accepts it in a pull request.
- **Reading in parts.** When the source, with the proposals left out, is more than one session reads (150,000 tokens, three quarters of a 200k context; or three quarters of a larger `--max-tokens`), the estimate proposes parts (`planParts`): folders whole where they fit, split into subfolders where they don't, in path order so a module stays together, each part closing at the room or its even share. `/atticus-map` gains a step: read one part per session or sub-agent, each adding its facts to the same facts file under the same id rules and verifying after each part; a fact two parts both need keeps one id. Tier 2 prompts are unchanged (the step is tier 1's).
- **Not done:** the parts don't follow the module graph (a Maven or Gradle module beside its own folder); `atticus verify` has no per-part coverage; an HTML reference text outside a docs folder still counts as a page.

### Follow-up (A-big2): what the first round still missed on a real repo

Run again on the same repo after A-big, the estimate flagged neither a third-party Python library cloned into `REFERENCES/` (its own LICENSE, setup.py and pyproject.toml, beside reference texts) nor a Java library's source copied into `jar/` with its LICENSE and README. - **The vendored rule** (`vendoredProjects`, `packages/verify/src/vendored.ts`). A non-root folder is proposed as vendored when either:
  - it holds its own LICENSE or COPYING and its own build file (`setup.py`, `pyproject.toml`, `pom.xml`, `package.json`, `build.gradle` and the like), and no build file above it includes it as a module. The module lists read are Maven `<module>`, Gradle `include`, `includeBuild` and `projectDir`, npm and yarn `workspaces`, pnpm's `packages:`, lerna's `packages`, Cargo's workspace `members` and go.work's `use`. A workspace glob matches.
  - it holds a LICENSE and no build file (a copied source tree), and its packages aren't the repo's own. A package root is the first two parts of a Java, Kotlin, Scala, Groovy or .NET `package` or `namespace`, or a Python package's top folder. The repo's own packages come from every file outside the folders that may be vendored. When either side's packages can't be told, the folder is proposed as before, with "check before accepting". When they share a root, it isn't proposed.
  - The estimate reads the files' text for this. Without it (`proposeExclusions(files, all)`), no project with its own build file is proposed, as before.
  - Still a proposal, never a rule: a person accepts each in `org-pack/scan/<repo>.yaml`.
- **Documents.** An `.html`, `.htm` or `.xhtml` file outside the product's page folders (`src/`, `app/`, `web/`, `public/`, `static/`, `resources/`, `templates/`, `views/`, `pages/`, `components/` and the like, and Angular's `*.component.html`) is a document. A folder of documents and data is proposed ("documents, not code") only when no code is beside them; data and top-level docs keep the 90% rule. A folder that holds vendored projects beside documents or data is proposed whole, citing its biggest project's LICENSE when vendored code is most of it. A folder holding just one vendored project leaves the proposal to that project.
- **Every qualifying folder is proposed.** The cap of 10 is gone, so the parts never read a folder that qualified. The estimate prints the first 10 and says how many more; the `exclude:` block and `--json` hold them all.
- **The parts are of the product code.** They were already planned over what is left. The estimate now says so: "The parts below are planned over what is left with the N proposed folders left out (F source files, about T tokens); no part reads a proposed folder."
- **Every list in `atticus verify` is summarised.** Each list is a count, the first 5, and "... and N more" with where the whole list is: `authUncited`, `entriesNoFlowFollows`, `carried` and `corrections` in `<repo>.verify.yaml`, and rejected facts, refused questions, lines that aren't facts and refused reviewed lines in `<repo>.rejected.jsonl`. The lists covered are entries without an `authCite`, entries no flow follows, rejected facts, refused questions, lines that aren't facts, refused reviewed lines, corrections applied and stale, carried commits and commits the clone lacks. Lines of the corrections file that aren't corrections are capped the same way.

It now says "R raised for a person now, K raised before, P refused (of N lines in …)" and "Q questions open for <repo>", with the first 5 and `atticus questions list --state open` for all. A re-run used to say nothing about questions already raised. `--json`'s `questions` gains `lines`, `known`, `refused` and `open`.
- **Not done:** a vendored library that the build does include as a module stays product. A nested project's LICENSE must be in its own folder. Go and JavaScript packages aren't compared.

## Addendum (A-read): what six readers of a real repo reported about `atticus verify` (§2; the facts file gains `authCite`, additive; no C1 to C6 change)

Six readers ran `/atticus-map` on a real repo and reported five problems with the verifier. Each is fixed here test-first on an invented Forge service, `fixtures/verify-read/` (forge-limits: a controller, a service only flow steps cite, a request with its validation rules, an entity and a pure `calc/` package). Tests are in `packages/verify/test/read.test.ts`, `packages/cli/test/verify-cli.test.ts` and `packages/core/test/facts-carry.test.ts`.

1. **Coverage counts what a flow walks through.** A file used to count as read only when a fact's own cite or its `cite.with` named it, so the services and helpers a flow passes through stayed `unknown`. A fully read repo showed 24% coverage, and its reader was told on every run to read 578 unknown files. A4-fixes had left flow steps out as weaker evidence. In practice each step's line is checked, and a reader who writes the step has read the file. Coverage now counts every file `citedFiles` lists for a kept fact: its cite and parts, an entry's `authCite`, and every flow step's and error path's cite and parts. That is the same list the carry uses (A-incremental). This includes `transform` and `branch` steps, whose values are still not checked. Their line must exist, and the step is visible in the flow.
2. **"Read, nothing here" is said in a file of its own: `<repo>.reviewed.jsonl`.** A pure computation library has no fact to cite, so it stayed at 0% however carefully it was read. The reader now writes one `{"path": "<file or glob>", "why": "..."}` line for each file or folder it read and found nothing to record in. The file sits beside the facts file, like the questions and the corrections. It is the verifier's input, not part of the facts file, and the facts schema doesn't change for it. This is the least contract-changing shape. Two alternatives were rejected: a new fact kind would reach C1's projection, and a field on facts would have nothing to stand on.
   - **The checks.** `parseReviewed` and `verifyFacts({ reviewed })` in `packages/verify/src/reviewed.ts` and `verify.ts` check each line. A line must be inside the repo and not a secret's file. A plain path must be a file of the repo at the commit, and a glob (`*` within a folder, `**` across folders, the exclusion globs' syntax) must match at least one. A line that fails any check, or isn't JSON of that shape, is refused: it goes to `<repo>.rejected.jsonl` as `bad-reviewed` with its line and why, and verify exits 1, as for a bad question. Nothing is reviewed on a refused line, so a reader can't hide a file behind a stale path. A reviewed file that a kept fact cites is simply read.
   - **What it counts.** Coverage has three counts: N read, M reviewed with nothing to record, and K unknown. `ratio` stays what facts and routed reads show, read / (read + reviewed + unknown), so a reviewed file never raises it (§2: never excused on the reader's word). A reviewed file just isn't unknown any more.
   - **Where a person sees it.** `<repo>.verify.yaml` gains `coverage.reviewed` (the count) and `reviewed: [{path, why, files}]`, each line with the files it stands for. `map.md`'s trust line says "M files reviewed by the reader with nothing to record (each with why, in the verify report)". Both are left out when there are none, so existing reports and maps are byte for byte as they were.
   - **The app.** The Trust tab's state reads `unknown`, so it turns trusted when nothing is unknown. It doesn't show the reviewed count, because that needs a field in `TrustView`, a C4 change, left for a C4 bump.
   - **The protocol.** `/atticus-map` step 8 asks for the file in one sentence. A file's age isn't tracked: on a re-read, a changed file is in the re-read list and read again whatever the reviewed file says. `atticus map`'s batch loop reads the file too, though a batch prompt doesn't ask for it.
3. **A `validate` step's value is checked.** `NEVER_CHECKED_STEPS` (C1, `packages/core/src/schema/kinds.ts`) lists `transform`, `branch` and `validate`. It is a C1 constant: catalog validation refuses `confirmedBy: check` on those kinds, and the projection and the scanner's spec check read it. So the constant doesn't change, and neither does the projection: a validate step is still never marked confirmed by the check. Only verify's own use changes (`stepClaims`). A validate step's `cite.value`, the rule as written (`50000.00`, `signum() <= 0`, `@NotNull`), must be on its line or one either side, with parts and the comment rule as for any step. A value with a `/` is also tried as a word, so a pattern isn't read as a route. `transform` and `branch` stay unchecked: their values are descriptions more often than code, and no safe check was found. On the 27 bench repos' facts (577 validate steps), none is rejected by this.
4. **An entry's `auth` rests on a line: `authCite`.** Nothing checked `auth`, so a reader could claim `mtls` anywhere. An auth checker (which annotation, middleware or setting means which scheme) is out of scope.
   - **The fix.** `EntryFact` gains `authCite: {file, line, value}` (optional; the `CitePart` shape): the line that sets the auth and what it writes there (`SCOPE_ledger.read` in a `@PreAuthorize`, `RequireCertificate`, `oauth2ResourceServer`). Verify checks it as it checks a part: the file is in the repo, the line exists, and the value is written there or on a line either side, and not only in a comment. A false citation rejects the entry (`claim-not-on-line` or `claim-in-comment`), and the message names the authCite.
   - **No authCite.** An `auth` without one is left out of the kept fact. So the facts file, the catalog's `Endpoint.auth` and the map never say it. It is listed as a note, not a rejection: `authUncited` in the report, `<repo>.verify.yaml` and the summary. A fact a person made (`by: person`) keeps its `auth`, since it is the person's word and marked as theirs.
   - **Why this shape.** A dedicated field over a `cite.with` part: a part there can't be told from the path's own parts, so any prefix would have made any auth "cited". Over marking the entry `conf: inferred`: that would also mark its path, which the line check did verify.
   - **Carry and protocol.** `citedFiles` lists `authCite`, so a changed auth line invalidates the entry (A-incremental). The protocol gains one sentence (routes and protocols batches): "An entry's `auth` goes with `authCite` … An `auth` without one is left out."
   - **The cost.** None of the bench facts has `authCite`. Re-verified, all 515 of their auth claims would be left out until the repos are read again.
   - **Fixture change.** `packages/verify/test/fixtures/forge-ledger.facts.jsonl`'s `oauth2` rested only on a comment. Its `AccountController.java` gained the `@PreAuthorize` line it describes, in place of an empty comment line, so no other line moved, and the fact cites it. The map golden is unchanged.
5. **Messages.**
   - **A complete read is said.** When nothing is rejected and nothing is unknown, `atticus verify` says "The read is complete: every source file is read (N) or reviewed with nothing to record (M)". It no longer says "Next: read the N unknown files" on every run. While files are unknown, it says where a file with nothing in it goes.
   - **All of a fact's problems in one run.** Verify now checks a fact's own cite, its `authCite`, every flow step and error path, every reference, and every call-out and publish step. `Rejected` keeps the first problem's `code`. When there are several, its `message` numbers them all, and the new `problems` lists them. A fact with one problem reads as before. A fact of another commit still has its one problem, and `ref-rejected` is still given only to a fact with no problem of its own.

**Measured** on the bench facts at `~/.cache/atticus/bench/facts/` (re-verified with this verifier, nothing written). Read files rose on every repo but node-realworld: eshop from 180 to 236 (unknown 476 to 420), spring-petclinic-rest from 45 to 64 (unknown 60 to 41), bulletproof-react from 95 to 127. No fact is newly rejected. laravelio's 13 `publish-no-event` flows (C-estate's check, newer than its last verify) are rejected as before, and 5 of them now list several publish steps at once.

**Contracts.** The facts file gains `authCite` (additive and optional, so every facts file written before still parses; the projection is unchanged). `VerifyReport` gains `coverage.reviewed`, `reviewed`, `reviewedProblems` and `authUncited`, and `Rejected` gains `problems` (the verifier's API, not a contract). `<repo>.verify.yaml` gains `coverage.reviewed`, `reviewed` and `authUncited`, each left out when empty. `<repo>.rejected.jsonl` gains the code `bad-reviewed`. C1 to C6 don't change. `FACT_RULES`' pinned sha256 was re-pinned for its one added sentence. The `/atticus-map` golden and `plugins/atticus` were regenerated. A tier 2 batch prompt grows by the reference's `authCite` field and, for a routes or protocols batch, the sentence; the map-cli tests still pass at 7,000 tokens.

- **Not done here:**
  - The app's Trust tab doesn't show the reviewed count (C4).
  - A reviewed line isn't tied to a commit.
  - Transform and branch values are unchecked.
  - The bench facts haven't been read again for `authCite`.

- **Where they live: a field on the entry, `scopes`.** `EntryFact` gains `scopes?: Cite[]` (additive and optional, so every facts file written before still parses): one citation per scope, its `value` the scope as written, on the line that names it, with any other line a scope is built from in `cite.with`, exactly as a path's parts are cited. A space-separated `<Scope>` list is one fact per scope, all citing that line. The field is on every entry, but only a gateway batch's rules ask for scopes (the prompt budget, below), so a service's own `@PreAuthorize` scope is read only where a reader writes it unasked.
  - **Why a field and not a fact kind of its own.** A scope has no identity apart from the entry that demands it: nothing refers to a scope, nothing is owned by one, and it is never read without its route. A kind of its own would widen `FACT_KINDS` (which the parser, the carry, the projection, the batches and every tool that counts facts read), need a projection into C1 and give a reader one more thing to get wrong, for a list of strings. The `authCite` precedent (A-read) is the same shape for the same reason. A `cite.with` part was rejected as it was there: a part can't be told from the path's own parts.
  - **No C1 change.** `GatewayRoute.scopes` already exists and was empty; it is now filled from the facts. `Interface` gains no `scopes` field: that would be a C1 bump from 3 to 4 with a migration and a rewrite of 48 record files and 44 tests, and a single list on the Interface could not say which hop of a chain demands what, which is the shape that matters. The hops' scopes ride on the join result (`FactJoin.scopes` and `GatewayHop.scopes`, core's API, not a contract) and on one GatewayRoute per hop, which the Interface's `route` names. An `Interface.scopes` field is left for a C1 bump if a reader ever needs the union without walking the routes.
- **Verify checks each like any other claim.** A scope is checked as a word on its line or one either side, its `cite.with` parts and its quote as for any cite, with the comment rule; a fact whose scope fails is rejected (`claim-not-on-line`, `no-file`, …) and the message names which scope (`scope 2 ("orders.admin")`). So an invented scope, or one cited on the policy's wrong line, never reaches the catalog. `citedFiles` lists a scope's files, so a changed `<Scope>` line invalidates the entry that rests on it (A-incremental).
- **The join carries them.** Each `GatewayHop` keeps the route's `scopes` in the facts' order and its `auth`; `FactJoin.scopes` is every hop's, in the order the call meets them, each once. `joinRecords` writes one `GatewayRoute` per hop with its own `scopes` and `policies`, citing the route's line, its `authCite`'s line, every scope's line and the forwarding call's line.
- **The critic uses them** (`constitution.public-entry-auth`, question `safe`, the four questions unchanged and no new check added): a public entry through a gateway route that demands no scope is an issue naming the route ("checks who the caller is and nothing about what they may do"); a caller whose own callers' routes demand scopes, none of which a downstream route demands, is a knowledge gap asking how it gets a token for them (raised only where the facts show both sides, never on a caller nothing is known about); and a scope a story's acceptance criteria name, quoted or in backticks on a line that says "scope", which no route the change names demands, is an issue. Where the facts settle it, it is a finding; where they don't, a question; never a silent pass.

### 2. Many hops, internal and external

- **The walk** (`joinFacts`). A call that lands on a gateway's route joins where the route forwards, and where that is another gateway's route the walk goes on, so `FactJoin.gateway` is the hops in order and `path` is what the last one's target receives. `MAX_GATEWAY_HOPS` is 4. A route that forwards back into a gateway already in the path, or a chain past the bound, raises an ask with the new reason `cycle` ("Where does GET /pay/loop/ping, which edge-gateway calls, end? Its gateway routes lead back into partner-gateway, which it has already been through, so the facts can't say."), with both routes as candidates; the call still joins the gateway route it does reach, so what is known stays and only where it ends is asked. A hop whose next step is asked, missed or forwards to several services ends the chain there, exactly as one hop did.
- **Internal or external, read not guessed.** A hop is marked `facing: internal` or `external` from the manifest's repo type (`gateway-external`, `gateway-internal`; a plain `gateway` says nothing), else from the proxy's own `<VirtualHost>`, which the protocol now asks the reader to record as a `config` fact (`key` `VirtualHost`, `target` the proxy). The words are `FACING_WORDS`, overridable per estate (`joinFacts`'s `facing`), because which virtual host means which side is each estate's convention. A value neither list knows leaves the hop a plain gateway: no basepath or host shape is read as a boundary. `joinReposOf` types any `gateway*` repo a gateway.
- **The views.** `map.md`'s call lines print the whole path — `via forge-pay-v1 /forge/pay/v1 (OAuth-VerifyPay; scopes payments.charge) then northwind-pay-v1 /pay/v1 (OAuth-VerifyCharges; scopes northwind.charges.write)`, and the auth the caller meets — and the app's Interface page gains "The path of the call": each hop's proxy and base path, what it checks, and its scopes or a marked "no scope demanded", ending at the service and its path, with the words in the copy file. Both find the hops as the GatewayRoute records the Interface cites on its gateway side, matched by the line each rests on, so they show what the catalog holds and nothing more, and a call with no route record reads as it did.

### 3. An authCite's policy kind

`packages/verify/src/apigee-policy.ts` finds the bundle a citation sits in (up to and including its `apiproxy/` or `sharedflowbundle/`), opens `policies/<name>.xml` and reads its root element. `OAuthV2`, `OAuthV1`, `VerifyJWT` and `VerifyAccessToken` make `oauth2`, `VerifyAPIKey` `api-key`, `BasicAuthentication` `basic`; 22 elements that authenticate nobody (`SpikeArrest`, `AssignMessage`, `Quota`, …) make none. A claimed auth the element cannot set is rejected with the new code `auth-policy-kind`, naming the policy, its file and what it does check. A policy the module doesn't know (a `FlowCallout`, which may lead anywhere, a custom or newer policy), one not in the bundle, and a citation outside a bundle are not judged: a check that can't be sure says nothing.

**Contracts.** The facts file gains `scopes` on an entry (additive and optional; the projection is unchanged, and `GatewayRoute.scopes` was already there to hold it). `RejectCode` gains `auth-policy-kind` and `FactJoinAsk.reason` gains `cycle` (the verifier's and the join's APIs, not contracts). `FactJoin.gateway` is a list of hops where it was one hop, and `GatewayHop` gains `auth`, `scopes` and `facing`; `joinFacts` gains `facing`. C1 to C6 don't change. `FACT_RULES`' pinned sha256 was re-pinned for the Apigee rule's fourth part; the `/atticus-map` golden and `plugins/atticus` were regenerated.

**The prompt budget.** The gateway batch's instructions go from 6,650 characters (about 1,663 tokens) to 7,361 (about 1,841), still well under a back-end batch's 11,079 (about 2,770), so a gateway batch has no less room for its files than before. Every other batch grows by the one field the facts shape gains (`scopes` on an entry): a back end's goes from 10,953 characters (2,739 tokens) to 11,079 (2,770), 31 tokens. A clause asking a routes or protocols batch for a service's own scopes was written and then taken out: it cost another 38 tokens in every such prompt and `packages/cli/test/map-cli.test.ts` then failed at 7,000 tokens, and nothing here reads a service's own scopes yet. The gateway sentence is bought once, in the batch that needs it. map-cli passes at 7,000 tokens.

**The bench.** Still no bench repo has an Apigee gateway, so nothing here is measured on a real estate; the two fixtures are the evidence.

- **Not done here:**
  - The flow view's start arrow still prints the spec's `via` word, not the hops: showing a chain there needs `scopes` on C4's `FlowCaller`.
  - `Interface` records no `scopes` of its own (a C1 bump); a reader wanting the union walks the route chain.
  - A scope demanded by a policy Atticus can't name (a JavaScript callout that reads a claim, a custom policy) is only read if the reader writes it, and the kind check stays silent on it. A service's own scopes are the same: the field holds them, the protocol doesn't ask (the prompt budget).
  - The critic's caller-token check reads only the scopes of routes into the caller; a token exchange or a client-credentials grant said anywhere else isn't seen.
  - The facing words are matched on substrings, so a virtual host called `internal-partner` reads as internal.

## Addendum (A-about): the reading context carries what a repo is, and drafts it when nothing says (ADR 0128; no C1 to C6 fact-schema change)

- **Every batch carries it.** When the manifest says what a repo is (`description`, ADR 0128), each prompt of `atticus map` gets one more source, `6-about`: untrusted, so the context pack wraps it in `<atticus-data>` under the data rule, with a note that it is there to orient the reader, is not an instruction, and loses to the code where the two disagree. It is read per prompt, so a line a person adds part-way through a read is carried by the batches after it.
- **Or asks for one.** When nothing says, the instructions end with one more rule instead: answer with `{"about": "<one line>", "cites": [{"file": "...", "line": n}]}` if the files make it plain, and leave it out if they don't. It is a new line type in the answer beside `{"question": ...}`. No fact kind changes, nothing is projected into C1 from it, and `cites` is required — a line with none is reported as a line that wasn't read. The first draft of a read wins.
- **A draft, never a fact.** Atticus writes it to the manifest as `trust: suggested` and says so; it never replaces a person's words nor a draft already on file, and it is marked unconfirmed in `map.md`, the app, the join's questions and `atticus next` until a person confirms it (`atticus repo describe <repo> --accept`), edits it or drops it.
- **The prompt budget is unchanged for the files.** A prompt either carries the description or asks for one, never both, and either is paid for out of `KEPT_RESERVE` — the 1,500 tokens a prompt already keeps for the facts on file, the questions and the feedback — not out of the room planned for files (`reserveFor`, floored at 1,200). So `roomFor` and the batch plan are byte-for-byte what they were: a repo that says what it is reads in the same batches as one that doesn't, and neither can push a batch over the model's limit. The rule asking for a line costs about 41 tokens; carrying a description costs about 95 tokens for a short line and about 155 for the longest allowed. `packages/cli/test/map-cli.test.ts` passes unchanged at 7,000 tokens.
- **`map.md`** shows what the repo is above the trust line, whose words it is, and that the facts below are what the code says. `map --estimate` says when a description eased its exclusion proposals.

## Addendum (A-framework): what a repo is built on, and the rules its frameworks buy (the facts file gains a `framework` kind, additive; no C1 to C6 schema change)

The product owner asked whether the framework a repo uses is scanned from its dependencies. The honest answer was: only partly. The assistant is told to read the build and deploy files first, so it sees the dependencies, but **no fact recorded the framework**; `atticus repo type detect` and the legacy `houseDependencies` reader read poms, Gradle builds and package.json, but that is Atticus 1's path and a repo-type guess; the C6 framework files (ADR 0054) teach Atticus a house annotation only once someone learns one; and the reading rules knew framework behaviour in general, but a batch's rules were chosen **by file path alone** (`RULE_TOPICS` / `FILE_KINDS`, addendum A-lean), so a Spring repo and an Express repo got the same route rules. All of it is fixed here test-first on a third invented estate, `fixtures/frameworks/` (nine repos: Spring Boot with a module of its own and a house starter, ASP.NET, Express, Angular, React, Quarkus, Django, Rails with Sidekiq, and a Spring Boot repo whose routes are hidden in a house starter), with its facts written by hand.

### 1. A framework fact

- **A kind of its own, not a field.** `FACT_KINDS` gains `framework`: `name`, `version?`, and the common fields every fact has. A-gateway2's precedent for "a field, not a kind" turns the other way here, for the same three reasons read in reverse. A scope has no identity apart from the entry that demands it; a framework's subject is the **repo or the module**, which `common` already carries as `repo` and `component`, and no other fact owns it — a field would have to hang off an unrelated fact, and a repo can declare Spring Boot before any entry, call, store or deploy fact exists (a library repo, a starter, a repo whose entry points the reader hasn't reached). Nothing refers to a scope; a framework is referred to by name by the rule chooser, the missed-read check, the repo-type signal and the C6 framework files. And a scope is never read without its route, while a framework is read **first and on its own**: the rules a batch's prompt carries are chosen from it before any entry is read. The cost A-gateway2 named is paid once and is what it said: `FACT_KINDS` widens, and the parser, the carry, the projection, the batches, `claimOf`, `factLabel`, the bench's counters and the conformance text all name the new kind.
- **The version rides on `cite.with`.** `version` is the version as declared. Where the declaring line doesn't write it — a `<properties>` entry, a parent pom's `<version>`, a `<TargetFramework>`, a dependency-management block — that line goes in `cite.with`, exactly as any other part of a claim built across lines does (A4), and the verifier checks it there with the machinery that was already in `checkCite`. No field of its own: the version is part of this claim, not a claim about something else, and a `versionCite` field would have cost about 31 tokens of the facts reference in **every** batch prompt for a shape `cite.with` already has.
- **The verifier checks the declaration, then the name it means.** `cite.value` is the declaration as the build file writes it (`spring-boot-starter-parent`, `Microsoft.NET.Sdk.Web`, `express`, `gem "rails"`), and the line check confirms it is written there like any other claim. The **name** is then checked against what that declaration means (`frameworkOf` in `packages/verify/src/frameworks.ts`, where the named knowledge belongs: core never branches on a framework's name): a declaration Atticus knows must carry the name Atticus gives it, so `name: "nest"` on a line declaring `express` is rejected with the new code `framework-name`; a declaration it doesn't know (a house starter, a framework newer than the table) must be named as the build file writes it, group, version suffix and letter case aside, so a reader can't put a name of its own on an artifact nobody here can read. A version written nowhere is rejected as any claim off its line is. The declaration table matches a Maven or Gradle coordinate's artifact, an npm package with its scope, an MSBuild SDK, a PyPI requirement (`django==5.1.1`), a RubyGem and a Composer package.
- **Build files the reading order was missing.** `Gemfile`, a `*.gemspec`, `requirements*.txt` and `composer.json` are build files now (`BUILD` in `packages/verify/src/batches.ts`), so a Rails, Python or PHP repo's framework is read in the first batch with the other build files instead of somewhere in the middle of the repo. `fileKinds` gives them `deploy` and `config`, as it gives every build file.
- **Nothing is projected into C1 from it.** No record there holds what a repo is built on, and a field on `Component` would be a C1 bump from 3 to 4 with a migration and a rewrite of every record file — the cost A-gateway2 refused for `Interface.scopes`. A framework fact does give its repo or module a `Component`, as every other kind does. The views read the facts themselves: `renderMap` takes them as an input beside the description (A-about's precedent), and so do the Trust tab and `atticus verify`. An `Component.frameworks` field is left for a C1 bump if a reader ever needs to query it.

### 2. Rules chosen by framework, not only by file path

- **A rule part can name its frameworks.** `RulePart` gains `on?: FrameworkTopic[]` beside `when?: RuleTopic[]`; `FRAMEWORK_TOPICS` in `packages/assistant-files/src/map.ts` is `spring`, `aspnet`, `express`, `nest`, `angular`, `react`, `vue`, `next`, `quarkus`, `django`, `rails`, `laravel` and `house`, mirrored as `FRAMEWORKS` in @maycombhq/verify with a test holding the two equal, as `FILE_KINDS` and `RULE_TOPICS` are. A part needs its kind **and** one of its frameworks. The derived-names rule (A-derived) was cut into one part per framework, each saying more about its own than the single compressed clause could; the MVC route clause came out of the generic path rule; the slugified routes, the ASMX method and the page-by-its-place rule are ASP.NET's and Next.js's; and three new parts say how Angular's, React Router's and Vue Router's own routes are written. The `house` part tells a reader that one of a house framework's annotations, base classes or wrapper clients may serve a route or read a table with nothing in the repo's own code to show it.
- **Where the frameworks come from.** `frameworkTopics` reads the repo's own framework facts kept so far. The build files are read first, so from the second batch of a first read onwards it is the code that says. Before that, and only then, `frameworkTopicsOfType` takes the repo's `type` in the manifest as a hint (`spring-boot` or `java` → spring, `dotnet` → aspnet, `frontend` → the four front ends, `node` → express, nest, next and react, `python` → django); it is written nowhere and decides only which rules a prompt carries, so the rule that a document never overrides a fact holds. A repo with neither carries no framework part at all: a framework's rule refines a rule that is already there, and is bought by evidence. `factRulesFor()` and `mapBatchInstructions` with no `frameworks` still carry every one, so tier 1 is every rule as before; an empty list means none are declared.
- **The plan and the prompts agree.** `overheadOf` counts the frameworks the read will carry, so the room the batch plan leaves each file is the room its prompt really has. `map-cli` passes at 7,000 tokens, and the rooms are larger than before, not smaller.
- **Measured** (instructions only, `estimateTokens`, repo and commit as in the tests). Before, every repo's back-end batch was the same 2,773 tokens and every front end's 2,259, because the rules knew nothing of the repo. After: a Spring repo's back-end batch is 2,698 (−75), a .NET repo's 2,742 (−31), an Express repo's 2,678 (−95); an Angular front end's is 2,138 and a React one's 2,175 (−121 and −84), a Next.js one's 2,205 (−54), and a Spring repo that also declares a house starter 2,788 (+15, the `house` part it needs). A build and deploy batch goes from 1,463 to 1,698 (+235): it is the batch that carries the rule for writing the fact. The core is 1,028 to 1,038 and a gateway batch 1,843 to 1,853: +10 in every prompt for the new kind's two fields in the facts reference. A prompt for a repo that says nothing at all carries every framework's rules and is 3,291 — bigger than before, which is why `atticus map` always passes what it knows, and why the plan counts it. Tier 1 (`FACT_RULES`) goes from 2,896 to 3,625 tokens: it is a file, not a prompt, and it now says more about each framework.

### 3. A framework whose patterns the facts show none of

`frameworkGaps` (in `verify`, on the kept facts) names a framework the repo declares whose shape of fact none of its facts hold: a REST entry for Spring Boot, ASP.NET, Express, Nest, Quarkus, Django, Rails, Laravel; a screen for Angular, React and Vue; a `batch-job` for Sidekiq and Celery; a table for Hibernate, Entity Framework, TypeORM and Prisma. It is a note and a question for a person, never a rejection: `atticus verify` prints it and the report keeps it under `frameworkGaps`, `map.md` puts it in the open above the trust line, and the Trust tab marks it. Kept to what the facts support: only for a framework Atticus knows the shape of, only when the facts hold something else of the repo (a repo nobody has read is not a repo whose entry points were missed), and never for a house framework — nothing here can say what its patterns look like until it is learned.

### 4. An unknown house dependency becomes a prompt to learn it

`frameworksToLearn` names the framework facts whose declaration is neither one Atticus knows nor one the org pack's framework files cover (by their `name` or their `artifacts`, matched as a declaration is). `atticus verify` prints why and the command, `atticus frameworks learn <name> --from <repo>` — the path that already exists (ADR 0054, 0055) — so a house starter is taught once rather than having each repo's annotations read as ordinary code.

### 5. Where it shows

`map.md`'s **Built on** line above the trust line, beside what the repo is, each framework with its version as declared, its module where a module declares its own, and a link to the line that declares it. The Map's facts view gives a framework fact its own label (`factLabel`), so it is correctable like any other. The Trust tab gains `frameworks` per repo (C4 2.29.0, additive): the name, the version, the module, where it is cited and the question where its patterns are missing — the estate's answer to what each repo is built on. `detectRepoType` takes a framework the repo's facts declare over any guess from the files, with the citation as the signal and `high` confidence, a gateway's bundle aside; `atticus repo add` passes the facts of a repo that has been read. Words from the copy file.

### 6. The bench

No bench reference turns on a framework: `covers` is one of serves, calls, stores, deploys, fields and config, and none of the 28 references lists what its repo is built on. So **nothing here is measured on a real estate** — the nine fixtures are the evidence. A framework fact is left out of the projection and counted (`left.frameworks`), as a screen and a job are, so a read that writes one is neither better nor worse on this bench for it, and the committed scores are unchanged. Scoring it would need a `frameworks` section in the references, which is a change to the references, not to a reader.

**Contracts.** The facts file gains the `framework` kind (additive: every facts file written before still parses, and the projection writes no new record). `RejectCode` gains `framework-name` and `VerifyReport` gains `frameworkGaps` (the verifier's API, not a contract). `RenderMapInput` gains `frameworks`. C4 goes to 2.29.0 for `frameworks` on a repo in `GET /api/trust`, additive. C1, C2, C3, C5 and C6 don't change. `FACT_RULES`' pinned sha256 was re-pinned, and the `/atticus-map` golden and `plugins/atticus` were regenerated.

- **Not done here:**
  - The gap check reads the whole repo's facts, so a module (ADR 0057) that declares a framework and has no entry of its own is not named while another module of the repo has one.
  - `repos discover` still guesses a repo's type from its files alone: it runs before any read, so there are no facts to take.
  - A framework a lock file pins and the build file doesn't name is not read, and neither is a transitive one: the rule asks for what the repo is built on, which is what a build file declares.
  - The declaration table is a list in code, not an org-pack file, so an organisation can't add a framework to it without a change here; a house framework goes through the C6 framework files instead.
  - A framework fact is projected into no C1 record, so a query across the estate goes through the Trust tab or the facts, not the catalog.
  - The bench is not re-scored, since no reference turns a framework on; and the per-framework rules are not measured against a model's reading accuracy, only sized.

## Addendum (A-ledger): a part read has a recorded state, and a call out of the estate is a name (§4; the facts folder gains a companion, additive; no C1 to C6 schema change)

A trial on a real repo found two things about reading a repo bigger than one session.

**The read plan is a file, and which part is next is read back from the facts.** `atticus map <repo> --estimate` planned that repo's read in thirteen parts and nothing recorded them: the parts were re-planned on every run, nothing said which were done, and the person kept the list by hand across thirteen sessions. The plan is now written beside the facts as `facts/<repo>.read-plan.yaml` (a facts companion, `FACTS_COMPANIONS`): its schema version, the repo, the commit and the session budget it was planned for, and the parts in the order they are read, each with the folder globs it covers, its file count and its tokens. `--estimate` writes it when there is none and leaves it alone while the commit, the session budget and the parts are the same, so a part already read keeps its number.

A part's state is not anyone's word that it is finished: it is read back from what the reader produced. A part's unit (a folder glob `planParts` gave it) is accounted for when a kept fact cites a file under it, or `<repo>.reviewed.jsonl` names it as read and holding no fact (addendum A-read). A part whose every unit is accounted for is `done`; one with some is `part-read`, and says which folders have nothing yet; the first that isn't done is next. So the ledger survives a lost session, a sub-agent, and a second person continuing, and re-reading a part can only ever leave it done. `--estimate` prints each part's state and names the one that comes next, `--json` carries the whole plan under `parts.plan`, and `atticus next` says `part 4 of 13 is next, 3 are read` with the folders that part reads instead of "isn't read yet". A repo that fits one session has no plan and no ledger.

**A call out of the estate is a name the catalog has.** At the architecture stage every change that called a model provider was told that `POST /chat/completions` and `POST /messages` were "names that neither the catalog, the knowledge, the specs nor the code has" — while the catalog held both, as `call` facts projected into `Interface` records with their method and normalised path. The index knew an endpoint name only from an `Endpoint` record, and a call out of the estate never has one: an `Endpoint` is read from the code that serves it, and nobody reads a vendor's code. So the gap was in the lookup, not the catalog, and every such change paid for it with a question nobody could usefully answer.

An `Interface` with a method and a normalised path is now indexed under its endpoint name too (`how: "call"`), beside the `Endpoint` records. A hop inside the estate gains nothing it didn't have; a call to a vendor or a model provider is known by the method and path the facts recorded, and its own record is selected into the step's pack, so the step reads what the catalog holds about the call rather than guessing. A call the catalog does not hold is still a gap: the fix widens the lookup to what the facts say, and invents nothing. The index schema version goes to 4, so an index built before this is rebuilt once. Proved on a Forge fixture whose ledger calls Thornefield Models, an invented model provider with no `Endpoint` record of its own.

## Addendum (A-uncited, A-room): what a `--write` keeps, and the memory a big read needs (no C1 to C6 change)

A trial of `atticus verify --write` on a real 4,900-file repo with 2,279 facts — the single command the whole read loop ends in — found two faults. Both are fixed here test-first on the invented Forge estate (`fixtures/verify-read/`, `packages/verify/test/fixtures/metarepo/`); nothing from that repo is in this one.

### A-uncited. The facts file keeps what its reader wrote; the catalog is where a claim is dropped

A-read point 4 took an entry's `auth` out of the kept fact when no line was cited for it, and listed it as `authUncited`. `writeVerifyFiles` then overwrites `facts/<repo>.jsonl` with those kept facts, so `--write` rewrote the assistant's own file with 221 auth claims gone. The warning went with them: the dry run said "221 entries' auth left out", and the second `--write` said nothing, because there was no longer an `auth` to notice. A person who re-verified was told their estate's auth was fully recorded while 221 endpoints said nothing about it. The loss and the evidence of the loss disappeared together, which is the worse half.

It was the right drop in the wrong place. So:

- **The kept fact keeps its `auth`.** The facts file is the reader's own; nothing it claims is taken out of it by the verifier.
- **The catalog drops it.** `catalogAuth` (core, `facts.ts`) gives an entry's `auth` only where `authCite` is set or the fact is a person's, and it is the one gate every path into C1 goes through: the projection's `Endpoint.auth`, and the three places the estate join reads an entry's auth (a `GatewayRoute` hop, a gateway Interface's `route.auth ?? entry.auth`, a direct Interface's). So an uncited auth reaches no record, in this repo's catalog or through the join from another's.
- **So the count is the same on every run**, `--write` included, until a line is actually cited: that is what the tests assert, three runs deep, on the file each `--write` left behind.
- **The message says what to do and what is where**: "N entries' auth rests on no cited line … kept in `facts/<repo>.jsonl`, as the reader wrote them, and left out of the catalog, so the map never says an auth nothing shows. To record them: give each entry an authCite — the file and line that sets the auth and what it writes there — and run `atticus verify <repo>` again."

**What else that function changes on disk, audited.** Two rewrites stay, because they change the bytes of a quote and never a claim, and one gains a count:

- **A secret in a quote is redacted** (`redactSecrets`) — kept, and the point of the exercise: a secret must not sit in a file. Its count does fall to zero on the next run, as `authUncited`'s used to, but for the opposite reason: the file now holds the right bytes and there is nothing left to do. Tested: the secret doesn't come back, and the second run claims no new redaction.
- **A quote the cited line can't be checked against is left off** (`quoteNotRequired`: a minified bundle, a notebook, a binary, a line over 1,000 characters). This differs from the auth claim in that a quote is corroborating evidence, not a claim — the route, topic or key is still checked on the line — and in that no warning hangs on it. But it was silent, so `VerifyReport` gains `quotesDropped`, `<repo>.verify.yaml` gains it when there is one, and `atticus verify` says it with the reason.
- **`verified` is overwritten** with `line` unless a person made the fact — deliberate (a reader can't vouch for itself), written into the file, and stable on a re-read.
- Nothing else in `accepted` is dropped: `reviewed.jsonl` and `<repo>.rejected.jsonl` are untouched by the write, which the test checks too.

### A-room. A read too big for the memory given says so

On an 8 GB machine with under about 2.6 GB free, `verify --write` was killed with **exit 137 and not one byte of stdout or stderr**; three runs were wasted before the tester saw it wasn't an Atticus bug. 137 is the kernel's own SIGKILL, not V8's heap limit, so no handler runs and nothing can be printed. A bank laptop with an IDE open meets this on a repo of this size.

**Where the memory went.** The verifier's line cache was unbounded, and the coverage pass asks every file of the repo whether it counts as source — so every one of the 4,900 files' lines were held, as arrays of strings, for the rest of the run. A file's lines cost about twice its bytes, which is the whole peak. Second, the facts file was read as one string and split into an array of every line, so it was held three times over (text, lines, parsed facts) before a fact was checked.

- The cache is now a window of `LINES_HELD` (64) files, oldest freed first. The facts are in id order and a fact's cite, parts, steps and error paths sit in a handful of files, so nearly every hit is kept.
- The coverage pass reads a file's lines, looks at them and frees them: nothing of a file no fact cites is held.
- The raw text of a file is dropped as soon as it is split, so one copy of a file is ever in hand.
- `streamFacts` (CLI, `memory-room.ts`) reads `<repo>.jsonl` a line at a time through core's new `parseFactLine`, which `parseFactsLines` now uses too, so a streamed read and a whole-text read give the same facts and the same issues.

**The ceiling and the message.** `roomGuard` is passed to the reader and to `verifyFacts` as its new `room` option, and is called once per line, once per fact and once per file of the repo, reading the memory every 32nd call. Past 80% of its ceiling it throws `NoRoomError`, which `atticus verify` prints and exits 2 on: "forge-estate's facts need more memory than Node was given: 135 MB of the 148 MB ceiling is in use. Run it again with ATTICUS_MAX_OLD_SPACE=4096 (megabytes Node may use for the heap), or in parts, a repo at a time. Closing an IDE frees the memory this needs."

What it watches is **resident memory**, not the heap, because resident memory is what the kernel kills on and is always the larger of the two (149 MB to 56 MB of heap on the estate measured below). The ceiling is the **lower of V8's heap limit and what this machine can hand this process** — what is free, plus what the process already holds, since `freemem()` leaves that out — because the kernel is what struck: a heap limit raised above free memory only moves the kill later.

`ATTICUS_MAX_OLD_SPACE` (megabytes) is honoured by **starting Node again** with `--max-old-space-size`, as `scripts/bundle/fetch-model.mjs` starts again for a proxy, rather than by the CLI setting a flag for itself: a running V8 cannot raise a heap it has already made, so a restart is the only way to make the message's advice true. Because that advice has to work wherever a person sets the variable, a `--max-old-space-size` already in effect — which an editor's or a wrapper's launcher may have set low — is raised to it, and never lowered to it. It costs nothing on an ordinary run: unset, nothing is imported and nothing is spawned, and `--version` still answers before any of it. `reExecForMemory` is a pure function, tested on its own, with `bin.ts` doing only the spawn. End to end on the synthetic estate: at a 100 MB heap the command prints the message and exits 2; with `ATTICUS_MAX_OLD_SPACE=4096` in front of the same command it restarts and keeps all 2,300 facts.

**Measured** on a synthetic Forge estate built from the fixture: 4,900 files (136 MB of invented Forge Java), 2,300 entry facts, 1.0 MB facts file. Peak heap **252–265 MB → 51–57 MB**; peak RSS (what the OOM killer watches) **351 MB → 146–150 MB**. Both runs keep all 2,300 facts and reject none.

**Contracts.** `VerifyReport` gains `quotesDropped` and `VerifyOptions` gains `room` (the verifier's API, not a contract). `<repo>.verify.yaml` gains `quotesDropped`, left out when none, so existing reports are byte for byte as they were. Core gains `catalogAuth`, `parseFactLine` and `BadFactLine`, all additive; the facts schema is unchanged, so every facts file written before still parses — and one written before this now **keeps** an auth it would have lost. C1 to C6 don't change.

- **Not done here:**
  - `atticus map`'s batch loop reads its facts with `parseFacts` on the whole text and passes no `room`, so only `atticus verify` has the ceiling; a very large batch answer can still be killed.
  - The ceiling is read once, when the command starts: memory another process takes while the read runs isn't noticed.
  - Nothing bounds the catalog write itself, which holds every record of the estate; the trial's write fitted, but a much larger estate would need the same treatment.
  - The bench repos' facts still have no `authCite`, so their 515 auth claims stay in their facts files and out of their catalogs.

## Addendum (A-mocks): a prototype's mocks and sign-on, read as a topic of their own (ADR 0133; no C1 to C6 fact-schema change)

- **A topic, `mocks`.** `RULE_TOPICS` and `FILE_KINDS` gain `mocks`, with one rule of two parts. The rule is kept apart from the gateway's, on its own line.
  - **The mocked operations.** A mock is the backend a prototype expects. Each mocked operation is a `rest` entry, with `{name}` for each parameter, cited where it is declared: an MSW handler, a WireMock mapping's `url`, `urlPath` or `urlPathTemplate`, a json-server `db.json` key or `routes.json` line, a Postman mock collection's request `url`, or a controller that runs only under a mock profile (with the `@Profile("mock")` line in `cite.with`). What it accepts and returns are `request` and `response` field facts owned by the entry. The mock tool's declaration is a `framework` fact on the mocks' module.
  - **The sign-on.** A prototype's sign-on (SSO, OIDC) configuration gives each BFF route its `auth`, with `authCite` on the line that wires it in, and its `scopes`, one citation each.
- **Told by the path, as a gateway's files are.** `fileKinds` gives `mocks` to:
  - a file in a `mocks/`, `__mocks__/`, `stubs/`, `msw/` or `wiremock/` folder;
  - a `mappings/*.json`;
  - `db.json` or `routes.json`;
  - a `.postman_collection.json`;
  - a sign-on file (`sso`, `oidc`, `keycloak`, `okta`, `auth0`).

  A structured mock carries only these rules, and a file of no kind the path says never gets them.

- **The facts file is unchanged.** A mock is an `entry`, as a gateway's route is, and no fact kind or field is added. What makes an entry a mock is read from its file, its module's mock framework or its mock profile line (`isMockEntry`, ADR 0133), not written on the fact.
- **The prompt budget.** Only a batch with a mock or a sign-on file pays for the rule. Tier 1 carries every rule as before, so `FACT_RULES`' hash is re-pinned, and the `/atticus-map` golden and the generated plugin and Copilot agent files are regenerated.
