# 0067. A shared parse cache: each file parsed once per repo scan

- Status: accepted (pending review by the product owner)
- Date: 2026-10-20

## Context

Every built-in extractor, every dialect and every dialect rule read and parsed its files on its own. On the synthetic estate of the M1 exit test (300 repos) each Java file was parsed 4.3 times on average (up to 6) by tree-sitter, each Terraform file 14.6 times (up to 19) by the HCL reader, each manifest-style YAML file 3 times, and each file was read from disk 9.1 times (up to 25). A dialect parsed a Java file again for each of its rules, and loadTerraform ran again for each extractor and dialect that reads Terraform. On a bank estate that work is repeated in every scan of every repo.

## Decision

**One parse cache per repo scan, shared by every reader.** `@maycombhq/sdk` gains `createParseCache()`, `withParseCache(repo, cache)` and `deepFreeze()`. The scanner makes a cache for each repo, wraps the repo's handle with it, and frees it when the repo is done, however the scan ends; `scanRepo` and `runExtractor` do the same when the handle they get has none, so the CLI, the SDK's own runner and plugin tests share parses too. A cache holds:

- **file texts**: `readText` on the wrapped handle reads each file once;
- **plain values**: what a reader makes of a file (a JavaFile, a SourceFile, flattened configuration, YAML documents and their plain values, an HCL file, an XML tree, Groovy calls);
- **native values**: tree-sitter trees, which live in the WebAssembly heap.

An entry's key is the reader's kind (`java:java`, `tree:kotlin`, `yaml`, `yaml-docs`, `hcl`, ...), the path and the content (its length and SHA-1, and the text compared on a hit), so a changed file, or another string read under the same path (a rendered Helm template), is parsed again. A failed parse isn't kept: the next reader parses again and gets the same error.

**Values are frozen.** Every plain value is deep-frozen before any reader sees it (objects, arrays, class instances' own properties; Maps and Sets have `set`, `delete`, `clear` and `add` replaced by functions that throw). A reader that changes what it was given fails at once instead of changing what the next reader reads. Typed arrays can't be frozen and are left as they are. YAML documents are frozen from their contents down (the documents' schema objects belong to the yaml library and are left alone). The one built-in reader that changed its parse, the Spring extractor adding the built-in annotations a house annotation stands for (ADR 0054), now copies the JavaFile first (`structuredClone`) when a framework model applies.

**Memory is bounded.** Each entry counts the length of the text it was parsed from. Plain values: 8M characters and 20,000 entries; native values: 1M characters and 2,000 entries; texts: 16M characters. Each bound drops least recently used entries first. Measured on generated Java, TypeScript, YAML and HCL files, a plain value holds 10 (a JavaFile, an HCL file, flattened YAML) to 37 (YAML documents, a SourceFile) bytes of JavaScript heap per source character, and a syntax tree up to 36 bytes of WebAssembly heap, so a repo scan's cache stays under about 300 MB of heap and 36 MB of WebAssembly memory at worst, which suits a 7 GB laptop. A tree leaving the cache is freed (`tree.delete()`), never while a reader is using it: readers get a tree through `useSyntaxTree` / `withTree` / `querySyntax`, which hold it until their callback returns. When the scan of a repo ends the cache frees every tree and drops every value. The bounds are `createParseCache` options; a value bigger than its whole bound is used and not kept.

**Readers.** Each reader of `packages/extractors/src/lang/` and `platform/` takes an optional place to share from: `parseJava(text, path, cache)`, `parseJavaTree`, `parseJavaClasses`, `parseJavaMembers`, `querySyntax`, `withTree`, `useSyntaxTree`, `SourceFile.parse`, `readSourceFile`, `groovyCalls`, `parseXml`, `parseHcl`, `readYamlDocs`, `parseYamlStream`, `flattenYaml`, `flattenYamlDocuments`, `flattenProperties`, `flattenConfig`, `renderCharts` and `buildKustomizations`. `at(repo, path)` makes one from a repo handle. Without a cache they parse alone, as before. A tree is shared by all its readers: the Java readers, syntax rules, the vocabulary readers and the framework survey read one tree per file. The YAML readers that allow duplicate keys share one parse; dialect `jsonPath` rules now read that parse too (duplicate keys only ever changed the error list, which they never read).

**Contract C4, additively.** `RepoHandle` gains an optional `parseCache`. Handles without it keep working and their readers parse alone; extractors and plugins that ignore it see no change. No record, rule or schema changes, so there is no schema version bump or migration. Output is byte-for-byte the same: the golden files, `packages/harbor-tests` (`expected/scan.yaml`), the scanner tests and the M1 exit counts are unchanged.

**Grammars run as baseline WebAssembly code.** Looking for the native memory behind the test-worker crashes (exit 0x80000003 under parallel load) found no leak: 1,000 runs of each tree reader leave the WebAssembly heap where it started, and no tree is left alive. The cause was V8 tiering the grammars up to optimised code. Tree-sitter grammars are generated C with very large functions, and compiling one with V8's optimising compiler took up to 2.2 GB of transient memory (peak RSS while parsing TSX; TypeScript 1.3 GB, Kotlin 0.5 GB), against about 0.1 GB otherwise; where the machine didn't have it, the process died with "Fatal process out of memory: Zone", which a Vitest worker reports as exit 0x80000003. It happened in 5 of 8 runs of a plain parsing loop with 2.6 GB of memory free. `lang/syntax.ts` now sets `--no-wasm-tier-up` and `--no-wasm-dynamic-tiering` before the runtime compiles anything (Atticus runs no other WebAssembly): peak RSS parsing TSX is 93 MB, and the `frameworks-cli` test worker peaks at 184 MB instead of 2.6 GB. Baseline code parses a file up to about twice as slowly, which the cache more than makes up for.

**Leaks are visible.** `liveTrees()` counts the trees parsed and not yet freed in the process; tests check that a scan, a failed extractor and a disposed cache leave none. A second `delete()` of a tree is a no-op.

## Consequences

- On the M1 exit estate every file is parsed once (2.9 parses per file before) and read from disk once (9.1 reads before) per repo scan. Timed back to back on a loaded 7 GB machine, the first scan of the 300 repos took 32 to 41 s against 59 to 90 s before, and the whole test 90 to 113 s against 118 to 170 s; the incremental scan (one repo changed, about 25 s) is spent outside parsing and didn't change.
- A reader that wants to change a parsed value must copy it; a test that mutates one now fails with a TypeError.
- Peak WebAssembly memory can be higher than with one tree at a time, since up to the native bound of trees are alive at once, and the WebAssembly heap never shrinks once grown: at most about 36 MB more per process.
- Still parsed on their own, outside the cache: YAML read by `parseDocument` with its own options (OpenAPI, Spec Kit, and `parseYamlDoc` in AsyncAPI, observability and Spec Kit), a SAM template with its intrinsics stripped, rendered Helm output and Kustomize inline patches; `package.json` through `JSON.parse`; SQL migrations and Liquibase changelogs; Prisma schemas and mainframe sources (read by their own line readers); class files and JARs; and the readers outside a scan (the onboarding survey, `atticus frameworks learn` from npm packages, the dialect and onboarding tree outlines). Within a scan their file texts still come from the cache.
