# 0006. Depend only on OpenSpec's stable core

- Status: accepted
- Date: 2026-10-18

## Decision

Atticus uses OpenSpec's stable core (specs, changes, schemas, instructions, status, validate, archive) through one adapter with contract tests and a pinned version range. It does not depend on OpenSpec's beta stores or worksets; the multi-repo layer (change workspaces, worktrees, cross-repo tracking) is Atticus's own. Existing stores are read if present.

## Addendum (2026-10-25, later): OpenSpec is the foundation; Atticus 2 is a layer on top

**The principle (the product owner's).** OpenSpec is the foundation and Atticus is a layer on top of it. Changes, artifacts, schemas, instructions, status, validation, specs, archive and stores are OpenSpec's, and Atticus calls OpenSpec's commands for them. Atticus adds accuracy on top: facts read from code with citations, verification, the catalog and its joins, knowledge, the critic and human gates. Atticus doesn't re-implement anything OpenSpec already does; where it still does, the gap is listed below with its reason.

An independent review found the opposite on a real change: `openspec status` showed 3 of 9 artifacts (the schema still listed Atticus 1's proposal, specs, interfaces, mappings, data and snow), `openspec validate` failed with "Change must have at least one delta", and `openspec archive` left `openspec/specs/` empty, so no archived change left a behavioural spec behind. `atticus change archive` didn't call OpenSpec at all.

- **org-flow v2** (`packages/openspec-adapter/src/org-flow.ts`, `ORG_FLOW_VERSION = 2`). The artifacts are the files Atticus 2's stages write, in its stage order, so OpenSpec and Atticus agree about what is done:

  | Artifact | File                       | Requires | Written by                                                                 |
  | -------- | -------------------------- | -------- | -------------------------------------------------------------------------- |
  | proposal | proposal.md                | none     | the feature stage, from brief.md and feature.yaml                          |
  | design   | design.md                  | proposal | the architecture stage, from target-flows/ (now with Rollout and rollback) |
  | stories  | stories.md (and stories/)  | design   | the stories stage                                                          |
  | specs    | specs/<capability>/spec.md | stories  | the stories stage, from the stories' criteria, no model call               |
  | tasks    | tasks.md                   | stories  | the stories stage, numbered per story                                      |

  The specs come after the stories because they are generated from them. `ARTIFACT_STAGE` maps each artifact to its stage. Each instruction says how Atticus makes the file and what it must hold. interfaces, mappings, data and snow are gone (their templates are removed). brief.md, feature.yaml, feature.md, target-flows/, stories/, tasks/, knowledge.yaml, needs.*, stage/ and review/ stay beside them, ignored by OpenSpec. A schema version bump: `atticus upgrade` runs `org-flow-v2` (writes the schema) and `stories-b-short` (re-writes each change's stories from its kept answer, no model call, which also writes its specs and proposal).

- **What is generated.** `proposal.md` (Why from the brief's problem, What Changes from the placement, Capabilities from the spec deltas once the stories exist, Impact, Open questions from the gaps); one spec delta per flow (`packages/planner/src/stages/openspec-files.ts`): a capability named stably (the one openspec/specs has for the flow, found by the flow its Purpose names, else the flow's name, repo-prefixed in a multi-repo estate), a requirement per story with SHALL wording and a `Flow:` trailer, a scenario per criterion (GIVEN/WHEN/THEN, named by its outcome). MODIFIED when openspec/specs has the capability's requirement for the flow, carrying every archived scenario (OpenSpec refuses a MODIFIED that drops one; a scenario with the same outcome is replaced in place); REMOVED for a removed flow; ADDED otherwise. A person's own proposal or spec file (no generated mark) is never overwritten.
- **Validate is a gate.** `openspec validate <change> --strict` runs on every stories draft, in a temporary copy of openspec/ with the draft's files (a failing draft never touches the change); each error or warning is a blocking finding (`openspec.validate`). It runs again before the plan hand-off and before archive (`requireValid` in `packages/changes/src/handoff.ts`).
- **Archive grows the specs.** `atticus change archive` now calls `openspec archive` after validating, so `openspec/specs/` holds each archived flow's behaviour. Tested on a fixture metarepo with the pinned OpenSpec: the first change ADDs the capability; a second change on the same flow MODIFIES its requirement, keeping the archived scenarios.

### Gaps: where Atticus still does what OpenSpec has a command for

- `atticus change show` and `change status` read change.yaml, not `openspec show --json` (the change-model work owns change.yaml; its deltas will join `status` there). The app's change list and spec pages read the local API (C4), which doesn't carry OpenSpec's task counts or openspec/specs yet; that needs a C4 bump.
- The OpenSpec root comes from the metarepo layout, not `openspec context --json` (beta, and its JSON is the agent brief, not a root).
- `atticus init` keeps `--tools none`: the `/atticus-*` steps replace `/opsx:propose`, `/opsx:continue` and `/opsx:apply` in a metarepo.
- Worksets: not written. `atticus workspace` already writes the change's editor workspace; `openspec workset create` from a change's repos is cheap but personal and local, so it waits for a switch.
- The Spec Kit hand-down is unchanged (one feature per task).

### Compatibility: OpenSpec's beta and experimental features

`openspecFeatures()` (`packages/openspec-adapter/src/features.ts`) finds once per CLI script what the installed OpenSpec offers, from its own `--help` (commands, subcommands, `--json`), never from its version. In 1.14.0 the beta and experimental ones are `store` (setup, register, list, doctor), `workset`, `context`, `doctor`, `schema` and `schemas`.

| Feature                                                  | How Atticus uses it                                                                    | Fallback                                                    |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| store reads                                              | `openspec list` / `show` run in the store's folder (`readStoreVia`, `via: "openspec"`) | `readStore`'s file reading (`via: "files"`), said in a note |
| store.yaml                                               | read from the file (OpenSpec has no command that prints it), tolerantly (ADR 0126)     | the same                                                    |
| `schemas`                                                | the contract tests read the schema back                                                | none needed                                                 |
| `context`, `doctor`, `store doctor`, `workset`, `schema` | detected and reported, not used yet                                                    | Atticus's layout and its own checks                         |

The result schemas are loose (`z.looseObject`): a field OpenSpec adds is kept, never an error; a field Atticus relies on that disappears fails the contract tests. `atticus doctor` reports the version, the features present and which path Atticus takes for each. A weekly CI job (`.github/workflows/openspec-compat.yml`, not part of the tests, which stay offline and pinned) installs `@fission-ai/openspec@latest` and the newest beta apart and runs the adapter's suite against each (`ATTICUS_OPENSPEC_BIN`), so a breaking OpenSpec release fails a job instead of an install.

## Addendum (2026-10-25): stores, read and written as a beta format

"Existing stores are read if present" is now built, behind switches that are off by default (ADR 0126). Atticus still depends on no beta feature. It can make the metarepo an OpenSpec store (`atticus init` or `atticus upgrade` with `--openspec-store` writes `.openspec-store/store.yaml`). It can add the metarepo to a code repo's `references:` at hand-down (`org-pack/openspec.yaml` `referenceInRepos`). It reads the stores `org-pack/openspec.yaml` names, read-only and labelled, in `atticus change list`, `atticus openspec check` and `atticus feature spec`. The store format is beta: its shape is kept in `packages/openspec-adapter/src/stores.ts`, read tolerantly, and checked against the pinned OpenSpec by contract tests. `atticus doctor` says when the installed OpenSpec has no stores. Registering, cloning, pulling or pushing a store, `store:`-only repos and worksets stay out.

## Addendum (2026-10-26): the first run has no dead end

A trial on a real repo, run as a developer would, hit three things in this ADR's area on a fresh metarepo. Each is decided here.

**`init` writes the assistant files.** `atticus init` ended by naming `/atticus-map <repo>`, a slash command no fresh metarepo had: the files that carry it are written by `atticus assistant-files`, which `atticus help` doesn't show (it is one of the commands under `atticus legacy`, ADR 0124 addendum D-cli). The choice was between naming that command in the message and promoting it out of `legacy`, or writing the files in `init`. `init` writes them: the guidance is then true rather than merely accurate, the twelve stay twelve, and a person meets a working metarepo instead of a step. `init` says how many it wrote and that `atticus assistant-files` writes them again when the org pack changes; a metarepo whose org pack can't be read still gets a message naming that command, because `atticus map <repo>` works without the slash commands. `init`'s result carries `assistantFiles`.

**`data.md` is the architecture stage's artifact, so the rule reads the stage.** `constitution.data-doc-present` demanded `data.md` of any change that touches a data store. Org-flow v2 ships five templates and `data.md` is not among them, because nobody writes one: the architecture stage writes `data.md` itself from the target flows, and only when a step changes the schema (a new table, a migration, a column with a type). A change that reads or writes columns the catalog already has was blocked on a document no stage and no template produces. The templates stay as they are and the rule reads the stage's own artifact: on the stage path (a footprint read from `target-flows/`, ADR 0124 addendum B-change) it asks for `data.md` only when the footprint carries a `schema` signal — exactly the condition under which the stage writes one — and when it does ask, its fix names the stage that writes it rather than telling a person to write the document by hand. Nothing is weakened: a schema change still blocks, and a change off the stage path (a person's own `data.md`) is asked as before. The alternative, shipping a `data.md` template from `init`, was rejected: it would put a file in front of people that Atticus overwrites.

**`atticus openspec <args...>` runs the bundled OpenSpec.** Atticus's messages named OpenSpec commands (`openspec instructions apply`) a person cannot run: `openspec` is not on PATH, it is vendored inside the installed package (ADR 0124 addendum D-npm2). Rather than teach people the vendored path, the CLI gains a thin pass-through: everything after `atticus openspec` that isn't `setup` or `check` is handed to the bundled script, run in the metarepo, with its own output and exit code. Atticus parses nothing. One thing it fills in: `status`, `instructions` and `show` take `--change`, and OpenSpec errors without it though a metarepo normally has one change open — when exactly one is open the wrapper adds `--change <id>` and says so, and when several are it names them. Every message that named a bare `openspec` command now names `atticus openspec <the same words>`.
