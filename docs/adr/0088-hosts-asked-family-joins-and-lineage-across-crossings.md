# 0088. Hosts asked, wrong families block joins, and lineage across a crossing (C6, C4)

- Status: accepted (pending review by the product owner)
- Date: 2026-10-21
- Builds on: ADR 0053 (hosts in the manifest), 0076 (client base URLs), 0078 (questions as files), 0079 (the Flow record and repo specs), 0085 (the estate pass)

## Context

Running the estate pass on the bench's petclinic estate (the Angular UI and the REST API scanned together) showed three gaps.

1. **Hosts were hand-written.** The UI calls `http://localhost:9966/petclinic/api/...`. Nothing joined until a person wrote `hosts: [localhost]` under the API's repo in the manifest. The scan knew the calls went nowhere, and the API's `application.properties` says `server.port=9966`, but nobody was asked. The manifest's host pattern also takes no port, so two services on one host (a UI on 4200, an API on 9966, another on 8080, all `localhost`) can't be told apart.
2. **A wrong family joined a call to the wrong flow.** The UI's "find owners" call (`GET /owners`) joined the API's `add-owner` flow, because that flow's family listed `GET /owners`. Families by resource allowed it: `POST /owners` and `GET /owners` are on one resource. `add-owner`'s steps validate and insert, so the joined flow said a search writes to the owners table.
3. **Lineage stopped at the crossing.** The UI sends one `owner` object; the API's entry takes `firstName`, `lastName` and the rest. `atticus estate lineage spring-petclinic-angular.add-owner firstName` found no step that sends `firstName`.

## Decision

### 1. Hosts asked, not hand-written

- **A host can name a port** (C6, `ManifestRepo.hosts` and `modules[].hosts`). `localhost:9966` takes only calls on port 9966. `localhost` (no port) takes calls on any port, as before. When both kinds match a call, the one with the port wins. A URL with no port has its scheme's port (http 80, https 443). We considered matching by port in a separate field. We chose the port inside the host because the port is part of where a call goes, as a person writes it, and the same string goes in the question, the answer and the manifest. Every existing manifest still reads the same way.
- **The scan asks** (`atticus scan`, and `atticus estate join`). Each loose HTTP call (an `Unresolved` http-call whose URL has a host, from a client base or a literal URL) whose host matches no repo's or module's `hosts` is grouped by host, with the port when the URL names one. Each host becomes one question file (ADR 0078), step `scan-hosts`: "Which repo answers on localhost:9966?". The options are the repos that serve HTTP (a component of theirs has a rest, graphql, soap, websocket, sse or webhook Endpoint), then "None of these". The evidence is up to three of the calls' lines, in the repo of the first call. When exactly one serving repo has a config line that sets the call's port (`server.port=9966`, `port: 9966`, `PORT=9966`, `EXPOSE 9966`, `--port 9966`, a compose mapping `"9966:8080"`), that repo is the first option, and its option names the file, line and text. Only these config files are read: `application*`, `bootstrap*` (properties and YAML), `.env*`, `Dockerfile`, compose files and `package.json`. A host asked before, answered or not, isn't asked again. The rerun is `atticus scan`.
- **Answering writes the manifest.** `atticus questions answer <id> --option <n>` (and `POST /api/questions/{id}/answer`, which calls the same core function) puts the host under the chosen repo's `hosts` in the `repos.manifest.yaml` that lists it. Comments and order are kept. A manifest that would no longer be valid is refused, and the question stays open. "None of these" writes nothing. The CLI says which file it wrote. The manifest goes through a pull request with the question file.

### 2. A family that spec check finds wrong blocks a join

- **The family rule gains one case** (`atticus spec check`, `family-mismatch`). A family member that does other work than the trigger is a mismatch: a read (GET, HEAD, OPTIONS) standing for a write (POST, PUT, PATCH, DELETE), or a write standing for a read. A flow's steps describe one of them only. The drafter's prompt now says: reads with reads, writes with writes. The rule stays advisory for `atticus spec draft`, so the flow is kept and the finding is handed back.
- **The estate pass applies it** (`familyMismatches`, shared by spec check and `atticus estate join`). The callee flow is the one whose own trigger is the entry point the call reaches. Only when there is none does a family stand for it, and only through a member spec check doesn't find wrong (with the template the spec header names). When every flow that stands for it does so through a wrong member, the call-out isn't joined. Its reason is `family-mismatch` (new in `EstateUnmatched.reason`), and the message says which flow, the finding, and `atticus spec draft <repo>`. The finding is worked out when the join runs, so it is always the current one, not the last `findings.yaml`.

### 3. Lineage across a crossing, and writes that name their columns

- **Objects at a crossing.** `Crossing.objects` lists each sent name the callee's entry takes as fields: `{ sent: owner, fields: [firstName, lastName, ...] }`. A sent name is mapped when the callee names fields on it (`owner.firstName`). It is also mapped when it is the only sent name the entry doesn't take, and the entry takes fields the caller doesn't send. A mapped name isn't counted in `unused`. The second rule also maps one plain field taken under another name (the UI sends `id`, the API takes `customerId`); lineage follows it the same way. `atticus estate flow` prints "owner carries the callee's firstName, lastName".
- **Lineage starts at the object.** `atticus estate lineage <flow> firstName` starts at a step that sends the field, or at a call-out whose crossing maps a sent object to it. The first link reads `sent owner.firstName`.
- **A write maps its fields to its columns.** In a write step, `data.from[i]` → `data.to[i]` maps a field to a column. Lineage uses that mapping first, then a column of the same name (letter case, `_` and `-` aside). Spec check gains `write-unmapped` (advisory in the drafter): a write sends a field that no column takes, by mapping or by name; or a mapping names a column the write doesn't list. A write with no columns is still `write-store`. The drafter's prompt asks for every column in `store.columns`, the written fields in `data.sends`, and a mapping where names differ, as the code shows it: an `@Column(name = ...)` or mapping file, the ORM's naming rule (only when the repo uses it), or an explicit INSERT or UPDATE.

## Consequences

- C6: `hosts` takes an optional `:port` (1 to 65535). Every existing manifest still reads, so the workspace schema version stays 1 and there is no migration. A manifest that uses a port is refused by an older Atticus. That is acceptable because the org pack and Atticus are upgraded together (as in ADR 0076).
- C6 (`specs/estate.yaml`, schema version 1): `unmatched[].reason` gains `family-mismatch`. The same holds: older files read, and a newer file is refused by an older Atticus.
- C4: the OpenAPI document changes only where it echoes the manifest's host pattern, so `docs/api/openapi.json` is regenerated. No call changes, and the API version stays 2.2.0. The answer call writes the manifest for a hosts question but doesn't report it in its response yet. The command line does.
- Spec check reports more findings on existing specs. On petclinic's REST spec: 13 new `family-mismatch` findings (the add and update flows stood for their resource's GETs) and 13 `write-unmapped` findings (date for visit_date, petId for id). The next `atticus spec draft` is handed them back.
- Measured read-only on the bench's petclinic estate (specs and catalog as they are): find-owners no longer joins add-owner (unmatched, `family-mismatch`); `firstName` from the UI's add-owner reaches `spring-petclinic-rest-db.owners.first_name` in three cited links; with the hand-written `localhost` removed, the one question asked is "Which repo answers on localhost:9966?", with spring-petclinic-rest first, citing its `application.properties:24` (`server.port=9966`).
- Not built: asking about calls through a gateway host that no gateway repo lists (still a scan note, ADR 0053); reading a port from code (`app.listen(9966)`) or from a Kubernetes or Helm file; a question per port when one repo serves on several; a hosts question scoped wider than one repo; choosing among several sent objects with no qualified names; and the API response saying the manifest was written.
- Tests use invented fixtures (`fixtures/estate/owners/`) and the mock runtime. No test calls a model or the network.
