# 0170. The waiting loop agrees with verify, and never waits forever

- Status: accepted (pending review by the product owner)
- Date: 2026-11-03
- Builds on: ADR 0124 (facts the assistant writes; addenda A-ledger, A-read), 0141 (what a read took), 0161 (the whole estate in one command), 0169 (reachable-first reading of model classes)

## Context

A person on Windows with Copilot in IntelliJ ran `atticus map --all --repos <repo> --max-tokens 90000`. For part 32 of 40 (a service folder, a validation folder, an SQL folder and a QA folder) they pasted `/atticus-map <repo>` into Copilot; Copilot read the repo its own way, wrote facts and ran `atticus verify <repo> --write` itself: "58 facts kept, 0 rejected; coverage 4% (0 files no fact cites yet)". The loop kept printing "Still waiting … part 32 (100 minutes)", and `r` printed the same verify line and gave part 32 again.

Two counts disagreed. Verify counts a file accounted for when a fact cites it, a reviewed line or glob names it, it is excluded, or the read plan records it as a model class nothing reaches (`notReached`, ADR 0169). The loop asked the read plan's own count (`readPlanProgress`), which looks only at the folders the facts and reviewed lines touch: a folder whose files are all `notReached` or excluded, which no fact or reviewed line touches, was never done, and nothing said why. The loop also printed a reminder every ten minutes for as long as the terminal stayed open.

## Decision

1. **A part is done when verify says nothing under it is left.** `atticus verify` passes its `coverage.unknown` (the source files no fact cites, no reviewed line names, neither excluded nor `notReached`) to `recordReadProgress`, which stamps a part of the read plan read (`parts[].read`, ADR 0141) once no file of `unknown` is under any of its units (a line range still needs a fact citing a line of it, as verify counts files, not lines). `readPlanProgress` counts a stamped part done. So `map --all`, `atticus next`, `--estimate` and the read plan say the same as verify, from one computation (`partUnaccounted` in `cli/src/map-parts.ts`). A stamp is never taken back.
2. **The loop verifies when the reader did.** Whenever the reader's verify passed after its last write (it may have run `verify --write` itself), the loop runs what `atticus verify <repo> --write` runs and asks the same coverage. Nothing left: the part is done and the loop moves on without a keypress. Something left: it prints exactly what (`Still not covered in <repo> part 4 of 4: <glob> (3 files: a, b, c)`) and that `r` gives a new chat only what is left of the part (`/atticus-map <repo> --part n --gaps`: those files, and any line verify lists as skipped under it). `r` itself verifies first and moves on when the part is done.
3. **Never waiting forever.** After `--idle` minutes (default 30) with nothing written, the loop says once that it stopped waiting, with the command that carries on (it verifies what was written and gives the line again for what is left), saves the state and ends the run. The "Copilot seems to have stopped" hint is gone; a run is always resumable.
4. **`map --all --force [--repos …]`** reads the named repos (or all) whole again in the same loop, at a fresh read plan at the limit. The facts on file stay, as already kept, as `atticus map <repo> --force` keeps them: the chat names one by its id and doesn't write it again. Since the facts already account for every part, each part is given by its number (`/atticus-map <repo> --part n`, which runs `atticus map <repo> --part n --estimate`: "This session reads part n of N"), is done once something was written for it (fact ids and cited lines, or reviewed lines, compared, since verify rewrites the facts file) and verify leaves nothing under it, and the parts done are kept in the state file (`force: true`) so a second run carries on. When the last part is done the read records the reading rules there are now (ADR 0167). `--force` doesn't go with `--stale` or `--gaps`.
5. **`atticus map <repo>` under Copilot runs the same loop.** A new read with no mode asked for, in a metarepo, where runtime.yaml (or `atticus probe`) names Copilot or a reader that reads by a pasted line, runs the waiting loop for that one repo instead of the batch hand-off (`mapReader` in `cli/src/map-all.ts`). When the batch hand-off is taken (another assistant is named, or `--copy`), it says plainly: "runtime.yaml says <assistant>; if you use Copilot, run atticus map --all --repos <repo> (it waits and copies each line)". Atticus doesn't guess the editor. The editors' `--handoff` steps are unchanged.
6. **`--models entries`** (beside ADR 0169's `reachable` and `all`): reachability from the repo's own entry points only (controllers, routes, handlers, listeners, and what its entry facts cite; a field a call owns is not followed). The model classes only an outbound client reaches are left out as `notReached`, listed under the new optional `notReached.clientOnly` with why ("reached only from an outbound client; --models reachable reads them"); the rest keep ADR 0169's reason. A repo with no entry point is reached from its calls, as `reachable` reads it. The read plan records `models: entries`. `reachable` stays the default.

## Consequences

- The read plan (schema 2) gains optional fields only: `models: entries` and `notReached.clientOnly`. A plan written before reads as it did. No contract (C1 to C6, the facts file) changes.
- A part whose folders hold only files verify doesn't hold the reader to (excluded, not reached) is done at the first verify after the plan; that is what verify's coverage says, and the estimate lists them as left out.
- The loop runs `verify --write` each time the reader's verify passes, not only when the part looked done: one more verify per reader verify on a big repo.
- A repo read in one session keeps its rule (done once facts are written and verify passed); the coverage rule is for parts.
