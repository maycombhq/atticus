# 0162. Answers that carry and suggestions that know the estate

- Status: accepted (pending review by the product owner)
- Date: 2026-11-01
- Builds on: ADR 0078 (questions), ADR 0124 (facts) and its addendum C-join, ADR 0140 (teams in roles.yaml), ADR 0143 (where a repo is reached), ADR 0153 (answers by rule, Q2), O1 and O2 (outside systems)

## Context

A call with no target and no host is asked about (`facts-targets`). Its options were the components of the read repos that serve that kind of call, then every outside system, then "None of these". On an estate read a few repos at a time that is the wrong list: the repo the call goes to is usually not read yet, so it is never offered, and the person types its name. Nothing said why an option was offered. An answer naming a repo not read yet was never checked once that repo was read. The same answer was given repo after repo. The Copilot reader was not told the rules that cover the repo, so it asked again. And a topic or queue another team owns stayed a loose end forever: only a call's `to` naming an outside system kept it outside.

## Decision

1. **Suggestions that know the estate** (`packages/scanner/src/target-suggest.ts`, `targetSuggestions`). Every repo of the manifest, read or not, and every outside system is a candidate, scored by evidence: an entry of a read repo that serves the call (6), the join's own candidates for an ambiguous call (6), the call's path under a base path (the manifest's, a module's, a proxy's `BasePath` or a Route's, 5), a host an outside system's aliases name (8), the call's config key, client class or host label naming the repo's id, component, modules or its system's aliases (4 each), its path's words naming it (2), its description (2), the caller repo's other answers naming it (3). A word most candidates share (the estate's prefix) counts for none. The question offers the top five with evidence, filled as before with the read repos that serve the call's type and the outside systems; each option says why, and whether the repo is read yet. A read repo keeps its component as the label (earlier answers hold); an unread one is named by its repo id, which the join resolves once it is read. Then **"Another repo…"** and "None of these" (and, for a group, "Not all to one place"). Question ids are unchanged: they rest on the words and the evidence, not the options.
2. **The picker.** "Another repo…" is never an answer (`TARGETS_ANOTHER_LABEL`, refused by `answerQuestion`). `atticus questions answer <id> --target <id>` takes any repo of the manifest (by id or component), any system of the profiles, or a team of `roles.yaml`; a team with a system answers with its system. A vendor not in the profile, or a team with no system, is offered; `--add-system vendor|internal` (and `--name`) writes it into `profile.yaml` (`addProfileSystem`, owner the team), a file change in the metarepo for review in the pull request, never a write to a shared system. The app's Questions page shows the same list under the option (GET `/api/questions/{id}/targets`; the answer takes `target`, `addSystem`, `name`; C4 2.45.0, additive). The Map's correction panel keeps its own list of known names.
3. **Answers that carry.** `catalogWithFacts` returns `answerMisses`: the calls a person's answer sends to a read repo where no route serves the call, on the caller's write and on the named repo's. `verify --write` reopens that call's own or group question: **question schema 4** adds `reopened` (when, why, and the answer it had), kept when it is answered again. A rule's answer (Q2) is not reopened by one call. Migration: versions 1 to 3 read as they are and come back as 4 in memory; `atticus upgrade` (`migrateQuestions`) rewrites them at 4, changing nothing else.
4. **The reader is told.** `map --estimate` (and `--json`'s `rules`) and the hand-off prompt's questions source list, beside the repo's own answered questions, the answers by rule from other repos' questions whose scope covers the repo (`rulesCovering`). Step 1 of `/atticus-map` says to follow each and never ask what one settles. `FACT_RULES` is unchanged; the steps' golden file and the generated Claude Code plugin and Copilot agents are.
5. **One answer for many.** `answerRuleOffers`: the calls on one host, or through one config key, answered with the same target in two or more repos offer the command that makes it a rule (`--match` the host, or the calls' shared path prefix, `--scope repo-type`, when the repos share a type) and the note it would be under `notes:` in `repo-types/<type>/type.yaml` (the `notes:` field another plan item adds in parallel). Only words and a command; nothing is written.
6. **Topics and queues of another team or a vendor.** In the merge's events step, a topic or queue with no counterpart in the estate (and no Interface the estate join made on it) whose name is among an outside system's aliases lands on that system: an Interface at `asserted` confidence, flagged `declared-topic`, citing the code's line and the profile (`source: manual, by: person`). A topic still loose is asked (`facts-topics`, "Who owns the topic …?", first option "A topic owned by another team or vendor", which opens the same picker); `--target` writes the topic under that system's aliases (or adds the system with it), for review. A repo of the estate is refused: its own facts say what it publishes and listens on. No schema change: aliases already exist.

## Consequences

- Contract changes: question schema 3 to 4 (C6, optional `reopened`, with the migration above) and the local API 2.44.0 to 2.45.0 (C4, additive). No C1 or facts change.
- The options of a question already on file stay as written; new questions get the new options.
- A write may now ask about loose topics it never asked about before (the map fixture's `forge.payments.settled` is one).
- The weights are code, not configuration; they rank and never decide: every answer is a person's.
