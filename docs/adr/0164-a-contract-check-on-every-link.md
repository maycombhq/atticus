# 0164. A contract check on every link

- Status: accepted (pending review by the product owner)
- Date: 2026-11-01
- Builds on: ADR 0124 (facts the assistant writes; addenda C-join, A-gateway, A-gateway2), 0125 (a Schema field says whether it is required), 0130 (a vendor's operations), 0142 (enums, headers, errors; another team's spec, O2), 0151 (contract files as evidence, J3), 0149 (the outside systems)

## Context

The join (ADR 0124 C-join) says which entry each call reaches, through which gateways, and lines up the fields that cross by name (`lineage`, `gaps`). It never asked whether the two sides agree on the payload: a gateway's published spec can promise a field the Spring Boot service behind it never returns; a listener can read a field the publisher never sends; two copies of a `.proto` can give one field number to two fields. Plan item F7 asks for that check on every link, and for wrapping (envelopes, gateway reshapes, mappers) to be read from the code, never assumed or configured per organisation.

## Decision

### 1. What is compared

`checkContracts` (core `contract-check.ts`) takes the estate join, every repo's facts, the specs on file and the outside systems' intaken specs, and compares, for every link:

| Link                                                                   | Boundaries                                                                                                                                         |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| A REST call joined to an entry                                         | caller → each gateway route's published spec (when its repo has one) → the service; a route with no spec is passed through                         |
| A gateway's forwarding call                                            | checked as a hop of the calls through it (once), and its own Interface named on each finding (`interfaces`)                                        |
| A publish joined to a listener                                         | publisher → listener; publisher → the spec its message type names; listener → the spec it reads by; that spec → the publisher's (protobuf numbers) |
| A listener whose publisher is outside                                  | the intaken spec → the listener                                                                                                                    |
| A call to an outside system matched to an operation (ADR 0130's match) | the call (or a forwarding call's route spec, translated) → the operation                                                                           |

Kinds: `field-missing` (read, never sent or returned), `field-extra` (sent, not taken; or returned and not published, when the sender is a published spec), `field-not-sent` (required, not sent), `field-required` (required on one side only), `field-type` (another type family), `field-number` (a protobuf number given to another name or type), `error-unlisted` (answered, not listed or handled), `error-unanswered` (a published spec lists it, the service never answers it; 401, 403, 429 and 502–504 are a gateway's own and skipped behind one). ADR 0125's rule holds everywhere: a side that lists nothing is unknown, not different. Names compare dotted segment by segment, case, `_`, `-` and `[]` aside; a path that differs only in its prefix matches its one field with the same last segment.

### 2. Wrapping, from the code

All of it is field facts already in the facts file (`mappedTo`, `transform`); nothing is a setting:

- **Envelope**: the wrapper's field (`data`) is a field fact of the side; each field inside it has `mappedTo` it and a `transform` saying envelope (`envelope Response<T>`). The wire name is `data.id`.
- **Mapper** (MapStruct, AutoMapper, a converter): a field `mappedTo` another field of the same owner and side, with a `transform` naming the mapper. Outbound (an entry's response, a call's request or message) the target travels; inbound the source does.
- **Gateway reshape** (AssignMessage, JavaScript, XSL): a field of the route `mappedTo` one of its forwarding call, or the other way, cited on the policy. These are mapping facts, not a payload: the forwarding call's face excludes them.
- **Untraced**: a field with a `transform` and no `mappedTo`. Any difference that touches it is `unconfirmed`, never a mismatch. So is a difference on its counterpart: a field read, sent or required that the other side lacks, where the other side has an untraced field on that payload that matched nothing across the boundary (the converter may have renamed it: `acctBal` written by `BalanceSerializer`, read as `balance`). The finding cites that untraced line, the first by name, preferring one of the same type family.
- **Message type**: a `message` field fact with `transform: message type`, its `name` the type as the code writes it and `type` its full name. It ties a publish or listener to its spec (the listener's repo first, then the publisher's, then the estate, then intake).

The reading rules (`FACT_RULES`) say this in three parts (backend, frontend, protocols; gateway). Repos read before need `atticus map --all --stale` (or a read of the files that hold DTOs, mappers and policies) before their links are compared; until then they are unknown, not different.

### 3. The specs on file

- **A repo's own** (`<repo>.specs.yaml`, a new facts companion, `FACTS_COMPANIONS`): `verify --write` reads the checkout at the facts' commit (`readRepoSpecs`, intake), by content, in any folder. The files are the commit's, through the clone's local git (`ls-tree` and `cat-file` of that commit, nothing fetched), so an edit nobody committed and a file nobody added are no spec; the facts' commit is the checkout's HEAD when the facts are of it (a write carries them there), else the one most facts are of (a tie to the newest); when that commit isn't in the clone the specs are read at HEAD and that is said and stamped; a checkout that isn't a git clone is read as its folder holds it. It reads: OpenAPI (through `readVendorSpec`), `.proto` (messages, nested, labels, numbers), Avro `.avsc`, JSON Schema, AsyncAPI (each message with its channel). An operation one of the repo's own REST entries serves is `own` (a gateway's published spec, tied to its route); another is a consumer's copy (J3), standing in for a call with no fields. The deny-list applies as for contract files.
- **Intake**: `.proto` and `.avsc` are classified (`protobuf`, `avro`), linked to the system their name or package names, and read into Schema records of that system. An outside system's newest spec is compared, and the one it replaced too: `newFindings` gives what the new spec brings.

### 4. Surfaces

`atticus join contracts [--json]` (and `estate contracts`); `GET /api/contracts` and the page Map › Mismatches (aside, with empty, loading and error states); a link whose calls have findings gets the gaps `contract-mismatch` or `contract-unconfirmed` on the canvas and its findings under each call in Why is this linked? (a finding is a link's by its Interface, or, naming none, by its line: a call to an outside system by the caller's line, a listener read against an outside publisher's spec by the listener's line on the link's callee side); the Trust tab counts them (`TrustView.contracts`); an outside system's page lists the calls against its newest spec, marking what the spec brought.

The check costs little per ask: `checkContracts` indexes each repo's facts once (by id, field facts by owner, flows by entry and by the call a step names, each entry's or call's payload worked out once), so 40 repos of 2,520 facts and 2,400 links check in a fraction of a second. `contractCheckOf` (CLI) keeps each metarepo's result, with a stamp of the path, size and modification time of every file under facts/, the inputs, the org pack, the questions and the curated catalog; `/api/contracts`, `/api/trust` and `/api/outside` share it, asks at once share one run, and any change to one of those files works it out again. A run that fails isn't kept.

## Contract notes

- **The facts file:** unchanged. Every reading above uses `side`, `name`, `type`, `required`, `mappedTo` and `transform`, which it already has.
- **C1:** schema version 4: a Schema's `format` gains `protobuf`. No other field changes; version-1, -2 and -3 files read as they are and come back as version 4. Migration: `migrateCatalog` rewrites a version-3 file with only the number changed; `atticus upgrade` has the step `catalog-schema-v4`.
- **C4:** local API 2.47.0, additive: `GET /api/contracts` (`ContractsView`), `TrustView.contracts`, `OutsideSystemView.contracts`.
- **New file schema:** `SpecsFile` (`<repo>.specs.yaml`, schema 1), a facts companion like ADR 0151's contracts file.

## Consequences

- A gateway's published spec is held to the Spring Boot payload behind it, through its envelope and its AssignMessage renames, on the bank-shaped fixture (`fixtures/link-estate/contracts/`, an overlay so P1, P3 and J1's pinned figures are unchanged).
- Topics are checked publisher against each listener and against their `.proto`, and a renumbered field is a finding.
- A mapping nobody traced never shows as a mismatch.

**Not done here:** Pact files' bodies aren't read as payloads (only their method and path, as J3 has them); enum values aren't compared on links (the prototype comparison does); `oneOf` bodies and proto `oneof` as alternatives are flattened; the check is computed on demand, not stored in the catalog.

## Addendum (2026-11-17): a field's place in its payload, built from the facts

**What went wrong.** On an estate read in the field, a link's panel counted dozens of mismatches and most were false: "reads the response field depot, which the spec never returns", for a spec that returns it at `receipt.stamps[].depot`; "the spec requires the request field payload, which the call doesn't send", for a call whose recorded request fields were the ones inside `payload`. A reader writes one field fact per field of each class a body is made of, cited on its declaration, by the name it has there. Nothing but the type of the field that holds a class says where the class sits, and the check compared the bare name as if it were the path. Section 1's fallback (a path that differs only in its prefix matches its one field with the same last segment) hid this until two nested fields shared a last segment (a `stamps[]` under the envelope and one under each item).

**The rule.** `placeFields` (core `field-places.ts`), used by `checkContracts` for every code-side payload, builds each field's path from the payload's root out of the facts on file. Nothing is read again and no model is asked:

- **A class** is the fields of one owner and side cited in one file. The verifier checked each on its line, so the file is the one part of membership that is not the reader's choice of words; an id is any slug (ADR 0124) and `mappedTo` is only there when a reader wrote it. Where one file holds several classes, the fields whose id carries a type's name (`field.case-owner.team` for `CaseOwner`) are that type's.
- **A parent** of a class is a field of the same owner and side whose declared type names it: the fact's `type`, and where a fact has none, the type its cited line declares for it (`declaredTypeOf`, from `cite.quote`: `List<X> x`, `X[] x`, `x: X[]`, `val x: List<X>?`, `x: list[X]`, `X []Y`, and `@JsonProperty("x") private List<X> y;`, where the wire name is only in the annotation). A type only counts when it names a class of that same payload. A list gives `[]`. A wrapper that only passes its value on (`Optional<X>`, `Mono<X>`, `ResponseEntity<X>`) is no level. A class named inside any other generic type is placed through that type's own fields when they are on record (`Envelope<Order>` with `T content` gives `content.…`), and has no place anyone can name when they aren't (`Page<Item>` with no `Page` on record). A generic class named with two arguments (`Result<Customer> customer`, `Result<Account> account`) places each argument class under its own holder only. A generic class with two type variables, or named with two argument classes (`Pair<Customer, Account>`), places nothing through its fields: which variable is which isn't on record, so the argument classes have no place anyone can name.
- **A path** is the parent's path, then the field's name, through as many as ten levels. A class reached from two fields is at both places, up to 64 (a bound by cost: a class in more places is rare, and each place is compared); beyond either limit the field says so and is never silently dropped. One fact that differs the same way at several of its places is one finding, at the first place by name, its words listing the others (`…; the same at 4 more places: …`), so a shared `Money` with one wrong field counts once. A class that holds itself is followed once more and no further, and a field that exists only on such a second turn is compared where it matches and never reported alone.
- **Roots.** Every class no field points at that holds another class is a root, its fields top-level: a body and an error body, a base class that holds the envelope and the class that extends it.
- **An envelope mapping** (section 2) places one field under another, as before, and its line is still in `via`; so are the lines of the fields a path was built through. Where a field mapped to the envelope belongs to a class that a field under that envelope holds by type (the field-types rule maps every field inside a wrapper to it, nested classes too), the type's path is the place: `data.customer.name`.
- **A dotted name** is the reader's own path. Where it starts with the end of its class's place it is not prefixed again (`receipt.depot_token` under `receipt` stays `receipt.depot_token`). It places itself only: its bare siblings keep their names.

**Matching** (section 1, restated; `findOf`). The same path, always. Beyond that it depends on whether the places are sure. A spec's path is. A code field's is when its path is built from a root class on record (a class that holds others and that nothing holds) and that root is borne out by the other side: one of its fields sits at the same path there. A class that holds others may still sit under a field nobody recorded, so until one of its paths matches it is taken for a fragment.

- _Where either place is not sure_ (a fragment; a flat class nothing says is the root): the fields with the same last segment of which one path is the end of the other; one of several is told from the rest when no field of the same side sits at its very path, or by the longest shared end. Failing that, a field whose own place isn't sure takes the one field of that last segment anywhere, unless its own side already has a field there.
- _Where both are sure_: only a field at the same depth whose path differs in one segment that isn't the last, when there is exactly one (a parent recorded under its Java name, `stampLines` for `stamps`, doesn't make a difference of each child).

A field that matched nothing whose name is on the other side only somewhere else (at a path its own side doesn't already have a field at) is unconfirmed and says where (`a field of that name is only at receipt.stamps[].depot`), a root field no less than a nested one: a part renamed twice over looks the same, and one chance match can bear out as the root a class that really sits under a field nobody recorded. For a required field nothing sends, a field of the sender whose path is the end of the required one counts as such a name too. A field whose name the other side has nowhere is a mismatch.

A type or `required` that differs on a pair matched under another parent name is unconfirmed (`matched under another parent name (stamps[].depot)`): the pair holds, the difference on it is not certain. The parent recorded under the other name is itself a mismatch.

**Where the place isn't sure.** A difference is `unconfirmed`, with the reason in its message and no `untraced` line, in these cases and no others:

- _A place that decides._ The class is held in a map (its keys are data); inside a generic type whose shape isn't on record; an envelope mapping and a type name parents that don't agree; a dotted name doesn't start where its class sits; the field is deeper than is compared, or held in too many ways to follow. Any difference on such a field is unconfirmed.
- _A place not on record_ (a class nothing points at beside classes that hold others; classes that only hold each other; a class at more places than are compared) is a doubt only where the difference depends on it. It is ignored, and the difference is a mismatch, when the other side has that name nowhere (missing is missing wherever the class sits) and when a type or `required` is compared with the only field of that name on the other side.
- _A shared name._ A field that matched nothing shares its last segment with several fields of the other side and nothing on record says which (`2 fields of … are named status, and nothing on record says which this one is`).
- _A name only elsewhere_, and _a pair matched under another parent name_, as under Matching.
- _Nothing listed inside._ The other side names the part the field is in and lists nothing inside it: an object with no properties, a spec read no deeper (intake stops at its own depth), or a list (`what the items of tags are isn't recorded for …`: the spec's reader keeps no item type, so a list of strings can't be told from a list of objects nobody listed). Unknown, not different. A part of a scalar type is no such part: a field inside it is a mismatch.
- _A request recorded without its envelope._ A required field isn't sent, and every sent field that matched sits deeper on the other side under one same prefix, with at least two such matches or no sent field left unmatched (`…'s request fields on record don't start at the payload's root`). Only for a required field outside that prefix: one inside it is missing wherever the root is, a mismatch. Or the sender names the part that holds the field, as an object or a list, and has no fields on record inside it.

Two things are no difference: a required part of which the sender sends a field it places inside that part (or any field inside it, when the sender's root is unknown as above); and a field required inside a part that may be left out, of which nothing is sent.

A payload whose fields are cited in several files none of which holds another (a flat DTO, a mapper's line, fields cited where the calling code names them) is compared as before: `fixtures/link-estate/contracts` gives the findings it gave.

**What stays found.** A field the code reads that the spec has nowhere is a mismatch at its full path; so is a type of another family at a nested path. `fixtures/contract-paths/` (the invented forge-desk against Forge Parcels' Shipments spec, taken in through intake) pins both, with the false lines gone; `contract-paths-review.test.ts` pins the cases where a doubt must not hide a difference.

**Reading rules.** What the reader is told beside the model classes it is given (`MODELS_RULE`, ADR 0169, in the estimate, the batch, gaps and top-up prompts) and step 6 of /atticus-map now say it: a field is cited under its own name, never a dotted path, and a field that holds another class is a field fact too, with `type` as declared. It is not a part of `FACT_RULES`: an 8000-token batch of back-end code has 305 tokens left for its files beside its rules, five above the least a prompt is worth (`MIN_ROOM`, 300), so a part more would turn the smallest supported model away. `MODELS_RULE` itself is no longer than it was (444 characters): a batch's room doesn't count it, so more words would come out of what a prompt keeps for the facts on file. So the rules' hash and sets are as they were, no repo becomes `rules-changed` (ADR 0167), and no top-up is planned; which repos have a class the check can't place is said per repo by verify, below. None of this is needed for the above to take effect: the check is computed from the facts on file, so an Apply is enough.

**verify.** `atticus verify` notes (`fieldsUnplaced` in its report and `verify.yaml`, a note and never a rejection, so an older read still verifies) each class of a request, response or message whose place isn't on record, with its fields and why, over the fields the check compares (a mapper's end that doesn't travel and a gateway policy's mapping are left out).

**Contract notes.** The facts file is unchanged: `owner`, `side`, `name`, `type`, `mappedTo`, `transform` and `cite` are read as they are. C4 is unchanged: a finding's fields are the same, and an unconfirmed one may now have no `untraced`, which was already optional. `VerifyReport.fieldsUnplaced` and the same key of `verify.yaml` are optional additions to the verifier's own report. `newFindings` keys on the full field path, and for a finding that stands for several places of one fact, on each of them: the places are kept beside the findings of the process's own two checks (the newest spec and the one before are checked in one run and never read back), and a finding from anywhere else vouches for its own field only, so a place it may have listed counts as new rather than be missed.

**Not done here.** A map's value class is never placed (`additionalProperties` isn't read from a spec either). Inheritance isn't followed as such: a base class's fields are cited in the base's file and are a class of their own, a root beside the class that extends it when it holds another class (which gives the right paths), and a class nothing reaches when it holds none (its fields then differ only as far as the place doesn't matter). Two classes of one name in different folders of a payload are tied to neither. A type variable is recognised as one capital letter and an optional digit (`T`, `T1`): a generic class whose fields are declared `TItem` or `TData` places nothing through them, and its argument class is unconfirmed. `additionalProperties: false` isn't read, so a spec that forbids extra fields and one that says nothing are alike. Intake keeps no item type for a list: recording one would add a field to the spec file's shape (`SpecField`, `<repo>.specs.yaml`), which needs an ADR of its own, so a field read inside a list of scalars is unconfirmed, not the type mismatch it is.
