# 0192. A library of the estate's own is what its services depend on: build coordinates as facts

- Status: accepted (pending review by the product owner)
- Date: 2026-11-10
- Builds on: ADR 0068 (`Component.uses`, a module's build dependencies inside one repo), ADR 0124 (facts the assistant writes, the verifier checks), ADR 0135 (why is this linked, this link is wrong), ADR 0167 (rule sets a read is topped up with), ADR 0174 (corrections from the canvas)
- Contracts: the facts file (ADR 0124) gains the `artifact` and `dependency` kinds at version 5, additive: older files read unchanged. C4 (local API 3.10.0, unreleased, so no bump) adds the graph edge type `depends-on`, the join `how` `coordinates` and the join's optional `dependency`. C1 is unchanged: nothing is projected from the new kinds. The corrections file is unchanged: its `target.kind` takes every fact kind, these two included.

## Context

An estate often has a library of its own (an invented example: `forge-payments-common`) that several Spring Boot or Fuse services build on as a Maven or Gradle dependency. The map drew it as one more box beside the services, with nothing joining them, and a reader that met the library's client classes in a service sometimes wrote them as calls, so a box named from the reader's free text appeared. What a person expects, in their words: the dependency shown as a line, the library's own calls its own, and an arrow from every module that builds on it, because it is our own repo.

Nothing in the facts said what a build publishes or what it depends on. ADR 0068 read a module's dependencies inside one repo with a built-in reader and left "uses across repos" to the framework model (ADR 0054), which teaches what a house library's annotations mean, not who depends on it.

## Decision

### 1. Two fact kinds (facts file, version 5)

```
artifact:   group: text, name: text, version?: text
dependency: group: text, name: text, version?: text, scope?: compile|runtime|provided|test|import
```

An `artifact` fact is the coordinates a component's build publishes: a pom's own `<groupId>` and `<artifactId>` (a module that writes no `<groupId>` has its `<parent>`'s), a Gradle project's `group` and name (`rootProject.name`). A `dependency` fact is a dependency the build declares in its dependencies (never a `<dependencyManagement>` entry, a plugin's dependency, an exclusion or a BOM import). Each is cited on the line that writes the name (`cite.value` the name, or a Gradle line's coordinates as written), with the group's line, and the version's when one is given, in `cite.with`. A dependency belongs to the component whose build file cites it: a module's pom is its module's (`component`). Coordinates are written resolved (`${project.groupId}` is refused by the schema; the line that writes the value is cited).

Two kinds, not one with a role: they are joined against each other, a repo has one of the one and many of the other, and the verifier checks each against a different part of the build file. Fields of their own, not `framework` facts: a framework fact names what a component is built on in the sense of its reading rules (Spring Boot, a house starter to learn), it is one per framework, and a dependency on the estate's own library is no framework to learn.

The reader records every dependency, the organisation's own or not. Which are the estate's own is never the reader's call, nor a group prefix or naming convention's: it is read from what the estate's repos publish (section 3).

### 2. The verifier reads the build file (rule 4)

`verify/src/build-coords.ts` is a small deterministic reader of a pom (elements line by line, comments left out) and a Gradle build (a dependency line's configuration and coordinates, `group = '…'`, `rootProject.name`). The verifier checks, beside the usual line check of the name: an `artifact`'s cited line is the project's own `<artifactId>` (not a dependency's or the `<parent>`'s); a `dependency`'s is a `<dependency>`'s in `<dependencies>`, not under `<dependencyManagement>` or a plugin; the name is the one that line writes; the group the project, its parent or the dependency writes is the one claimed and its line is cited; the scope is the one declared (a Gradle `test…` configuration is `test`). A miss is `build-coordinates`, with the line it found instead. The same reader is the cross-check: the coordinates and dependencies the build files a kept fact cites write that no fact records are a note (`buildUnrecorded`), never a rejection. The reader is never the path to the facts: it writes none.

### 3. The dependency join

`joinDependencies` (`core/src/facts-deps.ts`) pairs every `dependency` fact with the `artifact` fact whose coordinates (group and name, letter case aside) it names: a "depends on" link from the depending component to the library's, cited at both ends. A dependency on coordinates nobody in the estate publishes draws nothing and asks nothing (counted as `outside`); a test-scoped one draws nothing (`test`); coordinates two components publish draw nothing and are said (`ambiguous`); a component's dependency on itself draws nothing. Pure and order-free.

The library's own calls are untouched: they are the library repo's call facts, joined as before, and nothing of the library is given to the services that depend on it.

### 4. Where it shows

Nothing is projected into C1, as with framework facts: `Component.uses` stays ADR 0068's (a module's dependencies inside a repo, from a built-in reader), and a cross-repo link with its lines at both ends has no C1 field to hold it without a C1 bump. The views read the facts: the graph API (`ui-api-graph.ts`) joins the verified facts on file and hands the links to `buildEstate`, which draws each as a `depends-on` edge between the two catalog components (a link whose end isn't in the catalog yet is left out, never a box of its own). It is its own edge type, so it is never merged into the calls or counted with them, and it is lifted to system level like every edge. The architecture and repo lenses draw it; the integration, data and infrastructure lenses don't (it is no call, event or table). Its join's `how` is `coordinates`, `verified` (code at both ends, each claim checked on its line), with `dependency` (group, name, version, scope), the dependency's lines as `caller` and the publishing lines as `callee`.

The canvas draws it dash-dot with the label "depends on" in words (in italics), and the legend says it apart from the calls with its count; the link counts by who made them leave it out. Why is this linked? says the coordinates and both ends' lines. This link is wrong marks the dependency fact on the depending build file's line `wrong`, with why (required), through the existing corrections file: verify leaves it out and the arrow goes at the next write, as any fact marked wrong does. A dependency arrow has no "All calls on this arrow are wrong" (it has no calls); each dependency on it is corrected under itself.

### 5. Reads before this

The rule is its own rule set, `build-coordinates` (ADR 0167), on the build files: a repo read before is topped up with it alone (`atticus map --all --stale`), and a read with no record lacks it too. A batch prompt (tiers 2 and 3) whose files include no build file carries neither the rule nor the two kinds' lines of the facts reference: a small model's room is mostly its instructions (ADR 0124 addendum A-lean), and at an 8,000-token limit two more lines everywhere left a batch of a generated client less room than a batch may have. The tier-1 command carries everything, as before.

## Consequences

- A library of the estate's own is drawn as what its services build on, with no naming convention to configure; a vendor's SDK and open-source libraries stay off the map.
- The library's calls are its own, so a call through it reads as the library's, once.
- Not done: `depends-on` in `map.md`, impact (`atticus impact`) and the ecosystem views read from C1; a dependency declared through a version catalog's bundle (`libs.bundles.forge`; a catalog's single alias and a pom property's value are read since the beta.25 addendum); npm, NuGet and Python packages (the same two kinds fit them, with readers of their own); the transitive reduction `uses` edges get.

## Addendum (beta.25): reading the build files as they are written, and the arrows a person corrects

- Date: 2026-11-10
- Contracts: the facts file stays at version 5 (a pom's `<scope>system</scope>` is recorded as `provided`, section 6, so 2.0.0-beta.24 reads every file beta.25 writes). C4 3.11.0, additively: a `depends-on` join's `dependency.facts` (each with the coordinates it names) and every publishing line in `callee`, GET /api/graph/edge-calls for a `depends-on` edge, and POST /api/links/corrections for dependency facts. C1 is unchanged. The reading rules' words change, so their hash does; no rule set is added.

A review of beta.24 found the "depends on" arrows missing or wrong in builds as people write them. What changes:

1. **A pom is read as one text with its lines kept**, not line by line: a tag written over several lines (the namespaced `<project xmlns=… xsi:schemaLocation=…>` a Spring Initializr or Maven archetype pom starts with, which beta.24 never matched, so the project published nothing and its `<parent>`'s group was lost), an attribute holding a quoted `>`, a comment and a CDATA section (read as its text) wherever they break. The fixture library's pom starts with that header.
2. **A coordinates fact belongs to the module whose build file it cites, and a module is a component only when the manifest lists it.** The module is the manifest's module whose folder holds the build file (`repos.manifest.yaml`'s `modules`, handed to the verifier as `estate.modules`); a Gradle root build's `project(':x') { dependencies { } }` line is `x`'s. Any other build file is the repo's own component's (`estate.repoComponent`: the manifest's `component`, else the repo's id). A repo whose manifest entry lists no modules ships as that one component, so every build file in it is that component's, whatever folders its build has: a multi-module build (`forge-cards`, its root pom listing `cards-api` and `cards-core`) is drawn as the one service box its endpoints are in, with one arrow to the library, and a dependency of one of its modules on another draws nothing. A component is never made from a folder's name (review of beta.25: before, `cards-api` and `cards-core` became components of their own, the service box had no arrow, an intra-repo arrow was drawn, and a fact naming `forge-cards` on `cards-api/pom.xml` was refused). A fact naming another component than its module's is refused (`build-coordinates`); one naming none is given its manifest module's, or stays the repo's. Every other fact (an entry, a call, a store, a config) of a repo whose manifest entry lists no modules that names a component neither the repo's own nor one the manifest names anywhere (`ledger-api`, the folder its controller is in) is placed in the repo's component (`placedComponentOf`) by the verifier, said as a note (`componentsPlaced`, never a refusal), when the folder its cite is in is a module the repo's root build lists (`<modules>` in the root `pom.xml`, or a `settings.gradle` include: `isBuildModuleDir`), so its endpoints are in the box its depends-on arrow starts from. A monorepo whose folders each have their own build (a web app and an API, the forge-studio journeys) keeps the components its facts name, and the projection a scan makes takes the components as the facts file holds them; a prototype's UI, BFF and mocks (ADR 0133) are components of their own and stay so. The schema's `component` and the build and framework reading rules say a fact's component is the one the manifest names (a module only when the manifest lists modules); the core rules, which every batch carries, are left as they were, since an 8000-token batch has no room for more. A root build's `subprojects { dependencies { } }` (or `allprojects`) line is each subproject's dependency: when the subprojects are all one component (the repo's, when the manifest lists no modules) that component's; when they are several, one fact per component, each naming it (a fact naming none is refused, saying which). The join does the same for facts verified before (`JoinRepo.moduleDirs`).
3. **A Gradle build is read with its blocks.** Only a line directly in a project's `dependencies { }` (at the top level, or in `subprojects`, `allprojects` or `project(':x')`) declares a dependency; a line in `dependencyManagement`, `constraints`, `buildscript`, `resolutionStrategy` or `repositories` never does, and a group or name must be a coordinate as the schema takes it (`url 'https://…'` is none). A Kotlin script's string configuration (`"implementation"("g:a:v")`) is read as the configuration it names. A test suite's configuration (`integrationTestImplementation`, `componentTestRuntimeOnly`, `functionalTest…`, `testFixtures…`) is `test`; `providedCompile` and `providedRuntime` are `provided`; Spring Boot's `developmentOnly` (devtools, on `bootRun`'s class path only, an Initializr pom's `<scope>runtime</scope><optional>true</optional>`) is `runtime`. A build tool's own configuration (`checkstyle`, `pmd`, `spotbugs`, `jacocoAgent`, `detekt`, `ktlint`, `codenarc`, `errorprone`…) runs the tool and ships in nothing: no dependency, and a fact citing one is refused saying so.
4. **A multi-project Gradle library's subprojects publish**: settings.gradle's `include 'x'` (or `include(":x")`, or an include over several lines, Kotlin's `include(\n ":a",\n ":b"\n)`, each name cited on its own line) is a subproject's name, `project(':x').name = 'y'` renames it (the include line is then refused for `x`, citing the renaming line), and its group is the one the root build's top level or `allprojects { }` sets (the root's), `subprojects { }` or `project(':x') { }` set, or its own build's top level.
5. **This link is wrong removes the arrow.** A link is one per pair of components and keeps every dependency fact it rests on (two module poms of a component, a `<profile>`'s copy, `implementation` and `runtimeOnly` of the same coordinates, and every other coordinate of the same library component: `kit-api` and `kit-core` of component `kit` are one link, `published` holding each artifact fact), `from` first; its join's `dependency.facts` lists each with its lines and the coordinates it names, `callee` every publishing line, and the form lists them all with their coordinates, every one chosen at first. The chosen ones are marked wrong in one POST /api/links/corrections, all or none (every item checked before any is written, each file written whole, put back on a failure), never one POST per fact, which could leave some written. Before, only the first was offered, the arrow came back from another line after Apply, and two coordinates made two links of one id, so a view showed one and hid the other. A merged link's `scope` is said only when every fact on it has that scope (review of beta.25: a compile `kit-api` and a runtime `kit-core` say none, and Why is this linked? heads it with none).
6. **`<scope>system</scope>` is recorded as `provided`** (a jar from a path on the machine, compiled against and never packaged, drawn as `provided` is): the facts file keeps its version 5 and `DEPENDENCY_SCOPES` its five values, so a beta.24 reader reads every file beta.25 writes.
7. **A `${property}` is resolved** from the pom's `<properties>`, its own coordinates (`${project.groupId}`, `${project.version}`) and its `<parent>`'s (`${project.parent.groupId}`), and from its parent poms' `<properties>`, nearest first, a property of a property followed; every `<properties>` line it resolves through (in the parent pom too) must be in `cite.with`, as section 1 says of the value's line. The project's and its `<parent>`'s own `<groupId>` and `<artifactId>` are elements the verifier reads itself, so a `${project.groupId}` that resolves to the group a module inherits needs only its own line cited (a careful reader of `<groupId>${project.groupId}</groupId>` cites that). One neither the pom nor a parent sets is refused, naming it. A module's parent pom is the file its `<parent>`'s `<relativePath>` names (`../parent/parent.xml`), else a pom whose `<modules>` lists its folder (`<module>../cards-api</module>` in a sibling `parent/` folder), else `../pom.xml`, each only when its `<artifactId>` is the one the `<parent>` names; `<relativePath/>` says it is in a repository. A pom is `pom.xml`, `*.pom`, a parent pom named for what it is (`shared-pom.xml`, `parent-pom.xml`), or a file a pom of the repo names by its `<relativePath>` (`parent/parent.xml`); never a plugin's generated `dependency-reduced-pom.xml` or `.flattened-pom.xml`.
8. **A newer Atticus's facts.** 2.0.0-beta.23 and beta.24 refuse a whole facts file holding a kind they don't know (beta.23 a version-5 file); that can't be changed in a released version, and so beta.25 writes nothing they refuse (section 6). From beta.25 a fact a newer Atticus wrote is left out of the read, one fact at a time, and said as "written by a newer Atticus" (`parseFacts`' `newer`, `parseFactsLines`' `newer`, with the line as written), as the catalog says of a record of a newer version: a fact of an unknown kind, or of a known kind whose only faults are a field this version doesn't know or a value of one of its lists it doesn't know. A slip of the assistant's is no newer fact: it is refused, as any fact the schema refuses, so the assistant is told and writes it again, never kept unread for good (review of beta.25). A value is a newer one's only when it is a lowercase word more than two edits (a letter added, dropped or changed, or two swapped) from every value of its list (`scope: "shaded"`); one within two (`scope: "complie"`, `"runtine"`, `conf: "declard"`, `verified: "lnie"`, `by: "asistant"`) is a slip, refused naming the value it may have meant, and `"Compile "` is a slip as before. `scope: "system"` is refused saying "record a system-scoped dependency as provided" (section 6). A field is a newer one's when it is a name as Atticus writes them and not a slip of a field the kind has (or its citation has): a slip is one edit from that field, starts with its letter and is not the field with an `s` (or a `d`) added or dropped (`pathh`, `scpoe`, `verison`, `componnet`); a word of its own is a newer field (`lines`, `path`, `note`, `size`, `date`, `code`, `lang`, `hint`, `since`, `title`, `named`, `scopes`, `versions`, `components`, `repos` on a dependency fact: `lines` made `verify --write` exit 1 before). `atticus verify --write` (and `atticus map`'s write) keeps such lines in the facts file as written, never moved to `rejected.jsonl`, and says how many; a repo's read (`repoReadOf`, the Repos page and Home) names them as a reason it is incomplete. Every other reader leaves them out of what it reads. The file has no place for a version stamp an older reader would accept (each line is one strict fact, and a header line is no fact), so none is written.
9. **Every dependency on a merged arrow**: GET /api/graph/edge-calls gives every join of a `depends-on` edge, not only the 20 a view lists, and Why is this linked? reads the rest from it, each with This link is wrong.
10. **The prompt's room is keyed on the build files**, as section 5 says, not on the deploy topic: a batch carries the `build-coordinates` rule and the `artifact` and `dependency` lines of the facts reference only when it (or the files its rejected facts cite) holds a pom.xml, build.gradle(.kts) or settings.gradle(.kts), or a version catalog. A batch of a Dockerfile or a Helm chart carries neither. A read's top-up of the set still reads the deploy files' batches.
11. **A Gradle version catalog** (`gradle/libs.versions.toml`, or another `gradle/<name>.versions.toml`) is a build file. A dependency declared by an alias (`implementation(libs.forge.ledger.api)`) is cited on the catalog's `[libraries]` entry (`forge-ledger-api = { module = "forge.ledger:ledger-api", version.ref = "forge-ledger" }`, a `group`/`name` table or a `"g:a:v"` string), with the alias's build line in `cite.with`. The verifier checks the entry gives the coordinates, that a cited build line names the alias (`-`, `_` and `.` all separate its parts, after the catalog's name, the file's) directly in a project's `dependencies { }` with the scope claimed, and that a version claimed is the entry's own or the `[versions]` entry its `version.ref` names. The fact's module is the alias line's build file's. A bundle (`libs.bundles.x`) isn't read. The reading rule says so, and that a tool's configuration is no dependency; its words change, so its hash does.
12. **Read once, whatever the size** (review of beta.25): what is read from a build file (a pom's reading, its dependencies by line, a Gradle build's blocks and settings.gradle's includes, the repo's parent poms) is held per lines array or per repo, so a 3,000-dependency pom verifies in a few seconds. A parent pom named for what it is and a version catalog are read in the first batches with the other build files (`readingRank`), so the rule and an alias's lines come with the poms and builds that use them.
