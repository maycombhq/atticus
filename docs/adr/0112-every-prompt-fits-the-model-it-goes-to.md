# 0112. Every prompt fits the model it goes to (C1, C5)

- Status: accepted (pending review by the product owner)
- Date: 2026-10-23
- Builds on: ADR 0074 (the AI reads; every fact cites its code), 0082 (scan verify), 0090 (the VS Code extension runs the steps with Copilot), 0103 (AI steps that hold up with Copilot), 0106 (model runs; a knowledge scan in batches that fit the model), 0107 (the context engine)

## Context

At a bank that allows only GitHub Copilot, the VS Code extension sends each AI step's prompt to Copilot's model through `vscode.lm`, often GPT-4o mini with a 12,078-token limit and no file tools: one prompt in, one answer out. The steps built their prompts against the org pack's budget (150,000 tokens by default), so on Copilot most ended "too-long" in the runner after the prompt was built. Only the knowledge scan was batched (`--batch-tokens`).

Two steps also put code in a prompt in a way a one-shot model can't use:

- **Spec draft** sent the first 30 files the catalog cites, whole (400 lines each), at the lowest priority, so under a tight budget the code went first, and the service and repository lines a flow's steps cite were never ranked above a file nobody cites twice.
- **Scan verify** sent no code. Its instructions said "open every file you need", which a model with no tools can't do, and a record it listed as `confirmed` was kept with no check and pinned as verified, which the context engine then weights up (ADR 0107 point 3). A model that confirmed every id passed.

## Decision

1. **A model limit every step honours.** `atticus <step> --max-tokens n`, on every hand-off AI step (scan survey, scan verify, spec draft, knowledge scan, find and ask, change feature, architecture, draft and needs, plan stories, and the critic's lenses), means the whole prompt must fit n tokens. While the command runs, every pack it builds is fitted to it (`withPromptLimit` in `@maycombhq/ai`, scoped to the call, so steps running side by side on the app's server keep their own): a step's budget becomes the smaller of its own and the room the limit leaves, less its instructions as before. The steps on the context engine take that room as the engine's budget (`roomFor`, `stageBudget`); the others through `buildContextPack`'s budget. A knowledge scan given only the limit sizes its batch from it (the room less 4,000 tokens for its instructions and the items read before).
2. **How the room is counted.** Tokens are counted as the pack counts them (characters / 4). Code and YAML tokenize nearer 3 characters a token, so a quarter of the limit is kept back for the counter's error, and 400 tokens for the frame around the pack (the hand-off's heading, result file and finishing command, and the runner's preface): room = ⌊n × 0.75⌋ − 400. For GPT-4o mini's 12,078 that is 8,658. The runner still counts the real tokens with the model before it sends, as a last check.
3. **Who passes the limit.** The VS Code runner passes its model's real limit (`maxInputTokens`) to every step, not only the knowledge scan; the resume command carries it, so every round fits. The app's server passes the configured model's limit to each step it starts (`POST /api/runs`) when `runtime.yaml` gives it: `adapters.model.settings.maxInput`, a new optional setting every model provider reads and checks (a whole number of 1,000 or more).
4. **Code excerpts, not whole files.** Where a step puts code in a prompt (spec draft and scan verify), it sends a window of 20 lines on each side of every line a fact cites, merged where windows overlap or touch, ranked by how many facts cite them. Each excerpt keeps its path and the file's own line numbers ("`path` lines 10-54 (cited at 30, 34; numbered as in the file)"), so the model can cite exactly. Spec draft ranks by the catalog records and the steps of the flows on file, and places the code above the other repos' entry points, so the cited code stays in the prompt before a target list is cut. The target list itself goes in as the entry points this repo's calls reach (kept with the catalog), then each other component's list a hundred at a time, the components this repo calls first, so a tight budget cuts it in parts instead of whole.
5. **Scan verify gets the code and must cite.** Its prompt carries the excerpts around each record's evidence. A confirmed record is written as `{ record, at, says }`: the line that shows it, in the file the record was read from, within the excerpt window of the record's line, with a quote of at least 8 characters found on that line that names the record's path segment, method or table. That is checked deterministically. A confirmation without such a citation, or a bare id (the form before this ADR, still read), is not recorded as verified: it is handed back with the reason, and after the last attempt it is listed as left out. Only cited confirmations are pinned in the proposal's `verified` list. The answer schema (`VerifyAnswer.confirmed`, C1) widens to take either form; the stored proposal (`ScanVerifyProposal`) is unchanged, so its schema version stays 1 and nothing needs migrating.
6. **A prompt that can't fit is said before the hand-off.** A step names what it can't do without beside its instructions (spec draft: the repo's catalog records; scan verify: the record lists; change needs: the brief). When those alone don't fit the room, the pack is not built and the step ends, before anything is handed off, with the numbers and what to do: "atticus spec draft forge-orders can't fit its smallest useful prompt in the model: it needs about 9,100 tokens (its instructions and 4-catalog), and a model of 12078 tokens leaves 8658 for the prompt. Use a model with a bigger limit (atticus.model in VS Code, or adapters.model in runtime.yaml)", and, for the knowledge scan, "or read fewer pages at a time with --batch-tokens n". A critic lens that can't fit is recorded as failed, unsent, with the same sentence as its reason.

## Consequences

- On Copilot every step's prompt is built to fit, or the step says why it can't before anything is sent; the runner's "too-long" ending becomes a last check, not the usual end.
- A one-shot model reads the code the facts rest on, and a scan verify confirmation is a cited fact, checked like the others, not a list of ids.
- C5's runtime interface is unchanged: `buildContextPack` gains optional fields (`maxTokens`, `required`, `step`, `smaller`) and the context pack manifest records the fitted budget as before. C1's change is additive and confined to the model's answer to scan verify.
- Not built: the model's tools (ADR 0107 point 4); a step whose required sources are bigger than the model still needs a bigger model, and spec draft has no batched form yet.
