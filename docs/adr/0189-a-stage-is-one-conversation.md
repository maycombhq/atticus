# 0189. A stage is one conversation

- Status: accepted (the product owner's decision "One thread per stage", 2026-11-09)
- Date: 2026-11-09
- Builds on: ADR 0070 (the change drafter), ADR 0078 (questions and answers), ADR 0087 (the stage loop), ADR 0106 (model runs), ADR 0113 (files attached to a change), ADR 0115 (the critic's lenses in a stage), ADR 0116 (the expansion and the rerank), ADR 0119 (live events and the file watcher), ADR 0124 addendum D-app (a stage tab's findings), ADR 0179 (a change sketched on the canvas), ADR 0181 (stage drafts and corrections), ADR 0185 (a stage's lenses in one hand-off), ADR 0186 (a person confirms writes to shared systems), ADR 0187 (the Console)
- Contracts: C4 (local API 3.5.0, additive): `GET` and `POST /api/changes/{changeId}/stages/{stage}/thread` (StageThreadView, StageThreadPost), the sketch stroke `retire`. The stage files gain the optional `dropped` list in `stage/<stage>.yaml` (stage schema 1 stays) and the proposal's `stage/proposal-thread.yaml`; a deploy step may name a planned repo. No catalog (C1), dialect (C2), rule (C3), plugin (C4 SDK), AI runtime (C5) or org-pack (C6) schema changes. The hand-off prompt's last line changes, so prompt hashes change (the recorded replays were re-baselined).

## Context

An app-only audit took a change through every stage with only the app. Each stage was a trip: Prepare it for your assistant sent the person to Set up › Model runs (a setup page of prompt file paths, token counts and embedding model names); they pasted a long prompt; the assistant wrote YAML; they came back to press Done. The app didn't notice the answer arriving: the run said "Waiting for its answer" until Done was pressed, and the prompt itself ended with "When the file is complete, run: atticus handoff done run-…". Every stage took two pastes or more (a context-expander prompt before the real one; architecture took five). Replies were scattered: a comment box per finding, a Correct box per file, the Questions page elsewhere. After Done the screens contradicted each other ("Passed the checks" beside a banner telling the person to run `atticus change draft … --resume run-…`; an empty banner after a failed round; "any AI lens is with your assistant. Each waits in Model runs" when no lens waited; "0 open" beside four findings at another gate). A question the assistant raised was dropped without a word because its citation was two lines off. "Make the fix" on a finding about a file the stage's assistant may not write only recorded "Fixed by" and changed nothing, so the critic found it again. The proposal drafter didn't read the files attached to the change. Components the architect drew as new were refused as "not in the catalog", though drawing the future before the repos exist is the point of the design stage. The Change diagram's "doesn't exist yet" box stayed ticked from the previous stroke, and there was no stroke to retire a component.

## Decision

1. **A stage is one conversation, on its own tab.** Each stage of a change (the proposal, feature, architecture, stories, and a small change's one step) is shown as one thread: the prompt the person gives their assistant (with Copy), the assistant's answer summarized and what its checks said, what the stage wrote, what the critic found (Reply, Make the fix, Ask the owner, Not relevant), the questions it routed to a person (answered in place), the person's replies and corrections, and the questions that couldn't be kept, in order. A reply box at the bottom, "Tell the assistant…", sends the person's words and starts the next round. The thread is the view and the place to reply, not a new AI runtime: the AI still runs in the person's VS Code or IntelliJ (Copilot or Claude Code, by hand-off), unattended Copilot where allowed, or a server model where configured. Feature design, Architecture and Stories show their stage's thread where the critic's panel was; At a glance shows the proposal's (or a small change's). Set up › Model runs stays the administrator's view of every run; the thread keeps a prompt's size, its model and its files under Details.
2. **Assembled from what exists.** `GET /api/changes/{id}/stages/{stage}/thread` reads the change's runs (each run's prompt, answer, state and errors; a lens run is the stage's when it came after one of its drafts), the stage's loop file, the critic's latest round at the stage's gate with each finding's options and comments, the stage's questions, the corrections (ADR 0181) and the replies. No store of its own. `POST` writes a person's words through the mechanisms that already carry them to the next round: a reply is a question the person answered as they asked it (ADR 0078), listed in the stage's loop file, so the next round's prompt hands it to the drafter as their answer; a reply about a finding is a comment on it (ADR 0124 addendum D-app); the proposal step, which has no loop file, lists its replies in `stage/proposal-thread.yaml` and its drafter reads them as data. The thread follows the live events it already had (`file.changed`, `run.changed`).
3. **The answer arrives by itself.** The server watches for the answer file of every waiting hand-off of a stage's drafter or the critic's lenses (the watcher and its events exist, ADR 0119) and runs the check Done runs, the same function, then resumes the step as Done does; the thread shows the result and says the app checked it. It never acts on a half-written file: the file must sit unchanged for three seconds (each write starts the wait again) and read as complete (YAML that parses, a change draft with its proposal, a batch with every part's section). It never runs twice: one check at a time per run, never again on the same text (a failed check waits for the file to change), and a run Done or the command line checked has moved on and is left alone, or only resumed when its resume is still kept. A task run's Done (it builds and commits) and a decision's stay a person's to press. Done stays, as a manual fallback.
4. **One paste per round.** A hand-off round asks no separate context-expander prompt (nor a rerank prompt). The expander's effect on the selection (its names mapped to the estate's ids, the seeds the index ranks from) is kept without a model: every name or alias of the estate's records that the input uses as words of its own becomes that record's id; names the estate doesn't know stay the index's own (names in backticks and endpoints), so the step's gaps stay. The synonyms a model would add are left to the assistant, which reads the code itself. A model runtime (server model, unattended Copilot) still runs the expansion, unattended. The critic's lenses, when AI lenses are on, remain their own prompt (a fresh session reviews the draft, ADR 0115), asked together in one hand-off (ADR 0185), and shown in the thread as the critic's prompt.
5. **The prompt's last line asks only for the file.** It reads "When <file> is complete, stop there: Atticus notices the file and checks it. There is nothing to run." A stage drafter that may check its own draft (W3a) is told, before it, the stage's read-only check it may run (`atticus stage check`), which writes nothing.
6. **No contradictions and no silent drops.** Done's lines and the next round's are said in the app's words (the next prompt is in the stage's thread; never a command with `--resume` to type); a failed round says what failed; the critic's note says a lens waits only when one does; the thread says when its findings are another gate's. A question the assistant raised whose evidence is no line in the metarepo is kept in the loop file's `dropped` list and shown in the thread ("1 question couldn't be kept: its line didn't match") with **Keep it anyway**: a person keeps it, citing the nearest line of the file it named (its last line, when it cited past the end), or the stage's loop file when no file it names is there.
7. **Make the fix, where the assistant can't.** A finding about a file the stage's assistant writes goes to the assistant in the next round (Make the fix fills the reply box with the fix, about that finding). A finding about a file it doesn't write (the critic citing `interfaces.md` lines while the architecture prompt writes only its answer) opens that file in the app's editor at the cited line; saving it records the fix as made. We picked the editor because it works today with nothing new to trust: giving one round's assistant permission to edit one more file would change what every hand-off prompt promises ("Change no other files").
8. **The first step reads the attached files.** The proposal drafter gets the files attached to the change (ADR 0113) as data, each cited by its file, as the later stages do; a change with an attached file and a template brief may be drafted from it.
9. **Planned components are known.** The components a change's own diagram draws as new (a new flow's component the catalog doesn't have, a call's target marked new) or retires are read off its target flows (and the proposal's Systems rows marked new) by the architecture and stories stage checks and by the critic. A callee the change plans is "planned in this change", not "not in the catalog"; the deploy order may name a planned repo, marked planned in the design; a story may depend on it; the lenses get the planned components as data. Nothing about them is a fact: the catalog has them once their code lands and is read. The canvas gains **A component retired** (every flow of it today is removed, one stroke, undone together), and "The API doesn't exist yet" and the stroke's own words are reset after each stroke is drawn.

## Consequences

- A stage round is: open the stage's tab, press Start (or send a reply), copy the prompt into the assistant, and wait; the thread shows the answer, the checks, the critic and the questions as they arrive, and the reply box starts the next round. No trip to Set up, no Done, no command.
- Prompts change (the last line, and no expander prompt in hand-off rounds), so the recorded replays (m3-exit, m4-exit) were re-baselined by their new prompt hashes.
- The app checking answers on its own means a half-done edit that sits for three seconds and parses is checked; a failed check just waits for the next change of the file, and the drafter's self-check limit (W3a) counts those checks as before.
- The proposal step's replies live in one more small file under the change folder, reviewed in its pull request like the rest.
- The thread is built on every read from the files; it is a view, so a change made from the command line, an editor or another page shows in it.
- Safety rules are unchanged: a person confirms every write to a shared system (ADR 0186); the AI never pushes or merges; every fact keeps its provenance; ingested content stays data (a reply is quoted in the hand-backs data block, never the trusted instructions).

## Accessibility

The thread is an ordered list; each item is an article with its own label. The headline is a polite status, so a screen reader hears the answer arrive. Every button names its finding or question ("Reply about F-3", "Keep it anyway: …"); the reply box's label says which finding it is about. Prompts, details and long text are behind disclosures. Loading, empty ("Nothing has happened at this stage yet") and error states (with Try again) are said; a reply that can't be taken yet says why.
