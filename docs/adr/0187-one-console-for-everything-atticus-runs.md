# 0187. One Console for everything Atticus runs

- Status: proposed (built from the person's question "when this map is running where do I see the log on the UI", 2026-11-09; for the product owner to accept)
- Date: 2026-11-09
- Builds on: ADR 0015 (the local server and its jobs), ADR 0050 (the local log and its redaction), ADR 0097 (the app in a VS Code panel), ADR 0106 (model runs), ADR 0119 (live events and the file watcher), ADR 0173 (an unattended Copilot run and its Console)
- Contracts: C4 (local API 3.1.0, additive): `GET /api/activity`, `GET /api/activity/{id}/lines`, the live events `activity.changed` and `activity.lines`, `title` on a Job and the job kind `work`. No catalog, rule, plugin or org-pack schema changes. The run files under `.atticus/logs/` are this machine's own, not a contract.

## Context

The app showed what Atticus was doing only for an unattended Copilot run it started itself (ADR 0173): its strip and Console drew nothing otherwise. The app's own jobs showed their lines only under the button that started them, and most printed nothing until they ended. A command run in a terminal (`atticus map forge-ledger`, `map --all`, `verify`, `workspace sync`), by VS Code or IntelliJ, or by a Copilot session wrote only an event summary to `.atticus/logs/atticus.log`, which the app never shows. A hand-off run waiting for the person's assistant was listed under Set up › Model runs, but nothing said what was happening. A person with forty repos and a long `atticus map --all` had nowhere in the app to look.

## Decision

1. **One Console, always there.** The bar at the foot of the app is on every page (open and close it). It lists everything Atticus is doing or did lately on this metarepo, newest first: its kind, its title (the command, or the app's job: "Scan", "Applying to forge-ledger", "atticus map forge-ledger --handoff"), where it was started (this app, a terminal, VS Code, IntelliJ, a Copilot session, the person's assistant), its state (running, waiting, done, failed, cancelled, ended without saying) and when. The entry picked shows what it printed, live, with follow, search, copy and earlier lines. A Copilot run keeps its tab per session inside it. The strip under the top bar shows whenever anything runs, with what and how far, **Show in the Console**, and **Stop** where the app can stop it (its jobs, a Copilot run); a command run in a terminal says to stop it there (Ctrl+C).
2. **The app's jobs keep what they print.** The JobManager keeps each job's last 5,000 lines and its last 100 jobs. Work prints with `c.line`, or anywhere inside the job through a printer the job sets (core's `withPrinter`/`printToCurrent`, an AsyncLocalStorage), which the command line's `main` and the routes' run helpers call for each line. So a scan, a sync, an AI step, Apply, Propose, Bring in, upgrade, conformance, a Match and Run all ready tasks stream their lines as they print them. A job that printed nothing gets its result's lines and errors when it ends. The requests a page waits on (the critic, a wiki's sync, a team's tool, a run's Done) run as jobs of the kind `work` through `JobManager.track`, which keeps their answers exactly as they were, so they show in the Console too.
3. **A long command run outside the app keeps its own run files.** When `atticus` runs from its own process (bin.js) at a metarepo, a command on the list (map, scan, verify, upgrade, reconcile, `workspace sync|bring-in|open`, `task run|run-ready`, `knowledge scan`, `handoff done`, `index rebuild|embed`) writes:
   - `.atticus/logs/runs/<runId>.log`: every line it prints, without colour codes, each redacted with ADR 0050's `redactText` (secrets, tokens, credentials in URLs, the home folder and user name), cut at 4,000 characters, and bounded at about 2 MB (past it the log keeps its last half, counting the lines dropped);
   - `.atticus/logs/running/<runId>.json`: the command words; the positional words that look like an id (a repo, change, run or task id: letters, digits, `.`, `_`, `-`, `/`, nothing redaction would change, no `//`), any other word shown as `…`; the flag names, never their values (ADR 0050's rule); who started it (from `ATTICUS_ACP_SESSION`, `ATTICUS_STARTED_BY` which VS Code and IntelliJ set on the commands they run, `TERM_PROGRAM=vscode`, `TERMINAL_EMULATOR=JetBrains…`, else a terminal); the process id and a hash of the machine's name; when it started; and, written again at its end, how it ended (exit code; 130 and 143 are cancelled). Ctrl+C or SIGTERM alone end it as before and record the end; with another handler (map --all's "stop after this step") that handler decides.
   - The run id is `YYYYMMDD-HHMMSS-<pid>-<4 hex>` (UTC; no `:`, so Windows takes it). Only the last 50 runs are kept. A run still `running` whose process is gone on this machine, or that started days ago, is shown as ended without saying.
   - Quick and read-only commands make no file: anything not on the list (help, list, show, next, `--json` questions), and `--help`, `--version`, `--check`, `--dry-run`, `map render`, `verify audit`, `scan review`. The app's server runs commands in itself (as jobs) and never writes these files. `ATTICUS_RUN_LOG=off` turns it off.
   - `.atticus/logs/` is in `.atticus/.gitignore` (LOCAL_ONLY) already, and the files are written as the log is: writing never fails the command.
4. **The server follows them.** The file watcher follows `.atticus/logs/running/` and `runs/` apart from the metarepo's files (never as `file.changed`, so pages don't read again for nothing) and nudges the Console's routes, which also look once a second. New lines go out as `activity.lines`, a new or changed entry as `activity.changed`, on the same event stream as the Copilot run's.
5. **Hand-off runs.** A hand-off run that waits (prepared, waiting, produced) or ended in the last day is an entry of its own (where: the person's assistant): its lines say where the prompt is, what to do with it and the Done to press or run. Once Done runs, in the app (its job, tagged with the run) or as `atticus handoff done <run>` anywhere (its run log), what it printed is in the same entry.
6. **The API.** `GET /api/activity` lists the entries (at most 100) and how many run; `GET /api/activity/{id}/lines?from=n` gives an entry's lines from a line on, or its last 5,000. A Copilot run's lines stay its tabs (`/api/copilot-runs/{runId}/tabs/{tab}`). Stop uses the existing routes, named on the entry. Nothing writes to a shared system, so no confirmation (ADR 0186) is involved; every route needs the session token.
7. **Editors.** VS Code's bundled panel passes every `/api/` call through the extension, so the routes work there as they are; it gets no live events, so the Console polls (every 1.5 s while anything runs or the Console is open, else every 5 s; 3 s and 15 s in a browser, which hears the events). IntelliJ's tool window loads the page from the server.

## Accessibility

The Console's toggle says Open or Close with `aria-expanded`; the list is a vertical tab list (arrow keys, Home, End) beside its panel; each log is a focusable `role="log"` with `aria-live="off"` (a chatty run would drown a screen reader). Instead a polite status says when an entry ends ("Scan: done") and, at most every ten seconds, how many new lines the shown entry got. Nothing takes focus: a new run is shown only while the person hasn't picked an entry. Empty ("Nothing has run yet on this metarepo"), loading and error states are said, with Try again.

## Consequences

- Wherever a long command was started, the person sees it in the app, with what it printed, while it runs and after.
- A command run in a terminal at a metarepo writes two small files under `.atticus/logs/`; fifty runs and about 2 MB a log at most.
- A job keeps its last lines in the server's memory (5,000 lines, 100 jobs), gone when the server stops; a command's run files stay.
- Other builders' routes that start jobs get the Console for free; a route that runs CLI code with its own io should pass its lines to `printToCurrent` (the run helpers do).

## Addendum (review, 2026-11-10)

- A Copilot ACP step's progress goes through the run's printer (`printProgress`): standard error, the command's run log and the app job's lines.
- The server tails a command's log from the byte and line it read to (core's `tailTerminalRunLines`), at most four reads of 5,000 lines a look and on at the next one; a log cut meanwhile (its record's dropped count or its file changed) is read again from the record. The watcher's nudge comes at most every 200 ms, and once after the last write.
- A run still running whose process is there is never pruned; the list keeps every running entry, then the newest of the rest up to 100.
- The Console takes an answer from a later line than it asked as lines dropped, says how many, and goes on from there.
- Liveness: on Linux the record keeps its process's start (`procStart`, from `/proc/<pid>/stat`, one file read) and a pid whose process started at another time is ended; a command started by the command line writes its record every 30 s (`beatAt`), and a record that beats but has been silent (record and log) for over five minutes is ended without saying. A record without `beatAt` (an older Atticus) is judged as before.

## Addendum (beta.27, 2026-11-11)

- A run's title keeps a flag's value that is an id, a name, a date or a handle (`atticus initiative plan transfer-limits-rollout --target 2027-03-31 --by @bao`; beta.26 showed `--target --by`). The record's `flags` stay names only, and the local log (ADR 0050) still keeps no values.
- **Which values: an allow-list** (beta.27 review; the first cut was a deny-list of secret-sounding flag names, and `--pass=hunter2`, `--client-key`, `--pw`, an email after `--by` and a token inside `user:pass@host` all reached the title, the running record and `/api/activity`). A value is kept only for a flag in core's `TITLE_VALUE_FLAGS`: string options the command line declares (cli-options' `OPTIONS`; a test holds every entry to a declared string option) whose value, by the flag's name and meaning, is an id, a name, a handle, a date or a small number (`repo`, `repos`, `change`, `task`, `run`, `round`, `story`, `epic`, `kind`, `type`, `mode`, `lens`, `gate`, `model`, `release`, `journey`, `target`, `step`, `state`, `scope`, `by`, `owner`, `team`, …). Free text (`--note`, `--answer`, `--with`, `--value`), files, folders, hosts and URLs (`--from`, `--path`, `--host`), keys (`--key`) and **every flag the command line doesn't know** keep their name only: the command line reads values only for those flags (`optionValuesOf`), and a word right after an unknown flag given without `=` (`--pass hunter2`) shows as `…`, never as a command word. Even for an allowed flag the value is dropped when it has an `@` anywhere but a leading handle's (`@bao` stays, `bao@northwind.example` goes: `--by` takes a person), a `://`, a `:` before an `@`, a backslash, a well-known token prefix (`ghp_`, `glpat-`, `npm_`, `sk_live_`, `sk-`, `xoxb-`, `AKIA`, `eyJ`, …) at any length, a token's shape (`hasSecretShape`, `keyIsSecret`), a run of 16 hex digits or 9 digits, or anything the log's redaction would change, with this machine's home folder and user name; a value kept is cut to 48 characters. `--root` and `--metarepo` still keep none.
- **Which words: the command's declared places, each an id's strict shape** (beta.27 re-review; positional words still passed only beta.26's id test, so `atticus secret set ATTICUS_MODEL_KEY <key>` showed the key, as did an `AKIA…`, `sk-…` or `glpat-…` token, 32 hex digits, `Summer2026` and every random 16 to 31 character string). `secret` keeps no run log at all (a quick command; its key is read from stdin, and `secret set <name> <key>` is refused without saying back either word). The command line shows a positional word only in a place the help declares for it (`titleSlotsOf`: the command's words, then its arguments' places, an argument's word only when it takes an id: a repo, a change, a flow, a system, a question, a finding, a record, one of a choice's values, or an argument named as an id); a free-text, file, folder or URL argument (`intake add <files...>`, `repo add <url|path>`) and every word past the places show as `…`, as does every word after `--` (its flags too), after an unknown flag without `=`, and after a known flag that took the next flag as its value (`--note --pass hunter2`). Every word kept, and every item of an allowed flag's value, passes core's `titleWord`: no `@` but a leading handle's, no space, backslash or `//`, none of cite.ts's `TOKEN_PREFIXES` (one list: Git hosts', package registries', payment, chat, cloud, mail, point-of-sale and telephony providers' keys, `AccountKey=`, a shared access signature, `Bearer`/`Basic`) or `hasSecretShape`, nothing the log's redaction changes; then either an id known by its form (a date, a version, a task's label `1.2`, `q-<hex>`, a run id, a slug of words and small numbers, `ado:1234`, `link:<repo>:<call>`) or no `:`, no long run of hex or digits (a card number in fours too), no `keyIsSecret` shape, and the strict shape of an id: parts (a lowercase word with at most three digits after it, a capitalised word, an acronym of up to 8 letters, a number of up to 6 digits) joined by `-`, `.`, `_` or `/`, with at most one run of digits. A random-looking string has none of these shapes, so it is dropped whatever its length (a seeded fuzz holds every random base62 string of 16 to 31 characters); a harmless word dropped is the price. An allowed flag's value with a `:` or starting with `-` is dropped. Words dropped one after another read as one `…`.
- **The runs beta.26 kept are titled again.** beta.26 run logs (machine-local, git-ignored, the last `RUN_LOG_KEEP`) may hold a key typed as a positional word. The first command of beta.27 at a metarepo writes each record of `.atticus/logs/running/` again with the title and words the rules above give, from its words and flag names, and nothing else of it (its log, state and times stay); `.atticus/logs/running/.retitled-beta27` says it was done. Beta.27 re-review: a run of `secret` is removed, its record and its log (beta.26 printed a mistyped key back into the log: "<key> isn't a variable's name"). The migration runs in the command line's own process only (never in a job the app's server runs in itself) and not when `ATTICUS_RUN_LOG=off`; it reads only regular files of at most 1 MB (`lstat` first, then opened with `O_NOFOLLOW` and `O_NONBLOCK` and checked by the descriptor: never a link, a FIFO or a folder), leaves a record still running to its process, writes a record beside itself and renames it into place (the Windows fallback that writes in place refuses a link), and makes the mark with `O_EXCL` (a link at its name counts as the mark). A folder it can't write (a read-only metarepo) is left alone without reading anything, and a mark it couldn't write isn't tried again by that process; the mark is written even when nothing changed.
- **Flag names a title shows** (beta.27 re-review): only those the command line declares (cli-options' `OPTIONS`, with the command's own); any other shows as one `--…` and is left out of the record's `flags` (a name typed may be the secret: `--correct-horse-battery-staple`). An argument the help quotes (`alias "<name>" <id>`, `feature name <id> "<name>"`) is free text, never an id's place. A work item's reference is an id only for a tracker C1's `ExternalRef` names (`ado:1234`, `jira:4711`, `jira:PAY-12`), so `pin:1234`, `pass:1234` and `otp:123456` are dropped. A command named another way (`join shared refresh <team>`, which runs as `estate shared refresh`) gives its places to the command that runs.
- **Kept by design** (beta.27 re-review): a lowercase, passphrase-like word in an id's place (a repo, a change, a task, a party: `atticus map correct-horse-battery-staple`) is shown, since it has an id's shape and nothing tells it from one. The realistic risk is low: `secret`, the one command a key is typed for, keeps no run log and refuses positional words, and every place a value could be typed into as free text shows `…`.
