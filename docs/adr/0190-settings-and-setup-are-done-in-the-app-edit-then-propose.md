# 0190. Settings and setup are done in the app: Edit, then Propose

- Status: accepted (the product owner's decision, 2026-11-09: "settings and setup are done in the app"; built from the app-only audits)
- Date: 2026-11-09
- Builds on: ADR 0009 (the repos manifest), ADR 0032 (manual adapters), ADR 0051 (the metarepo's stamp and `atticus upgrade`), ADR 0077 (repo types), ADR 0121 (the AI tab), ADR 0128 (what a repo is), ADR 0181 (AI decides first), ADR 0183 (Propose for review), ADR 0186 (writes to shared systems need the person's confirmation)
- Contracts: C4 (local API 3.5.0, additive). C6 unchanged: every file is written through the existing org-pack and manifest schemas. runtime.yaml's default is written at its current version (4), which the schema already took.

## Context

The product owner decided that settings and setup are done in the app, the way corrections are: the app writes the file in the metarepo and offers Propose for review, which opens a PR a person merges. App-only audits found what still needed a terminal or a YAML edit:

- **No metarepo from the app.** `atticus ui` in an empty folder ran a half-working app with no Create button; Repos said "run atticus repos discover <folder>, or add one to a repos.manifest.yaml"; Onboarding's steps were commands. There was no add-repo API, and the Repos page only edited repos already listed.
- **No Git host from the app.** The first hand-off said "No Git host is configured. Set adapters.gitHost in org-pack/runtime.yaml", then "set metarepo under adapters.gitHost.settings". Settings was read-only ("changed by PR"), and Set up › AI had no adapters section.
- **AI decides couldn't be turned on in a fresh metarepo.** The AI page said "runtime.yaml is at version 2; decide needs version 4. Run the upgrade on Home first", while Home showed no upgrade and `atticus upgrade --check` said "Up to date". The two disagreed at the source: init wrote runtime.yaml at version 2; `upgrade`'s `runtime-v4` step lifts only a file that already sets `decide` (any other file means the same at 1 to 3); and the AI save lifted only a version 3 file, so a version 2 file could be lifted by neither.
- Repo-type detect had no button; a prototype was "typed in its repos.manifest.yaml"; integration patterns had no editor; wikis and intake pointed to `atticus sources add` and `atticus intake add`.

## Decision

1. **Edit, then Propose.** Every setup edit in the app writes one file of the metarepo through the code its command uses: init's, repos discover's, core's manifest writers (`addManifestRepos`, `setManifestField`), runtime.yaml's (`setRuntimeAdapter`), sources add's. Each keeps the file's comments, order and line endings, and checks the whole file with its schema before it writes. Each takes `preview: true`, which writes nothing and answers the lines it would change, so the page shows the diff before Write it. Then the page offers Propose for review (scope `org-pack`), with its own Yes and confirmation (ADR 0183, 0186). Writing the metarepo's own file is local: it needs no confirmation.
2. **Create the metarepo here.** `/api/health` says whether the folder is a metarepo. When it isn't, the app shows Create the metarepo here (name and platform suggested from the folder's name, owner, the metarepo's repo on the Git host read from the clone's origin) and runs `initCommand` itself, or Open another folder, which starts the app for that folder on a free port and goes there. Home then continues with Onboarding.
3. **Add repos in the app.** Pasted clone URLs (one a line, up to 500) or a folder of clones (repos discover's own code, as a dry run) become a list: each URL normalised (credentials and a browser link's query taken out, quotes and angle brackets dropped; an ssh user kept), the id `repo add` gives it, a clone URL the manifests list already left out, and a taken id made its own with `-2` saying why (as discover does since round 50). The person ticks, may say what each is (verified, theirs), previews and writes. Each repo row has Detect the type: the org pack's repo types (`repo-type detect`) when it has any, else what the files say (repo add's detection); the type, `prototype` included, is set through the same preview.
4. **The outside systems.** An Adapters panel (Set up › AI and Settings) sets the Git host, work tracker, service desk, notifications, wiki and design tool: only the types runtime.yaml's schema takes (`mock` is not offered), the settings Atticus reads for each (the metarepo's repo, protected branches and default branch for the Git host; project and id pattern for the work tracker; a request number pattern; an export folder), and any further setting a plugin reads as `name: value`. Manual is first and the default for a fresh metarepo, matching the owner's "ADO and ServiceNow may not be API-accessible: show manual instructions". No secret goes through it: the schema refuses a setting named like one, and the route refuses a value shaped like a token or key. There is no route that keeps an adapter's token: the AI tab's key route keeps only a model's key (ADR 0186 item 5), and a Git token kept there could then be named as a model's key. So the panel names the terminal command, `atticus secret set <NAME>`, for the token only.
5. **Settings is edited, not read-only.** Settings says "Edit, then Propose". What has a form is edited through it (the AI tab, the adapters, repos, patterns, wikis). Anything else has Edit in app: the raw editor (the artifact editor's pattern) of an org-pack file, checked with the file's schema (`orgPackFileSchema`: runtime, sources, gates, change types, test strategy, pack, roles, conventions, patterns, manifests, profiles, procedures, service-desk templates, checklists, agents, repo types; other YAML must parse), written only onto the file as opened. The raw editor opens only paths inside the org pack. A runtime.yaml edit that moves where the model's key goes needs the `ai-model` confirmation, as the AI tab's save does, and the address becomes the confirmed one.
6. **AI decides in a fresh metarepo.** `init` writes runtime.yaml at the current version (4) and the Git host as `manual`, with the metarepo's id when given or read from the origin of the clone it runs in (`metarepoIdFromUrl`: the repo after `_git/`, `owner/name` on GitHub, GitLab and Bitbucket, a path's folder name). Turning AI decides on lifts a file of any older version to 4 by upgrade's own step (`migrateRuntimeV4Text` once decide is set), so the AI page and `upgrade --check` agree by construction. The AI page also shows the upgrade offer when a `runtime-` step is pending, from the same check.
7. **Forms where the schema is simple.** An integration pattern (`patterns/<code>.yaml`, a code there already is refused and edited raw instead) and a wiki (`sources add`'s code: its checks, its id, its relative path) have forms on Set up › Org pack; intake already has Add files on Knowledge › Documents. The empty states that sent a person to a command or a YAML file now name the page.

## Consequences

- From an empty folder to a first hand-off is clicks: Create the metarepo, paste the clone URLs, the Git host's metarepo id (prefilled from the origin), Propose for review, and on a change ready for it, Raise hand-off, whose PR on a manual Git host is a step on Home. Journey 29 walks it, with an accessibility check on each new screen.
- The CLI path stays and the guides put it behind the app's. `atticus init` in a terminal also writes the manual Git host, so its first hand-off needs no YAML edit either.
- A metarepo made before this keeps its version 2 runtime.yaml; it means the same, and the first save of AI decides lifts it.
- Opening another folder starts a second server in the same process; it stops with the first. Each server has its own token and page key, so the other folder's page asks its own server for every confirmation.
- Not done here: making Propose for review work in a repository with no commit at all (the host's repo is expected to have its `main`), and a schema of each live adapter's own settings, which belongs to its plugin.
