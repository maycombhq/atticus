# 0111. Checks that tie each value to its source (C5, C6, stage files)

- Status: accepted (pending review by the product owner)
- Date: 2026-10-23
- Builds on: ADR 0074 (every fact cites its code), 0075 (scan settings), 0083 (the knowledge scan), 0087 (flow deltas), 0095 (target flows beside today's), 0101 (what a change needs), 0103 (quotes forgiven only what a model adds)

## Context

Atticus checks that an anchor is real: a cited line exists, a quote is on its page word for word, an id is in the catalog. It did not check that the value written beside the anchor is what the anchor says. A knowledge item could quote one true sentence and carry a lead time from another section. A need could quote "the". A scan settings file could exclude `src/**` citing any line, or set a prefix that differs from the value it cites. An empty survey answer, the cheapest one, always passed. A call-out could name an endpoint the callee doesn't have. A target flow addressed today's steps by position, so a spec drafted again silently re-targeted it. A critic finding passed with a line number and no quote.

## Decision

Every value a step writes is tied to the words it cites, by a deterministic check. What fails goes back to the model as a problem, like the existing quote checks.

1. **Knowledge items (scan and find).** Text is folded to tokens: lower case; runs of letters or digits; an ordinal is its number; the number words zero to twenty, the tens to ninety, and a tens-unit pair ("twenty-one") are digits; minute, hour, day, week, month and year lose a plural "s". Nothing else is forgiven: "working days" is not "business days", and "days" is not "working days". Then:
   - `lead_time`: each token, apart from filler words (a, the, within, about, up to, at least, allow and the like), is in one of the item's quotes (its source quote and its `also_on` quotes).
   - `handled_by`, `owned_by`: the name's tokens are a run in one quote, or the name is the page's own front-matter `owner`.
   - `dates`: each `YYYY-MM-DD` is in a quote as written, or as its day, month name (or its first three letters) and year in any order.
   - `status`: a quote holds a word for it: mandated (must, shall, required, mandatory, always, only, every), banned (banned, never, must not, may not, cannot, not allowed, prohibited, do not, no), retiring (retiring, deprecated, sunset, decommissioned, switched off, phased out, end of life, withdrawn, replaced).
   - `rules`, `applies_when`, `inputs`, `steps` are the model's summary, so their words aren't checked; each number they state is on one of the item's pages.
     When the sentence that states a value isn't the source quote, the model adds it under `also_on`, which may name the same page. The bench reference does this for its three lead times stated in their own section.
2. **Needs.** A need's `because` quote has at least 12 letters and at least one word of three or more letters that isn't a stop word. Its `when` is worked out from the item's lead time where it reads as a duration: 20 working days or more is needed before design, 5 or more before build, less before release (a week is 5 working days, a month 21, calendar days count five in seven). Without one, the model's word stands. The stories stage's requests get the same.
3. **Scan settings** (checked whenever settings are read: the survey, scan verify's fixes and every scan):
   - An exclude's cited file is inside the excluded paths, or its cited line names the folder (the glob's longest literal segment).
   - An exclude is refused when it leaves out more than half the repo's code files (by extension, build output aside), or every code file of the repo's main source folder (the one top-level folder holding more code than any other), unless the cited file is a build or config file (by extension or name) whose cited line names the folder.
   - A prefix is the value on its line with one slash in front and none at the end, a URL's path, or a placeholder's default (`${NAME:/default}`).
   - An answer with every list empty and no question passes only when the built-in readers find no entry point and no call without a host, or when it says why under `nothing_to_set` with the lines read for it, each checked to exist. `nothing_to_set` is part of the survey's answer, not of the settings file.
4. **Target flows.** A call's `to.entry` is resolved against the catalog's endpoints of the target component (or of every component of a target system), when the catalog has any: an entry without `new` must exist; `new: true` on an entry that exists is refused. `store.new` on a table the catalog has is refused. A read or lookup names columns the table has, or that a write in the same change adds with a type. Each target-flow file records `base.steps`, the sha-256 of today's flow's steps (kind, what, to, store, in order; citations left out), when Atticus writes it; the assistant never sets it. The merge says "today's flow changed since this target was written" when it differs, and the stage's check blocks such a delta. The flow delta gets its own version, `FLOW_DELTA_SCHEMA_VERSION` 2; version 1 files still read, carry no base and are flagged as not pinned. The other stage files stay at version 1; they didn't change.
5. **Critic evidence.** An evidence entry needs a quote of at least 12 characters on the line it cites; a quote on another line counts only when it is on exactly one line of the file. A line number alone no longer passes. The prompt already asked for the quote, so recordings are unchanged.

## Consequences

- A value a model brings from another section, page or its own knowledge goes back with the words to quote. Lead times, owners, dates and statuses in the catalog of knowledge each rest on quoted words.
- The rules are exact on purpose; a page that states a value in words the folding doesn't cover ("a fortnight") needs the model to quote it as written. That is handed back, never guessed.
- `nothing_to_set` is a claim with lines, not a proof: a person still reads the survey's pull request.
- A merge still draws a stale target flow (so the picture shows), with the problem beside it; re-running the architecture stage re-pins it.
- The thresholds (half the code, 20 and 5 working days) are constants in the code for now; moving them to the org pack is a C6 change for a later ADR.

## Addendum (2026-10-23): what a live run with Copilot found

A small change on NadiEngine ("show when a chat was last renamed") was planned through the fast path with Copilot's GPT-4o mini, the weakest model a Copilot user may have. Its first plan passed every check and was wrong: it returned a renamed time it never stored. What changed:

- **Checks that catch what was left out.** A field a changed step newly returns must come from a step of the flow (received, read, written, sent, worked out, or returned by a call or lookup) or be a column of a table the flow uses (`delta.field-from-nowhere`). A write that sends a field it stores in no column is handed back (`delta.sent-not-stored`). A read, lookup or write names its table under `store`, never a component under `to` (`delta.to-on-store-step`).
- **Values checked against the catalog and the org pack.** A column added in other casing than the table's own (`updatedAt` for `updated_at`, `delta.column-name`); a classification that isn't one of the org pack's levels (`delta.bad-classification`); a migration named as the store's Flyway migrations aren't, with the next number given (`delta.bad-migration`).
- **Hand-backs a small model can act on.** An endpoint named as a flow is told the flow it starts; a table named as a component is told the `store` form; an entry written `METHOD /path` is told to write the method; the entries listed are the nearest to the path written, not the first eight. The prompts show a concrete `GET /orders/{id}` and say which steps take `to` and which `store`.
- **No rewriting of a draft.** A citation of a data block (`atticus-data:brief.md:5`) is read as that block's file, since the id is Atticus's own. Every other mistake is handed back for the model to fix: a first version that rewrote drafts to what Atticus thought they meant (a table under `to`, an endpoint as a flow, a column's casing, one classification level for every column) was taken out the same night. Judgments about meaning belong to the model, checked against the catalog, not to patterns in code (the product owner's direction; a judge step and stored judgments come next).
- **Questions only a person can answer.** A draft's question that cites no file and line is left out, and said. A reference error (a read of a flow that isn't there, something marked new that exists, the wrong repo, a missing type, migration or columns) is the draft's to fix, never a person's question. A column's classification is a person's decision: the question asks it plainly ("How is the new column renamedAt of nadiengine-db.chat classified?") with the org pack's levels as its choices. Each question is filed under its own repo.
- **A lost hand-off.** A stage run again while its run waits offers that run again (`--handoff` names it); a stage whose waiting run is gone drafts again, and one whose answer was checked but never read in reads it in.

The first plan's gap is the kind every model makes; a stronger model is held to the same checks and needs fewer rounds.

## Addendum (2026-10-24): the facts a table's steps need, given before the first draft, and a new table defined once

A live run of the architecture stage with headless Claude Code, on a chat app whose change adds a table, stopped after three drafts. The fixtures retell it on Forge (`fixtures/stages/pin-table/`): "pin an order note" adds `forge-orders-db.order_pin`. Each draft failed the same store checks: a column without a type, no migration, a field sent and stored nowhere, a classification of "personal" when the org pack's levels are public, internal, confidential and restricted, and a migration named "a new migration creating chat_pin". The checks were right. The model hadn't been given the facts: the prompt carried the format and the estate, but not the org pack's levels, the store's migrations or its types. And every flow change that touched the new table marked it `new: true`, so each one had to restate the table's types, classification, migration and retention. Each draft got one of them wrong somewhere.

1. **The facts are in the step's own prompt, from the first draft.** The architecture and fast-path formats add these rules, in Atticus's words: mark a table new only on the step that creates it; classify each added column as one of the org pack's levels (listed), written exactly; give each added column its type as the store's columns are written, and name its migration as the store's migrations are named; every field a write sends is a column it stores or a key under `fields.checks`. A `store-facts` data block (`storeFacts`, `storesFor`) covers the stores the change may write: those of the touched flows' tables and those owned by a component in a touched repo, at most five. For each it gives the repo, the migrations' folder, at most three file names (newest first), the next free name (`V4__<what_it_does>.sql`), and the column types its tables use. These are facts from the catalog's Migration and Column records. A store's numbering is read off its own file names (a prefix, a number, a separator, words, an extension), not from a tool's convention.
2. **Hand-backs say what is allowed.** A bad migration name gets the next free name in the store's numbering and its folder; a name in words gets `<what_it_does>` with an example. A missing migration gets the next free name. A column without a type gets the store's column types. A bad classification lists the levels and says to write one exactly.
3. **A new table is defined once.** The first step that marks a table the catalog lacks `new: true` defines it: its columns, types, classification, migration and retention. Every other step of the change that writes or reads it names the table without `new`, and only the columns it uses. It inherits the rest, and the checks read the definition from that one step. A column it uses that the definition lacks is handed back, naming the creating step (`delta.unknown-column`). Two or more steps that mark it new are one drafting finding naming each (`delta.table-new-twice`). What belongs to a table is one finding for the table, whatever the number of flow changes: its types (`delta.no-type`), its classification (`delta.no-classification`, a person's question), its migration (`delta.no-migration`) and its retention (`delta.no-retention`, a person's question). For a table the catalog has, the columns a change adds are gathered over every step, and a type or classification given on any step counts.
4. **Every classification is checked.** In the run, `pinned_by: personal` was flagged in one draft and not in the next. The check sat inside two branches that skipped it: a delta for a flow the specs don't have (`delta.unknown-flow` skipped all its steps), and a store step marked new on a table the catalog has (`delta.table-exists` skipped the rest). It now runs on every step's `store.classification`, wherever it is written: the defining step, a restatement, a removed step, or a delta whose flow is unknown.

No contract changes: the flow delta's shape is unchanged (`FLOW_DELTA_SCHEMA_VERSION` stays 2). The rules and the facts are prompt text, and the checks' rule ids gain `delta.table-new-twice`.

## Addendum (2026-10-24, later): what the live rerun found

The rerun of the same change confirmed the fixes above. It found five more.

1. **data.md and design.md read the table's one definition (R1).** `dataChanges` walked the deltas in flow order. A block that used the new table without `new`, in a flow that sorts before the flow that creates the table, got the catalog's columns for it. The catalog has none, so data.md listed every column as "add column", with no migration, above the "new table" row. The critic then raised false findings that a data change has no migration, and the design gate closed. Now `tableDefinitions` collects every table the change marks new before anything is rendered or checked. `checkDeltas`, data.md and design.md all read the same definition. A block on a defined table is a use of it, never added columns. Where several blocks still mark a table new, the definition is the block carrying a migration, then the one with the most columns, then the first in flow order.
2. **Schema problems in plain words, with file and line (R2).** A target flow with an empty `sends:` was reported as zod's "steps.2.fields.sends: Invalid input: expected array, received null", with the file and no line. `schemaProblems` now writes each issue as "target-flows/x.yaml:14: step 2's fields.sends is empty: write a list, such as [orderId], or leave sends out." The line is the node's, or its key's for an empty value, read off the YAML syntax tree. The words come from the issue's code and the value written there. The model's answer gets the same, with "In your answer at line N".
3. **A field sent under another name says which column it is (R3).** A write sent `id`, a path parameter that is the chat id, while `checks` listed `chat_id`. The hand-back told the model to name `id` under checks, which holds column names. Atticus doesn't guess the mapping from the words. The delta says it, in one additive field: `fields.as: { id: chat_id }` (optional, a map from a sent field to the column it is stored as or matches rows by; the flow delta stays at version 2). The check accepts a sent field that is a column, a check, a reads, from or to entry, or one `as` maps to a column the step stores, matches by, or the table has. The hand-back says exactly that, and the format and rules show `as`. The field stays in the delta: a merged flow step's data keeps only the lists.
4. **The migration example uses the table's SQL name (R4).** The example name was built from the catalog id (`create_chat-pin`). `sqlNameOf` takes the catalog record's `name`. For a table the catalog doesn't have yet, it takes the id's last part with hyphens as underscores (`create_chat_pin`). It is an example only: the next free number is the fact.
5. **The privacy line reads the change's own data definitions (R5).** `atticus change status` said "no personal data touched" for a change that adds a column classified confidential. The footprint read only the catalog's columns, and the change policy's default personal classifications (personal, pii, sensitive-personal, special-category) are none of the org pack's levels. Now the footprint also reads each target flow's `store.classification`. `personalLevels` decides which levels count. It takes the change policy's `privacy.classifications` when the org wrote them in its own levels (one of them is a level in pack.yaml). Otherwise it takes that list plus the pack's levels above internal (with the built-in four, confidential and restricted). The status line names the levels and where they came from, and `PrivacyImpact.counted` (additive) carries them. A catalog column classified above internal now counts as personal under the default policy too, which can raise a change's risk.

## Addendum (2026-10-24, pin a message): the order of a flow's steps, and a table's foreign keys

A live run on a real metarepo (a chat app; the change pins a message) found two more. The fixtures retell them on Forge (`fixtures/stages/pin-table/drafts/order-by-name*.yaml`, `keys.yaml`, `checklists/design-review.yaml`; `packages/planner/test/pin-message.test.ts`).

1. **The critic worked out the order of the steps from `after` (S3).** A blocking finding said "respond is placed after 5, the same position as the author lookup, so nothing makes sure the author is looked up first". The merge (`mergeDelta`) keeps adds with the same `after` in the order they are written, and a new flow's steps in file order. The lookup was the step before the respond, so the finding was false.
   - **The lenses read the merged target flow.** The architecture stage and the fast path give the critic's lenses a `target-flows-merged` data block (`mergedFlowsText`, `MERGED_FLOWS`, `StageSpec.reviewSources`). It numbers each flow's steps in their final order and marks each as same, added, changed or removed, with the delta step it comes from, what it stores, its fields, and the keys the change declares. The lens instructions say to read the order from it, never from `after`. It is data, kept above the estate in the lens's pack.
   - **The order is checked as a fact (`delta.returned-before-given`, drafting).** Every field that an added or changed respond step newly returns, or an added or changed call-out or publish newly sends, has a source earlier in the merged order. A source is the trigger's input (its entry's path parameters, the entry step's fields), a read, a lookup, or an earlier step's fields or store. A field that a later step gives is handed back with both step numbers. In a new flow, a field that no step gives is handed back too. In a changed flow that case is left to `delta.field-from-nowhere`, because today's flow may carry a field in a step that no list names. The architecture format says that adds with the same `after` run in the order they are written.
2. **A store block couldn't declare a foreign key (S4).** The critic asked about cascades and references three times, and a person could answer only in a step's `why`. The store block gains `keys`: `{ <column>: { references: <db>.<table>.<column>, onDelete: set-null | cascade | restrict | no-action } }` (`StoreKey`, `ON_DELETE`). It is optional and additive. It goes on the table's one definition, or, for a table the catalog has, on the step that adds the column. It is checked as facts, and each failure is a drafting finding:
   - keys on a step that uses a new table without defining it belong on the definition (`delta.key-not-on-definition`);
   - the keyed column is one of the table's (`delta.key-unknown-column`);
   - the referenced table is in the catalog or defined by this change, and its column is in the catalog, in the definition, or added by this change with a type (`delta.key-unknown-reference`).

   data.md lists the keys under `## Keys`. The architecture and fast-path formats show `keys`, and a store rule says when to give them. The lenses get them in the merged block, so they stop asking.

3. **No version bump.** `keys` is optional and additive, like `fields.as` before it, so `FLOW_DELTA_SCHEMA_VERSION` stays 2. A version-2 file without keys reads as before, and a reader that ignores keys loses nothing it had. The planner's merged step gains `store.keys` and `change`. The API's `MergedStep` (C4) is unchanged and drops them, so the Flows screen doesn't show keys yet.
