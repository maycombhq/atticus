# 0166. The editors catch up with beta.11: Another repo… in their own pickers, the contract check's count, notes as commands, counts to paste, and the viewer's keys

- Status: accepted (pending review by the product owner)
- Date: 2026-11-01
- Builds on: ADR 0105 addendum 2 (an action per job, the parity table), ADR 0159 (IntelliJ catches up with beta.10), ADR 0161 (how the editors took `map --all`), ADR 0162 (answers that carry: "Another repo…"), ADR 0163 (org notes per repo type), ADR 0164 (a contract check on every link), F10 (one diagram viewer, `doctor --counts`)

## Context

2.0.0-beta.11 added to the command line and the app: a target question's "Another repo…" (and a topics question's "A topic owned by another team or vendor"), which opens a picker of every manifest repo, profile system and roles.yaml team and answers with `atticus questions answer <id> --target <id>`, adding a new system with `--add-system vendor|internal`; `atticus join contracts` and Map › Mismatches; `atticus repo-type note` and `repo-type rules --save`; `atticus doctor --counts`; and one diagram viewer with keys (F, /, Esc and the rest). The app has all of it, and both editors embed the app. Their own question pickers did not: picking "Another repo…" there sent `--option <n>`, and the command line refused it with a message, because the option names nothing. Neither editor had a command for the contract check, the notes or the counts.

The app reads the picker from the local API (`GET /api/questions/{id}/targets`). VS Code can reach the API; the IntelliJ plugin runs only the command line, and the command line printed the picker only as lines on an error.

## Decision

1. **The picker comes from the command line.** `atticus questions show <id> --json`, on an open target or topics question, adds `picks`: the same list as the API's `TargetPickList` (repos read or not, systems with their boundary, teams, a team with no system carrying `adds`). Additive output, no contract change; any other question has no `picks`. Both editors read it, so they list what the app lists. An `atticus` without it is said plainly ("it needs 2.0.0-beta.11"), with the command to type.
2. **Another repo… opens the editor's own picker.** In VS Code's answer quick pick and IntelliJ's Answer dialog, the option that opens the picker no longer answers: it opens a searchable list of the picks (a topics question lists systems and teams only, since a repo's own facts say what it publishes) and a name may be typed. A repo, a system, or a team with a system answers with `--target <id>`. A team with no system, or a name the list doesn't have, is a new system for the profile: the editor says what it would add and shows the exact command, and runs `--target <name> --add-system vendor|internal` only when the person picks one of the two (a typed name is offered as a vendor first, another team's system second). A rule (`--match`) still goes with a target answer. The command line checks the target again and writes; the editors decide nothing.
3. **The contract check.** VS Code: Contract mismatches on every link (`join contracts`) opens the check in a read-only tab, with Open in the app for `#/mismatches`. IntelliJ: Contract Mismatches says the counts, shows the whole check and opens Map › Mismatches in the App tab. Neither editor showed the Trust tab's counts, so the count goes where each shows counts already: the status bar, beside the open questions ("3 contract mismatches", said only when there is one), its tooltip with the unconfirmed ones and the links compared, read with `atticus join contracts --json` when the status is read. A read: the B1 rule (the editors run commands only where they already do) holds, as the status bar already runs `next`, `waiting` and `watch`.
4. **Notes and rule drafts, a click and a yes.** A repo type's notes (`repo-type note <type>` or `--org-wide`) and Draft checklist rules from the notes (`repo-type rules`) are read-only and shown whole. Add a note (`--add "..."`, one line, up to 1,000 characters) and Save the drafts (`rules --save`) write files in the org pack, so each shows the command it runs and runs it only on the person's yes; nothing is committed or pushed. The repo types are the org pack's `repo-types/<id>/type.yaml` folders. After the drafts are shown, Save the drafts is a button, never a step taken for the person.
5. **Counts to paste.** `doctor --counts` opens in VS Code's read-only tab with Copy it, and in IntelliJ's panel with Copy: counts and flags only, as the command line prints them.
6. **The viewer's keys in the editors' hosting.** VS Code frames the app in a cross-origin frame inside the webview, so a key pressed while the app has focus is the app's alone: VS Code's webview forwards keys from its own page, not from a frame inside it, and binds nothing to F, / or Esc there. Nothing changes; the README says that VS Code's own shortcuts come back once focus leaves the tab. In IntelliJ the default keymap binds Esc to Focus Editor, and the platform dispatches a key to the keymap before the JCEF browser sees it: Esc in the App tab would move focus to the editor instead of leaving full screen or clearing Find a box. The App tab now takes Esc itself (an action on the browser's component) and hands it to the page as the keydown the viewer listens for, on the element with focus and bubbling to the window. So Esc no longer leaves the App tab for the editor; Shift+Esc still hides the tool window and a click in the editor leaves it. F and / are bound to nothing in the default keymap and reach the page; a keymap or plugin (IdeaVim) that binds a bare letter may take them first, said in the guide.
7. **Parity and versions.** The six new VS Code commands are keys of IntelliJ's parity table, each an action of its own in plugin.xml (`Atticus.ContractMismatches`, `RepoTypeNotes`, `AddNote`, `DraftRules`, `SaveRules`, `DoctorCounts`). The surface census counts 93 palette commands. The VS Code extension is 0.7.9 and the IntelliJ plugin 0.4.0, its change notes in `build.gradle.kts`. The Copilot agents and the Claude plugin name command-line commands, which did not change; regenerating them changed nothing.

## Consequences

- The person answers "Another repo…" where they already answer, in either editor, and a profile change never happens without their yes.
- The status bar runs one more read (`join contracts --json`) each time it reads; the check is a fraction of a second on a 40-repo estate.
- VS Code's extension test that its CHANGELOG names the Atticus it ships with fails until the command line is 2.0.0-beta.11: the release bumps both.
- None of it was clicked through in an IDE when it was written: the VS Code package's tests and typecheck ran, and IntelliJ's `./gradlew test buildPlugin` ran offline against a cached IntelliJ IDEA 2026.2.3. The Esc hand-off and the frame's keys are reasoned from how each editor dispatches keys, and are for a person to check: in IntelliJ, open a diagram in the App tab, F, then Esc, then / and Esc; in VS Code the same in the Atticus tab.
