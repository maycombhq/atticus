# 0203. The stages take work that is no runtime step, a person may accept a stage's finding, and a persona's naysayer is a lens

- Status: accepted (2026-11-18, by the owner, with the recommended answers: whoever accepts a finding may still approve the hand-off, as waivers today, each acceptance listed in the PR; a persona lens never holds a gate in beta.30; rollback is a required undo on every cut-over)
- Date: 2026-11-18
- Release: 2.0.0-beta.30, slices 3, 4 and 6 of [the plan](../plan/v30.md)
- Amends: ADR 0087 (the stage loop's end rule; the stage files), ADR 0201 (point 8: the two rules that end a stage on its first draft)
- Extends: ADR 0011 (findings), ADR 0029 (waivers ride with the hand-off), ADR 0114 (conformance), ADR 0115 (the critic's lenses in a stage), ADR 0189 (point 9, what a change knows), ADR 0201 (personas, the door check, waves in tasks.md)
- Contracts: C3, additive, no bump: a finding's lens may be `persona`, with the persona's name. C4, additive: the local API's next minor (three conformance checks, `persona` on a finding row). C6: the org-flow workflow schema goes from 2 to 3 (words of two artifacts; the existing upgrade step rewrites the generated folder). The stage files (the planner's, not C1 to C6) gain optional keys and one new file. C1, C2, C5 and the facts file are unchanged.

## Context

After slice 1 (ADR 0201) the three kinds of change tried on the Forge estate reach a valid OpenSpec change on the quick path. On the staged path the new product and the migration still stop on their first draft, and the stages are where the map checks the design and conformance checks the build. Three things keep a change off them:

1. A stage's blocking finding can only be fixed or, for a decision, answered. A person who knows the map is behind the truth has no way to say so and go on.
2. A change is flow deltas, and a flow delta is runtime steps. Deployment, pipeline, configuration, secret and route work has no word, so a migration "changes no step" and has nothing to plan.
3. The personas of ADR 0201 ask their questions in the assistant only. The critic asks four fixed questions and can't ask a fifth.

The owner's limit for this ADR: the smallest design that works, one mechanism over many, additive contract changes.

## How it is today

Read in the code on `release/b30`. No code was run.

- **Two kinds of finding.** A stage's own finding is a `StageIssue` (`packages/planner/src/stages/loop.ts:111`), kept as a `LoopFinding` in `stage/<stage>.yaml` (`stages/schema.ts:373`). A critic finding is a C3 `Finding`, one file under `review/<gate>/<round>/` (`packages/core/src/schema/review.ts:305`). Only the second can be waived.
- **A waiver today.** `atticus finding <change> <id> waive --reason …`: refused for an assistant (`packages/naysayer/src/act.ts:218`), for a constitution rule, for a rule that says it can't be waived (`:263`), and without a reason (`:264`). Nothing else limits who waives. The finding's file rides with its gate's hand-off PR, where the Git host's rules decide who approves (ADR 0029, ADR 0073).
- **A second system already projects onto a gate.** Conformance turns each item into a C3 finding on the built-in gate `conform` (`packages/taskrun/src/conform.ts:44`, `:174`), written by `writeGateRound` (`packages/testgen/src/rounds.ts:32`), which carries a finding's resolution into the next round. Every folder under `review/` is read as a gate (`packages/naysayer/src/findings.ts:411`), so `atticus finding` and the lenses' "recorded by people" block (`recorded.ts:36`) see it.
- **The end rule.** A stage is done when no blocking finding is open (`loop.ts:1646`: one whose question was answered no longer blocks). A stopped stage run again checks its files before it drafts (`loop.ts:997`). ADR 0201's two rules end it on the first draft (`loop.ts:1392`).
- **What a change knows beside the catalog** is worked out per check: planned components (`stages/planned.ts:57`, ADR 0189), manifest repos (`estate.ts:64`, ADR 0201), outside systems a call fact names (`estate.ts:214`).
- **A change is flow deltas.** The architecture answer is `flows`, `reads`, `deploy` (`stages/architecture.ts:159`). A deploy step is a repo's code or a migration (`stages/schema.ts:363`). Stories are made from deltas only (`stages/stories.ts:481`); with none the stage refuses (`stories.ts:4198`). `feature.nothing-placed` (`feature.ts:269`) and `small.no-target-flow` (`small.ts:511`) refuse a change with no flow.
- **What the catalog holds of operations:** `Component.runtime`, `Deployment` (env, platform, ingress) and `Setting` (kind, key, a value or a reference, never a secret) (`packages/core/src/schema/kinds.ts:59`, `:271`, `:300`). No stage reads them. Conformance compares calls, publishes, tables, columns, migrations, triggers and endpoints only (`packages/core/src/api.ts:3880`).
- **Lenses.** `Lens` is the four questions and seven old names (`review.ts:40`); a finding's `lens` is one of them (`:315`). The critic runs one lens a question (`packages/naysayer/src/ai.ts:805`), with the agent `lensAgent` finds or builds (`ai.ts:186`), what to look for (`ai.ts:246`) and the question's rules (`ai.ts:337`). A lens's finding is kept only when its quote is on the line it cites.
- **Personas** are Markdown in `org-pack/agents/` with free frontmatter (`packages/cli/src/skills-commands.ts:51`), written out for the assistant. The critic never reads them. `atticus scan review` exists; `atticus review` does not.
- **The archetype tests** (`packages/cli/test/archetypes.test.ts`, on the `b30/tests` branch, not yet on `release/b30`) take the three changes through the quick path, the new event through the staged path to the end of stories, and expect the other two to stop once with the hint.

## Decision

One helper carries most of A and B: **`knownToChange(change, estate)`** in `stages/planned.ts`, the ids a change may name that the catalog doesn't hold, each with its standing: `planned` (ADR 0189), `not read` (a manifest repo, ADR 0201), `outside` (declared, B.7) or `accepted` (A.4, with who and why). `unreadConsumer` and the checks that ask "is this id known" read it. A stage file that names such an id says its standing beside it.

### A. A person may accept a stage's finding (about 250 lines)

1. **The bridge is a gate per stage.** When a stage's run ends, in any state, its blocking findings of source `stage` in the current draft are written as C3 findings on the built-in gate `stage-<stage>` (`stage-feature`, `stage-architecture`, `stage-stories`, `stage-small`), with `writeGateRound`, as conformance does. Critic findings are not projected; they are C3 already.
2. **The projected finding:** id `stage-<fingerprint>` (the loop's 12 hex, so it keeps its id and its resolution across drafts); `rule` the stage rule; `layer: org`; `lens: true` for `feature.*`, `delta.*`, `operation.*`, `small.*`, and `complete` for `stories.*`; `severity: blocking`; `artifact` the stage's source file; `locator` the line `spec.locate` gives, else the target as a heading, plus `record` when the rule is about one id; `summary` the message's first 200 characters, `why` the whole message; `evidence` the issue's `path:line`, else the source file; `fix.text` "Fix <file> and run <stage command> again." and, when acceptable, "Or accept it: atticus finding <change> <id> waive --reason "<why>"."; `waivable` by point 3.
3. **Which rules.** `ACCEPTABLE_STAGE_RULES` in `stages/finding-kind.ts`, a fixed list, not configuration (rule 6). A rule is on it only when a person can know better than the map and the next stage can still do its work. A critic finding of a constitution rule is as before: never.

4. **Who.** As a waiver today: a person, never an assistant; a name (`--by`, else Git's) and a reason. No new approval rule: the acceptance is a file in the phase's hand-off PR, and the Git host decides who approves that. A refusal of a rule not on the list says the row's way on.
5. **Recorded** in the finding's file (`state: waived`, `resolution.by`, `at`, `reason`), nowhere else; the loop reads it there. `review/stage-<stage>/` rides with the stage's hand-off, and `phaseFindingGates` leaves these gates out: the stage's own state already holds its phase. **Shown** by `atticus findings`, by `atticus change status` ("1 finding accepted at the architecture stage: <rule>, by <who>"), in the hand-off PR's body (one line each: rule, who, why), in the stage's thread (ADR 0189, with Accept on an acceptable finding), and in the stage's files as the table says.
6. **ADR 0087's end rule becomes:** a stage is done when no blocking finding is open and no question it raised is open, where a finding is not open once a person answered its question **or accepted it**. An accepted finding is never handed back as something to fix (the drafter gets it as data, "accepted by people"), never counts toward three drafts in a row, and its open question, if it has one, is answered with the acceptance's words. A stopped stage run again after an acceptance checks its files and, when nothing else blocks, runs its critic round and is done with no new draft. If the finding's target or evidence changes, its fingerprint does, and it is a new finding.

### B. Work that is no runtime step (about 700 lines)

1. **One list, `operations`,** in one new file, `target-flows/_operations.yaml` (no flow id can start with `_`; it is under the architecture stage's source, so a person's edit of it is their draft, ADR 0087). The planner's schema, version 1:

```yaml
schemaVersion: 1
change: move-orders-platform
waves: # optional; without it every repo is in wave 1
  - { repos: [forge-orders], why: The pilot. }
  - { repos: [forge-ledger, forge-billing] }
operations:
  - id: deploy-new
    kind: deployment # deployment | pipeline | config | secret | route | cut-over
    repos: [forge-orders, forge-ledger, forge-billing] # one operation, N repos
    what: Deploy the service on the new platform beside the old one.
    today: [forge-orders.deployment.prod] # optional: catalog ids of what is there now
    sets: { platform: forge-cloud, env: prod } # optional: what a rescan can find (point 6)
    after: [] # optional: operation ids
  - id: switch
    kind: cut-over
    repos: [forge-orders, forge-ledger, forge-billing]
    what: Point the gateway route at the new deployment.
    after: [deploy-new]
    undo: Point the route back; the old deployment stays up for one release.
```

2. **Rollback is not a kind.** Every `cut-over` gives `undo`; any operation may. `design.md`'s "Rollout and rollback" table gains a row an operation with `undo`. A `secret` names the key and where its value is kept, never the value.
3. **Each stage.**
   - _Feature:_ `feature.yaml` gains optional `operations: [{ kind, repos, what, why, newRepo? }]` and `outside` (point 7). `feature.nothing-placed` counts operations. An operation's repo is checked as a new flow's is (ADR 0201).
   - _Architecture:_ the answer gains `operations` and `waves`; Atticus writes the file. Checks, all blocking, in a new `stages/operations.ts`: `operation.unknown-repo`; `operation.unknown-today` (an id under `today` is no Component, Deployment, Setting, GatewayRoute or Endpoint record of a named repo); `operation.no-undo` (a cut-over without one); `operation.after` (an unknown id, or a circle); `operation.wave` (waves are given and a repo is in none or in two); `operation.missing` (an operation the feature lists has none here). A note, `operation.today-uncited`: the catalog has a Deployment for a repo of a `deployment` or `route` operation and `today` cites none; it lists them. `delta.empty` is unchanged.
   - _Small (the fast path):_ its answer takes `operations` too; `small.no-target-flow` is raised only with neither.
4. **Today as evidence.** For the repos in scope the feature and architecture prompts get one more data block, `runs-today`: each component's `runtime`, its Deployment records (env, platform, ingress hosts) and its Setting keys and kinds (not values), each with its id. `design.md` gains "## Operations": a row an operation and repo, with what is there today, cited as the record's own provenance (file and line), and what it becomes.
5. **Deploy order, stories and tasks.**
   - A deploy step may be `{ repo, operation: <id> }` (one more optional key). The existing rules cover it: every operation and repo once (`delta.deploy-missing`), `after` kept and no step of a wave before the last step of the wave before it (`delta.deploy-order`). With no `deploy`, the suggested order is waves first, then `after`, then file order.
   - Stories: one story an operation, one task a repo of it, made without a model as today; the assistant words the story and writes each task's criteria, and `stories.no-criteria` holds. A story of an operation carries `operation` in place of a flow; what reads a flow for today's code passes it by. With operations and no flow delta the stories stage runs.
   - `tasks.md`: each task of wave n ends with `(after <the last tasks of wave n-1>)`, and of an operation with `after` names that operation's task in its repo. This is ADR 0201's wave syntax, so `run-ready` needs nothing new.
   - Spec deltas, with no model: one capability a repo, `<repo>-operations`, a requirement an operation story, a scenario a criterion. `openspec validate --strict` runs as today.
6. **Conformance, said plainly.** When an operation gives `sets`, the rescan of the branch's commit is compared, per repo: `platform` and `env` against a Deployment of the repo's component; `host` against a Deployment's ingress; `key` against a Setting. Found or `conform.missing`, as today (C4: `check` gains `deployment`, `route`, `setting`). **It can't check:** an operation with no `sets`; a pipeline (the catalog has no record for one); a secret's value; a cut-over (an act in a live system, which Atticus never connects to, rule 6); anything kept in a console or in a repo the change doesn't name. Each of those is listed in the conformance result as "not checked: <why>", never as found. What the assistant didn't read into a Deployment or Setting fact is missing here too: the fix is the scan, not the design.
7. **A consumer outside the map.** `feature.yaml` gains optional `outside: [{ id, what, why }]`: a party this change names that no repo of the estate holds (a partner's system such as `northwind-pay`). An id the catalog has is refused (`feature.outside-exists`). A declared id is known as `outside` to every check. A manifest repo nobody read keeps ADR 0201's note. `design.md`'s consumers show each one's standing: read, not read, planned, outside, accepted.

### C. A persona's naysayer as a lens, and `atticus review` (about 300 lines)

1. **Configured in the persona's own file.** A naysayer's frontmatter may give `gates: [design, plan]` (gate ids of `gates.yaml`). With no `gates` key it never runs in the critic; the starters ship without it. No schema changes: the frontmatter is free (ADR 0201). A gate id `gates.yaml` lacks is said in the round's notes.
2. **It runs as one more lens,** after the four, in the same round, through the same code: an agent definition built in memory as the built-in default is (`ai.ts:232`), with the file's name as its id; one rule built in memory, `persona.<name>`, org layer, severity `risk`, whose look-for is the file's body. The output format, the quote rule, the answers and recorded-facts rules and the batching of ADR 0185 are Atticus's and unchanged. The four questions are not reopened: `Lens`, the rules' lenses and a change type's `lenses` stay as they are.
3. **C3, additive.** `Finding.lens` takes one more value, `persona`, and `Finding` gains optional `persona` (the file's name), required with that lens and refused without it. A persona's finding is always a `risk`: shown, handed back to the drafter once (ADR 0087 addendum), never blocking, never a gap.
4. **`atticus review <requirements.md | change> [--no-ai] [--write] [--json]`.** For a change it reads `<change>/requirements.md`. It creates nothing and always exits 0 unless the file can't be read.
   - The door check (ADR 0201 point 2), its three reasons printed as findings, not a refusal.
   - Map checks on every id the file cites: not read ("in the manifest, not read: atticus map <repo>"), planned, and touched by an open change (`change conflicts --touching <id>`).
   - Unless `--no-ai`: every naysayer of the org pack whose `owns` heading the file has, as a lens over the file. A finding without its quote on the cited line is dropped and counted.
   - Each finding prints as `<file>:<line>: <who asks>: <question> [<evidence>]`. The checklist rules of the constitution and the org pack are not run: they need a change's artifacts and type, and run at a gate (`atticus critic`), which the command names for a change.
   - `--write` adds each finding not already there as a row of its role's table (Question, Evidence, Asked by the persona or `atticus`, `-`, `-`, `open`), making the table or the heading when missing, keeping the file's line endings. Nothing else in the file changes. `atticus change new --from` stays the only door that refuses.

## Migration

- **Org-flow 2 to 3:** the upgrade step that is there (`packages/cli/src/upgrade.ts:309`) rewrites the generated folder when the installed version is lower. Nobody edits that folder by hand.
- **Existing changes** need no rewrite. Every new key is optional; a change drafted at beta.28.5 has no operations file, no `outside` and no `stage-*` gate, and reads as it did. A done stage checked again passes with no model call.
- **An older Atticus** refuses a `feature.yaml` with the new keys and a finding with `lens: persona` (both schemas are strict). A metarepo is upgraded as a whole; the upgrade stamp already says which version wrote it.
- **Prompts:** the feature, architecture and stories prompts gain lines, so their hashes change and the recorded replays and the pinned hashes are re-baselined once.
- **The test:** `packages/cli/test/upgrade-b30.test.ts` gains a beta.28.5 metarepo with org-flow 2 and a change done through stories. After `atticus upgrade`: org-flow is 3; every file of the change is byte for byte the same; each stage reads as done with no model call; `change status` says what it said; a second run changes nothing.

## Risks

- **The stories stage** (4,671 lines) assumes a flow behind every story and task. Stories of operations are the largest and least certain part of B; if "passes it by" turns out to touch many places, operation stories get a small renderer of their own beside the delta one, with the same files out.
- **The accept list is a judgement.** A rule wrongly on it lets a later stage meet a case it can't handle; one wrongly off it sends people to the quick path. The per-rule test and field use correct it; the list is one constant.
- **Conformance of operations is thin** and depends on what the scan read into Deployment and Setting facts. The result says "not checked" so that it is never read as proof.
- **A persona lens is one more model call a round** for each naysayer with `gates`, and its look-for is the organisation's words, reviewed like the rest of the org pack. Another team's agents (ADR 0177) are never run as lenses.
- **`atticus review` is a new top-level command;** the surface census changes. Its lens runs have no change folder to be recorded under; where they are kept was not read in the code.
- **Not verified:** no code was run. Which rules block was read from the checks' sources and a few may be notes already; `openspec validate --strict` on a `<repo>-operations` capability was not tried; the size of each part is an estimate from reading.

## Addendum

- 2026-11-19, after the review of part B (beta.30). Point 6, conformance of `sets`, is **not built in beta.30**: `atticus change conform` checks target flows only, and for operations says so in words, with no change to C4: "This change's work is operations (N): Atticus doesn't check operations against the code in this release" for a change whose work is operations only (exit 0), and "N operations are not checked: …" beside the flows' result. `ConformItem.check` keeps its values and no `notChecked` list is added. The comparison and the C4 minor that carries it are left for a later release. Also from the review: one schedule of a change's operation tasks (waves, `after`, each repo's order) is what the stories write, what design.md's suggested deploy order lists and what the architecture stage checks; a plan it can't put in an order is refused (`operation.order`, blocking, not acceptable under part A). A wave with no operation holds nothing back. The stories stage runs the operation checks again. An `undo` is a sentence (not empty, `n/a`, `none`, `-`, `tbd`, or under ten characters). An archived repo is refused for an operation. An operation's requirement in `<repo>-operations` is named `<story title> (<change id>)` and always ADDED, so an archived operation of the same title is never merged into a new one. An operation's words and the `runs-today` block are redacted as a fact's quote is, and `runs-today` in the feature prompt covers the repos the change's files name and its systems hold, not the whole estate.
- 2026-11-19, after the review of parts A and C (beta.30). **What an acceptance covers:** a finding's fingerprint is its rule, target and evidence, so each acceptable rule's target now holds the accepted value: `delta.unknown-component` `<flow>#<n>:<component>`, `delta.unknown-entry` `<flow>#<n>:<component>:<entry>`, `delta.new-folder` `<flow>#<n>:new:<folder>`, `delta.consumer-missing` `<target>:<the consumers left out, sorted>`, `stories.field-not-checked` `<task>:<fields, sorted>`, `stories.shape-uncovered` `<shape file>:<story>`; the others held it already. A check never passes over what its own rule accepted: it raises it again and the acceptance is read off the fingerprint, so it stays on file; an acceptance at one stage counts at another for the same rule and target. An id accepted under one rule is known only as that kind (a consumer, a repo, a call's target). An id accepted under two rules is known as both. A stage's gate carries a finding's state and resolution, and tells a new round from the last, by the finding's id only (`stage-<fingerprint>`: the stage's rule and target) and its words, never by C3's fingerprint, whose summary is the message's first 197 characters and which, for a rule with no record, doesn't hold the target; C3's fingerprint is unchanged. An acceptance counts only where its rule is the finding's, so a finding file edited by hand to give one rule's id another rule accepts nothing. **An archived repo** is its own finding, `feature.archived-repo` or `operation.archived-repo` (a new flow or an operation put in a repo the manifest marks archived, whatever the catalog still holds of it), blocking and not acceptable, never `*.unknown-repo`, and checked again at the architecture and stories stages (with the same rule and target, so a repo archived after the feature stage is refused there; an operation once, as `operation.archived-repo` of the operations file; a target flow of one too, but not one that moves the work out: a flow removed, as the sketch's retire and absorb strokes write, or a modify whose steps are all removed. Anything else there blocks, a step sent to another component included (it is still a change of the archived repo's code, and its tasks are written there), and an empty modify; the work moves by a remove there and a new or changed flow of the repo taking it over, as the finding says); an acceptance of the repo from before it was archived no longer makes it known. **Who:** Atticus's own agents, any `*-critic` and `*-naysayer`, and the org pack's persona files are assistants, never the one who accepts, on every path that reads a resolution (the lenses' recorded facts, the lifecycle's check, the hand-up), not only where a person acts. Atticus's own agents match the whole handle or an email's local part, exactly (`feature-placer@…` is the agent); the org pack's agents, personas and models match the whole handle only, because a persona's name is often a role's and a team mailbox of that name (`security@…`, `qa@…`, `developer@…`, `product-owner@…`) is a person, so a waiver or an acceptance such an address recorded counts as a person's, earlier ones included; the `-critic`/`-naysayer` suffix matches only a handle of one hyphenated word of letters and digits, never an email or a dotted name, so `m.judge@…` and `judge.smith` are people. **A persona lens never holds a gate** (the owner, 2026-11-21, as the status line says; an amendment to C.3 drafted in review was withdrawn): not while it is with the person's assistant, not when it fails (recorded as skipped, with why), not at the lifecycle, the critic's gate status or a stage. Its answer, when it comes (`atticus handoff done`, or a stage run again), is read in as findings: into its own round while that is the gate's newest, else into the newest round, which says so, so a late answer is never lost and nobody waits for it. Its findings are risks, so none blocks. **The `stage-` prefix** is kept for the stages' gates: a `gates.yaml` gate named `stage-<x>` is a problem of the org pack when it is read, no phase's gate, and refused by the critic (gates.yaml's schema, C6, is not changed). `ACCEPTABLE_STAGE_RULES` is in `stages/finding-kind.ts`, as point 3 says.
- 2026-11-22, after the app's half of part A (beta.30). **A hand-off draft that only a person can settle goes to a person at once.** When every blocking finding of a draft handed in with `atticus handoff done` is a rule on `ACCEPTABLE_STAGE_RULES` (at least one; any other blocking finding and it is refused as before, until its self-checks are spent), the draft is handed in on that first check, its findings, blocking or not, are written on the stage's gate `stage-<stage>` at once (an earlier acceptance keeps its file), and `handoff done` names each with its `atticus finding <change> <id> waive` line. The stage then reads it in: what a person accepted meanwhile passes, and if nothing else blocks the stage is done on that one draft; else, in hand-off mode, the stage stops for a person ("stopped after N drafts for a person") instead of handing the draft back, since another draft can't say the map is behind. Accepted, the stage run again checks its files and is done with no new draft (point 6); not accepted, it drafts again with the findings, so the assistant can still hand in a fixed draft instead. The model runtime is unchanged (its drafts get the findings back, as before). **The app goes on after an Accept**, whoever started the stage: once nothing else holds it (no other open blocking finding at the stage, no open question), it runs the stage's step as **Start the next round** does, which keeps the stage's resume for the run it waits on, so the app finishes the run when its answer passes, and checks again at once an answer that failed only on what was just accepted.
