# 0073. The person is the Git user; approving is the pull request (C4, C6)

- Status: accepted (pending review by the product owner)
- Date: 2026-10-20
- Supersedes: ADR 0044 (role views, `.atticus/me.yaml` `view` and `groups`, `PUT /api/me`, approvals from `roles.yaml`); the approval parts of ADR 0047 (only `approvals.catalog-assert` holders may accept the baseline) and ADR 0048 (`GET /api/me/approvals`, reviews in the digest); the role and approval parts of ADR 0029 and ADR 0012 (`roles.yaml`, gate `approvers` and `minApprovals`, change-type `approvals`, `change-policy.yaml` `privacy.role`, `risk.approvals` and `selfApproval`)

## Context

The app gave thirteen roles a view each (a home, a sidebar, a tour), mapped directory groups to roles in `roles.yaml`, and decided in-app approvals from ownership: `roles.yaml` `approvals` for actions outside Git (waivers, the catalog baseline, release go / no-go) and required roles per gate. Every command that recorded a person took `--by <you>`.

The product owner's decision: "Lets remove the roles from ui and approvals... approval process is the pr... and the person is detected from the git user... thats all... we are making it unnecessarily complex for a meta repo local ui."

Atticus runs on one person's machine against a metarepo in Git. The Git host already decides who may approve a pull request (branch protection, CODEOWNERS, required reviews), and the person already has a Git identity. A second approval system inside the app duplicated the Git host's, could disagree with it, and needed a group directory Atticus doesn't have.

## Decision

- **The person is the Git user.** `gitUser(root)` (`@maycombhq/workspace`) reads `git config user.name` and `user.email` in the metarepo, as Git resolves them (the repo's config, then the global one). The handle Atticus records as `by` is the email's local part, else the name, made handle-safe. When Git has no user, the OS user name stands in and Atticus says so, with the two `git config` commands that fix it. It reads files only: no network, no directory.
- **The app** (server `ctx.user`, `/health`, `GET /api/me`) and **every CLI command that took `--by <you>`** default to it. `--by` (and `digest --as`) stay as optional overrides, for scripts and tests. `atticus change new`, `finding`, `baseline`, `todo done`, `task run`, `glossary`, `initiative`, `outcome record` and the rest no longer refuse without `--by`.
- **No roles in the app.** One navigation for everyone, one Home list of what needs a person, one tour. Removed: the view picker, role homes, role navigation and tours, Settings' group-to-role mapping, `PUT /api/me` and `.atticus/me.yaml` `view` and `groups` (an older file that has them still loads; they are ignored and dropped on the next save). The setup checklist loses "Groups are mapped to roles". Lessons keep their audience label, and open questions keep labels such as "(product owner)": these are words, not permissions.
- **No in-app approvals. A gate is approved when its hand-off PR merges.** `atticus change status` names the PR to merge (or says `atticus change handoff <id> --approve` opens it) instead of "Approvals needed: <role>". `change sync` reads the PR: merged on the Git host, the change moves on; approved by someone other than the person who raised it and the host's rules met, it is ready, and `--approve` merges it as the person. The person who raised a PR is never its only approver; who else may approve is the Git host's rule. Removed: approve buttons, "approvals waiting on you", `GET /api/me/approvals`, required roles per gate, separation-of-duties checks by role, the privacy-role blocker, and the role check on accepting the baseline.
- **Waive a finding, accept the catalog baseline, release go / no-go** are recorded metarepo file changes by the Git user that reach main through a pull request: a waiver is written to the finding's file and travels with the gate's hand-off PR; the baseline is `catalog/baseline.yaml`, committed and merged like any file; go / no-go is the release hand-off PR, and merging it is the go. Each command's output says so. Nobody's role is checked; constitution findings still can't be waived (C3).
- **Writes to shared outside systems still need the person's explicit confirmation** (CLAUDE.md rule 6, not configurable). Opening, updating, merging or closing a hand-off PR, filing service-desk requests, syncing work items, sending a digest and running an executor are a dry run until the person adds `--approve` (`--send` for the digest), or presses the button that says exactly what it sends). The approver is the Git user; no role is checked.
- **C6.** `roles.yaml` and the role-based approval fields (`roles.yaml` `approvals`, `mappings`, `separation`; gate `approvers` and `minApprovals`; change-type `approvals`; `change-policy.yaml` `privacy.role`, `risk.approvals`, `selfApproval`) are deprecated: a pack that has them still loads and validates, unchanged (no migration, no schema version bump: nothing is removed from the schemas), and nothing reads them. `atticus init` stops writing `roles.yaml`, and a pack without one isn't reported as using defaults. `ChangeHandoff.approvals[].roles` becomes optional: new entries leave it out, older files keep theirs.
- **C4.** The local API's version goes to 2.0.0: `PUT /api/me` and `GET /api/me/approvals` are gone, `GET /api/me` returns `user`, `name`, `email`, `source` (`git`, `os` or `given`), `warning`, `ai` and `notify`, and the release and governance views lose `releaseApprovers`, `required` and `separation`.

## Consequences

There is one approval system, the Git host's, and the record of who approved is the PR. A person sees the same app as everyone else and never chooses a role. A machine with no Git user works, with a visible warning, and records the OS user name. An organisation that relied on `roles.yaml` approvals moves those rules to branch protection and CODEOWNERS on the metarepo; its `roles.yaml` can stay until the next pack release removes it. A script that passed `--by` keeps working.
