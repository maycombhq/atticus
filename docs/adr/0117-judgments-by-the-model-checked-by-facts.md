# 0117. Judgments by the model, checked by facts (C5, C6)

- Status: accepted (the product owner approved the contract changes, 2026-10-23)
- Date: 2026-10-23
- Builds on: ADR 0074 (the AI reads, every fact cites its code), 0078 (questions as files), 0083 (knowledge items), 0089 (the same question from two steps), 0103 (AI steps that hold with Copilot), 0107 (the context engine), 0111 (checks that tie each value to its source), 0112 (every prompt fits its model)

## Context

An audit of the code (2026-10-23) found Atticus deciding questions of meaning with word overlap, word lists and regexes: two questions were "the same" when their words overlapped by seven in ten, so a person's classification of `renamedAt` was read for `renamedBy`; a criterion "named" a field when the field's letters were in it (`id` in "valid"); a lead time of "3 days" was "in" the quote "3 approvers and take 15 days"; a status was "stated" by any "no"; a process applied to a step that shared two words with it; an answer "relied on" a gap whose name it mentioned to leave it out. Each rule fails in both directions, and each failure was patched with another rule.

The product owner's direction: deterministic steps fail at meaning; be agentic, accurate and precise. Keep deterministic code for what a person could settle by pointing at something (a quote is on the cited line, an id exists, a file parses) and for the injection defences, which a model the content could steer must never replace.

## Decision

1. **A judgment is a closed question to the model** (`judge()`, packages/ai, C5): one question per kind, the answer one word of a closed set or "unsure", never free prose. Every quote the judge gives is checked word for word against the text it names; an answer whose quote isn't there, or whose word isn't in the set, is asked once more, then counts as unsure. Unsure is never a guess: the caller raises a question, or hands the item back. Catalog facts veto first and override the model; a vetoed item is never sent. The kinds:
   - `same-question`: same, narrower or different. Veto: the two name different ids, fields, paths or numbers (each names one the other doesn't).
   - `covers-field`: does a criterion's then clause assert a field's value? yes or no.
   - `states-value`: does a span from the page state a value? yes or no.
   - `applies`: does a process's applies-when hold for a step, given its catalog facts? yes or no.
2. **Judgments are kept** (core, `judgments/<kind>/<key>.yaml`, or `.atticus/judgments/` when adopted), committed for review as `questions/` are. The key is 24 hex characters of the sha256 of the kind and the inputs in canonical form, so the same inputs read the stored verdict and the model isn't called (rule 4), and a changed input asks again for its own judgment only. Each file holds the verdict, a normalised value when there is one, the quotes, why, the inputs, who confirmed it (`check` with its rule, `ai` with the run id, or `person`) and, when a person overrode it, what it replaced. A person's verdict is never replaced by a model's or a check's. The interface is small so other steps keep their judgments there too (the context engine's query expansion and rerank): `judgmentKey(kind, inputs)`, a `JudgmentStore` with `get(kind, key)` and `put(judgment)`, `fileJudgments(root)` and `memoryJudgments()`, `makeJudgment(...)` and `overrideJudgment(store, kind, key, {...})`. Judgment is a C5 file with its own JSON Schema (`ai/Judgment.json`), version 1.
3. **Hand-off or batched: batched into the step's own prompt wherever it can be, because a hand-off round costs the person a prompt.** `judge()` runs through the AI runtime like any step, so it can be handed off and resumed: with the hand-off runtime its run waits, and calling it again with `resume` once `atticus handoff done` checked the run reads the verdicts in and stores them (tested). But no step hands a judgment off on its own: each takes the cheaper way.
   - Questions: the step's prompt lists the questions on file with their ids, and the step says of a question it would raise which one it is (`sameAs: { id, verdict: same | narrower, quote }`). Atticus checks the id is a candidate, the quote is in that question and the veto, and keeps the reading as a judgment confirmed by the step's run. Where the runtime calls a model directly, the pairs left open go to the judge in one call. With neither, a question is raised beside the earlier one (`related`, unsure): a person sees both.
   - Criteria: the story writer says which fields each criterion checks (`checks`). A field written in the then clause is a fact; one that isn't goes to the judge where a model can be called, and is handed back to the writer with a hand-off ("name it in its then clause").
   - Requests: the story writer names each process a step meets, quoting its applies-when (checked word for word). Where a model can be called, the judge also asks of every other step and process whether it applies, a recall check.
   - Knowledge values: the scan cites the words for each value; with a hand-off a value must be the page's words and a reading (a status, a normalised lead time) is kept as the scan model's, with its run.
   - Gaps: the answer lists the gaps it relies on (`relies_on_gaps`), checked against the gaps it was given. No judgment is needed.
4. **Questions are matched in four steps** (`raiseQuestions`): the exact id; candidates (the same repo, not retired, another step's or an answered one, citing a file or naming an id in common); the veto; then the step's reading, a stored judgment or the judge. Same reuses the earlier question (`alsoAskedBy`); narrower or unsure raises the new one with the earlier under `related`. **A person's answer is never read for a question about more than it answered**: an answered question is reused only when the new one names no id it doesn't, so a column's classification is never reused for another column, and never without a person having seen the question it answers. `sameQuestion` is deleted.
5. **Criteria declare what they check.** A criterion is `{ text, checks: [fields] }` (a bare string reads as checking nothing). Each field of a task must be under some criterion's checks, and checks name only the task's fields: set checks on structured data. `namesField` is deleted.
6. **Knowledge values cite their words** (ADR 0111 sharpened). An item gives `lead_time_quote`, `status_quote` and `date_quotes.<name>`, each checked on its page. A check settles a lead time or owner written as one run of the span's tokens (numbers folded from words), and a date written as it is or as one run of day, month and year. Everything else is a claim: a lead time whose numbers are in its own span, a date in its own span, every status, and the scan's normalised lead time `lead_time_days: { min, max, unit }` (refused when its words give other numbers). Claims are judged where a model can be called; with a hand-off, values are refused and readings kept as the model's. `STANCE_WORDS` is deleted.
7. **One reading of a lead time.** The normalised lead time is kept as a judgment (`judgments/lead-time/`, keyed by the item and its lead time's words, so a changed lead time on the page is a new reading). `atticus change needs` takes a need's phase from it with one piece of arithmetic (`workingDays`: the upper bound, calendar days as five in seven, hours as eight a day) and the thresholds of ADR 0111, and copies it onto the need (`leadTimeDays`); the next-step list sorts by it. The words are never parsed: `leadTimeDays` in needs.ts and the next-step list's regex are deleted. The initiative planner's `Party.typicalLeadTimes` stays a format ("10d", "2w"), parsed as one.
8. **Contract changes.**
   - C5: the Judgment file (version 1), `judge()` and the judgment kinds.
   - C6: questions at schema version 2: `related` on a question and `sameAs` on a draft, both optional; version-1 files read as version 2, and `atticus upgrade` (`questions-v2`) rewrites them.
   - The stage answers the model writes: criteria with `checks`, requests with `quote`, `relies_on_gaps`; the knowledge scan's item: `lead_time_quote`, `lead_time_days`, `status_quote`, `date_quotes`. These are prompt formats, read with defaults, so older answers still read.
   - `needs.yaml`: a need may carry `leadTimeDays` (optional).
   - No catalog (C1) record changes.

## Consequences

- The audit's failing examples are fixed and measured: `packages/evals` scores each replaced judgment on `fixtures/judgments/` three ways (the deleted rule, kept in `judgment-baselines.ts` for this only; the model, replaying recorded verdicts through `judge()`; the hand-off). With the recorded verdicts no replaced judgment says yes where the truth is no. The recorded verdicts were written with the fixtures, standing in for a model: the bench measures what the checks settle, what reaches the judge and whether its quotes hold, not a live model.
- Copilot's cost: no extra prompt per change. The questions on file and the format's new fields add tokens to prompts the steps send anyway. A step that writes a field's check in other words, or a value the page doesn't say word for word, gets one more round, as any finding does.
- With a direct model, each kind with open items costs one batched call per step run (up to 25 items a call), and none when the verdicts are stored.
- With a hand-off, a status and a normalised lead time are the scan model's reading, recorded with its run, not a second model's; a question a step doesn't mark as the same is raised beside the earlier one rather than merged. A person sees both.
- Not built: a command and an app screen to list and override judgments (a person edits the file today, as the file's header says); the judge for the critic's data classification and observability checks, the release notes, testgen's tracing, the skeleton's traces and the readiness bar's coverage (audit items 7, 9, 10, 12 and 14); the fix-up pass that replaces hand-backs with patches (audit 4.3); the initiative planner's lead times on the normalised reading. The brief's unknown names and retrieval are the context engine's (ADR 0107 addendum).

A step reads what it can without spending a person's prompt with `settle(spec, items, …)` in `@maycombhq/ai`: the veto, a judgment on file, and the judge where it may be asked. An item none of these settles is open, and **an open item is never answered by the deleted rule**: it is shown to a person as not judged, or asked of them as a question (ADR 0117 §1, "unsure is never a guess"). ## Addendum (2026-10-24): an unjudged criterion is a note, not a hand-back

A live run on a real metarepo found point 3's hand-off rule for criteria failing as the deleted word rules did: a criterion `checks: [lastReadAt]` whose then clause was "unreadCount is 4, counting messages after joinedAt" (the count depends on lastReadAt without naming it) was handed back three drafts running with "name it in its then clause", and the stage stopped. Whether a criterion checks a field is meaning; a hand-back that asks for the field's name is a word match.

- **`settle()`** (the addendum above, `judgesDirectly`): a kind's veto, then a verdict on file, then the judge, but only where the runtime calls a model directly. With a hand-off nothing more is asked and nothing is guessed: a criterion with no verdict in its results is unjudged.
- **Criteria** (`coverageIssues`): a field written in the then clause is still a fact; the facts that stay deterministic are that each field is the task's (`stories.unknown-check`) and under some criterion's `checks` (`stories.field-not-checked`). A claim the then clause doesn't write is settled: "yes" passes; "no" goes back to the writer (`stories.check-not-in-criterion`, now a person's decision if it comes back, since a judge read it); "unsure", and a claim no judge read, is a non-blocking note (`stories.check-unjudged`), written under the criterion in the story file, where the critic's story lens and the PR's reviewer read it. Never a stop. A person records a verdict in `judgments/covers-field/`.
- **Kept as facts**: `stories.unknown-story`, `unknown-task`, `unknown-step` and `unknown-request` (ids that exist), `no-criteria` and `missing-story` (something is there), `unknown-check` and `field-not-checked` (set membership on structured data), and `request-unquoted` (the quote is word for word in the item's applies-when; whether the step meets it is the writer's reading, and with a direct model the `applies` judge checks recall).
- `fixtures/judgments/covers-field.yaml` gains the run's case and its opposite; the eval's hand-off row counts an unjudged claim as not yet a yes.

## Addendum (2026-10-24): an answered question isn't asked again in other words

A live run on a real metarepo (headless Claude Code) found a question a person had answered asked again. The person answered "Which messages can be pinned?" with "text messages only, not questions, answers or system notes"; the next draft asked "Which kinds of message count as 'text messages'? Only plain posts, or also questions, answers, system notes?", which the answer already said. The fixtures retell it on the Forge estate (`fixtures/stages/pin-note/`, `fixtures/judgments/answered-by.yaml`).

Why it got through:

- The answer reached the drafter in the `hand-backs` block, with "follow their answers", but nothing said not to ask it again in other words or that the answer is part of the brief. `questions-on-file` listed the answered question with its state and not its answer, so the drafter's `sameAs` had nothing to read it against.
- The same-question judge ran (headless Claude Code calls a model directly, `judgesDirectly`), and saw the answered question as a candidate, but only the two questions, never the answer. Asked whether two questions are the same, it could fairly say no: the new one asks what a word in the answer means. And a question judged narrower than an answered one was raised beside it, to the person.

What changed:

1. **The prompt.** `questions-on-file` gives each answered question its answer and who gave it. The rule (`SAME_AS_RULE`) says an answered question is decided and its answer is part of the brief, as binding as the brief's words: never ask it again in any words, nor ask what its answer already says; ask only what it leaves open (`sameAs` narrower); and a question raised anyway that an answer decides says so: `sameAs: { id, verdict: answered, quote: <the answer's words> }`. The hand-backs instruction says the same. `QuestionDraft.sameAs.verdict` gains `answered` (C6, additive; a prompt format).
2. **A judgment kind, `answered-by`** (`ANSWERED_BY_SPEC`, `answerJudge`): "a person already answered the existing question with the answer given; does that answer decide what the new question asks?" yes or no, quoting the answer (`JudgeSpec.quoteFrom`, a quote of another text is refused). Its key includes the answer, so a changed answer is judged again. The fact veto: the new question names an id, field, path or number that neither the answered question nor its answer names (`namedBeyondAnswer`); a person answered about those things, not these (§4 holds).
3. **`raiseQuestions` asks it first**, of the answered questions that may decide a draft: the candidates as before, and every one the same step asked, since a draft re-asking its own answered question often cites other lines. In order: a stored judgment, the step's own reading (`sameAs` answered, its quote checked word for word in the answer), then the answer judge where the runtime calls a model directly (`stepJudges`: model, headless Claude Code, replay; not the hand-off, not the mock). Yes: the step reads that answer, the draft becomes the answered question (`alsoAskedBy` when another step asked it, `decidedBy` in the result), nobody is asked, and no same-question judgment is spent on it. No: the question is weighed as before.
4. **Nothing settled it: back to the drafter once, not to the person.** With a hand-off and no `sameAs`, or a judge that says unsure, the stage loop holds the question back (`hold`, `held`): it isn't written, and the next draft gets a hand-back in the data block naming the answered question and its answer, saying to follow it and either mark the question or leave it out. The loop remembers it (`handedBack` in `stage/<stage>.yaml`); asked again after that, it goes to the person with the earlier one under `related`. When the stage stops for other open questions anyway, held ones go with them. Unsure is still never a guess: the drafter or a person decides.

- **Contracts.** Additive: the `answered-by` kind (C5 kinds are open strings), `JudgeSpec.quoteFrom`, `RaiseOptions.answerJudge` and `hold`, the result's `held` and `decidedBy`, `sameAs` verdict `answered`. No question file changes shape, so no migration.
- **Measured** on `fixtures/judgments/answered-by.yaml` (3 cases: the live run's, one the answer leaves open, one vetoed): the judge, on the recorded verdicts, 3/3, the vetoed case never sent. Each mode is tested on the pinned-note scenario: model and headless (a fake runner) read the answer by the judge; hand-off by the drafter's `sameAs`, or by one hand-back.
- **Copilot's cost.** None when the drafter follows the answer or marks its question; one more draft when it re-asks without saying so, rather than a question to a person.
- **Not built.** The answered-by kind in the evals' judgment bench; the scan steps (`scan verify`, `spec draft`) pass the answer judge but don't hold questions back.
