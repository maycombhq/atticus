# Running Atticus's steps through Copilot agent mode

At an organisation where GitHub Copilot is the assistant people have in their editors, this is the
path Atticus's steps take. Copilot's **agent mode** opens files, writes them and runs commands,
which is what Atticus's steps want: the agent writes the facts file or the stage answer where
Atticus expects it, runs the Atticus command that checks it, and fixes what the check hands back.

The `@atticus` chat participant still works and is unchanged. It carries prompts between Atticus's
command line and the model and answers in the chat. Agent mode is the other way to take the same
step, and it is the one to use where the step writes files.

See also: [Choosing models at an organisation on Copilot](models.md), and
[Installing Atticus](install.md) for the command line itself.

## Setup

1. **Install Atticus's command line** so `atticus` is on your PATH (`npm install -g @maycombhq/atticus`,
   or the offline bundle; see [Installing Atticus](install.md)). Every check in every step is one of
   its commands, so without it agent mode has nothing to check against.
2. **Put the agent files in the metarepo.** They live in this repository at `plugins/copilot/`,
   generated by `pnpm copilot-agents` from the same commands `atticus assistant-files` renders:

   | File                                                 | What Copilot does with it                                                                                     |
   | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
   | `.github/agents/atticus-repo-reader.agent.md`        | Reads a repo into facts and loops on `atticus verify`. A **read** step.                                       |
   | `.github/agents/atticus-verifier.agent.md`           | Checks what was recorded about a repo against its code. A **read** step.                                      |
   | `.github/agents/atticus-repo-describer.agent.md`     | Drafts the one sentence that says what a repo is for, cited, for a person to confirm. A **read** step.        |
   | `.github/agents/atticus-stage-drafter.agent.md`      | Drafts a change's feature, architecture, stories, fast path or first draft. A **draft** step.                 |
   | `.github/agents/atticus-task-runner.agent.md`        | Implements one task in its worktree, from the context Atticus loads. A **draft** step.                        |
   | `.github/agents/atticus-knowledge-reader.agent.md`   | Reads the wikis into items, searches them, answers from them, says what a change needs. A **knowledge** step. |
   | `.github/instructions/atticus-rules.instructions.md` | The rules every step keeps, applied to every file.                                                            |
   | `.github/instructions/atticus-tools.instructions.md` | Atticus's commands and MCP tools, applied to every file.                                                      |
   | `.vscode/mcp.json`                                   | Registers the read-only `atticus mcp` server.                                                                 |

   Copy those three folders into the metarepo, in a pull request like any other change to it. Each
   agent carries, word for word, the protocol of the slash commands it covers, so it says the same
   thing `/atticus-map` and the others do.

3. **Run `atticus assistant-files`** in the metarepo as well. It writes `.github/prompts/*.prompt.md`
   from the org pack, which is where the agents' `/atticus-*` slash commands come from, and the
   organisation's own agents and skills beside them.
4. **Pick the model for the kind of step.** Each agent file says its kind. In VS Code,
   **Atticus: Pick the model** writes `atticus.models.read`, `.draft`, `.critic`, `.knowledge` or
   `.quick`; `runtime.yaml`'s `models.<kind>` is the organisation's choice where a person sets none
   ([Choosing models](models.md)).
5. **Reload VS Code**, open Copilot Chat, choose **Agent**, and pick the agent for the step you are
   taking. Or let Atticus open it: **Atticus: Run the next step in Copilot's agent mode** reads
   `atticus next`, picks the agent for that step, opens the chat on it with the step's prompt in the
   box, and says which kind of step it is. Where the workspace has no agent file, where no agent
   covers the step, or where agent mode can't be opened, the same command sends the step to
   `@atticus` in the chat instead, and says why.

## The checklist a person runs in a real Copilot session

Nothing in CI can sign in to Copilot, so the checks below are the ones only a person can make. Run
them once per organisation, on the invented Forge estate or on your own, and keep the result with
the setup checklist.

1. **The agents are offered.** Open Copilot Chat, choose **Agent**, and open the agent picker. The
   six `atticus-*` agents are listed, each with its one-line description.
2. **Atticus opens the right one.** Run **Atticus: Run the next step in Copilot's agent mode** from
   the Command Palette. Copilot Chat opens on the agent for that step, the step's prompt is in the
   box (not sent), and the notice names the agent and the kind of step.
3. **The model is the one your organisation chose.** Check the model shown in the chat against the
   kind of step the notice named, and `atticus.models.<kind>` or `runtime.yaml`'s `models.<kind>`.
4. **A repo read runs end to end.** Send the prompt for `atticus-repo-reader` on a small repo. The
   agent should run `atticus map <repo> --estimate` itself, write the facts file it named, run
   `atticus verify <repo>`, read `<repo>.rejected.jsonl` and fix or drop each rejected fact, and
   stop only when `atticus verify` exits 0. Check the terminal: every one of those commands is
   `atticus`, not a script the agent wrote.
5. **A stage draft runs end to end.** Send the prompt for `atticus-stage-drafter` on a change with a
   brief. The agent should run the stage with `--handoff`, write its answer to the result file the
   command named, run `atticus handoff done <run>`, then the same command with `--resume <run>`, and
   keep going until it says the stage is done. It should tell you the pull-request command and not
   run it.
6. **The MCP tools answer.** Ask the agent what is waiting on you. It should use the `atticus` MCP
   server (`waiting_on_you`, `next_step`) rather than reading files by hand.
7. **A finding stays open.** Where the critic found something, ask the agent to dismiss it. Atticus
   should record its claim as a proposal and leave the finding open, and the agent should say that a
   person decides. Then check `atticus findings <change>`: the finding is still open, with the
   proposal beside it.
8. **A question goes to you.** Where a step raised a question, the agent should show it with its
   options and say that `atticus questions answer <id> --option <n>` records your answer, not answer
   it itself.
9. **Nothing is pushed.** Check `git status` and the branch: the agent changed files in the
   workspace or the task's worktree only, and pushed nothing.

If step 4, 5 or 7 fails, the agent file is being ignored or an instruction is being read as
optional. Keep the transcript and the terminal output: those two say which.

## What is proven here, and what isn't

**Proven in this repository, without Copilot.** An integration test
(`packages/cli/test/copilot-agent-path.test.ts`) drives the whole path with a stub agent that does
only what the agent files say to do, through the same `atticus` commands a terminal would run, with
no model and no network:

- a Forge repo read into facts, one fact that doesn't hold, `atticus verify` exiting 1 with the
  reason, the fact dropped, and `atticus verify` exiting 0 with its report;
- a repo description handed over as a draft marked unconfirmed, and refused when it cites nothing;
- a feature stage drafted in hand-off mode, the critic's lens finding the flow marked read, the
  agent's second draft fixing it, and the stage ending done, every command exiting 0;
- an AI's attempt to close that finding recorded as a proposal, with the finding still open.

The generated files themselves are held to the protocol by
`packages/assistant-files/test/copilot-agents.test.ts`: each agent carries the body of the slash
commands it covers word for word, keeps every rule, names its kind of step, and is committed as the
generator makes it. `packages/vscode/test/copilot-agent.test.ts` checks what the editor asks VS Code
to open and what it says, including the fall back to `@atticus`.

**Still needs a person with Copilot.** Nothing here signs in to Copilot, so none of this is proven:

- that Copilot lists and loads a custom agent from `.github/agents/*.agent.md` in the VS Code the
  organisation ships, at the version it ships;
- that Copilot's agent mode obeys the instructions — that it runs the Atticus command instead of
  reasoning its way to an answer, writes to the exact path, and loops on the check;
- that `.vscode/mcp.json` registers the `atticus` server where the organisation's policy allows MCP
  servers at all;
- that the model picked for the kind of step is the model the request actually runs on, and what it
  costs in premium requests;
- that `workbench.action.chat.open` opens agent mode on a named custom agent in that VS Code
  version. The editor command catches the failure and falls back to `@atticus`, which is tested;
  which of the two happens in a given VS Code is not.

The checklist above is how a person closes that gap.
