# Troubleshooting

Start with `atticus doctor` in the metarepo: most problems are on the machine, and each line it prints says what to do. It also says how AI steps run here (handed off to your assistant, or model mode with which provider and whether its key variable is set, by name only) and whether the `/atticus-*` slash-command files are there and current. It makes no network call, so it doesn't call the model.

## Where am I, and what do I run?

```bash
atticus status
```

prints one line: the Atticus you are on, the version the metarepo was last upgraded by (`.atticus/metarepo.yaml`), whether this Atticus reads the metarepo's catalog, what the editor's extension needs (when a terminal or an app the extension started is asking), and one thing to do. It exits 0 when there is nothing to do and 1 otherwise; `--json` gives the parts, and the app's Home shows the same line with one button.

| The line ends with                                                                                                                             | It means                                                                                                                                                                                                                                                                                          | What it tells you to run                                                                                                                     |
| ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `Do: atticus init . --platform <platform>`, `Do: atticus init <folder> --platform <platform>, in a folder of your choice` or `Do: cd metarepo` | This folder isn't an Atticus metarepo. In an empty or plain folder, `init .` makes one here once you name your Git host's platform; inside a repository you choose the folder; in a practice sandbox the metarepo is one folder down                                                              | That command                                                                                                                                 |
| `Do: npm i -g @maycombhq/atticus@beta` or `npm install -g @maycombhq/atticus@<version>` after "its catalog was built by …"                     | A newer Atticus built this metarepo's catalog, so this one neither reads nor writes it. The exact version is named when the catalog says which Atticus built it                                                                                                                                   | Install that Atticus (from your npm mirror, or its offline bundle). Don't run `atticus upgrade`: it is for a catalog older than your Atticus |
| `Do: npm install -g @maycombhq/atticus@<version>`                                                                                              | The metarepo was upgraded by a newer Atticus, its stamp is one this Atticus can't read, or the editor's extension needs a newer one. When several are behind at once (the catalog's Atticus, the stamp's, the extension's), the newest version needed is named, once; `@beta` when none names one | Install it                                                                                                                                   |
| `Do: atticus upgrade`                                                                                                                          | The metarepo has no stamp, was last upgraded by an older Atticus, or a step waits (the line under it says how many)                                                                                                                                                                               | `atticus upgrade`, then commit what it changed in a pull request                                                                             |
| `Nothing to do.`                                                                                                                               | Your Atticus, the metarepo and its catalog agree                                                                                                                                                                                                                                                  | Nothing                                                                                                                                      |

The first row that holds is the one said. When something is behind, the same line is the last line of every refusal, so you don't have to work out which of the three versions is behind.

To check an estate where it is, with nothing leaving the machine:

```bash
atticus selfcheck
```

runs four named checks against the metarepo, reading only (it writes nothing but the usual line in the log, which names the command and nothing else; it makes no network call and no model call):

- `calls-accounted`: every call the join left has a reason. It counts the calls joined or placed outside, asked about, left with a reason, and left with none; one with none fails it. This is the join's own tally over the verified facts. It does not compare with the arrows in `catalog/generated` or with the questions on file, so it does not prove that an asked call has its question or that a joined call's arrow is drawn. With no call facts it is skipped.
- `refusals-have-next-step`: where the build's guard or `atticus status` refuses, it names a command to go on.
- `build-is-repeatable`: two builds in memory of the same sources, the second with nothing kept, list the same files byte for byte. On a catalog of 10k records or more it first says what the two builds cost, as an estimate keyed to the card's record band (10k-50k: about half a minute and under 1 GB; 50k-200k: about a minute or two and 1 to 2 GB; over-200k: several minutes and over 2 GB), never a figure of your estate; `--quick` leaves this check out.
- `no-long-silence`: the newest run of each command on record printed a line at least every 30 seconds. Time you take to answer a question is not counted.

The checks give their counts in bands (`10-99`, `1k-10k`), never exactly. Then it prints a shape card: the estate's size in bands, which known shapes it has, the platform and the slowest step in a time band, in words from a fixed list. Nothing it prints holds a name, id, path, hash or exact count of your estate. `--names` adds, on your screen only, the exact counts and the first 20 ids or paths behind a failed check; they are never in `--json`. It exits 0 when no check failed, 1 when one did, and 2 when it couldn't run (no metarepo here, or another command holds the lock). Whether even the card's words may be said outside your site is your organisation's decision, not Atticus's.

## Where to see what Atticus is doing

Open the **Console** at the foot of the app (in the bottom panel, under the page; in the classic layout **Open the Console**; it is there on every page, in a browser and in the VS Code and IntelliJ panels). It lists everything Atticus is doing or did lately on this metarepo, newest first, wherever it was started:

- what you started in the app: a scan, a sync, Apply, Propose, Bring in, an AI step, the critic, a wiki's sync, a team's tool, a run's Done, a Copilot run (with its tab per session);
- the long commands run in a terminal, by VS Code or IntelliJ, or by a Copilot session: `atticus map` (and `map --all`), `verify`, `scan`, `workspace sync`, `task run`, `task run-ready`, `knowledge scan`, `upgrade`, `handoff done`, `index rebuild`, `reconcile`;
- the hand-off runs that wait for your assistant, with where the prompt is and how to finish it, and what Done printed once it ran.

Each entry says what it is, where it was started, whether it is running, done, failed, cancelled, waiting or "ended without saying" (its terminal was closed, or it crashed), and when. Pick one to see what it printed, live: follow the end, search, copy. While anything runs, a strip under the top bar says what and how far, with **Show in the Console** and **Stop** for what the app started. A command run in a terminal stops in its terminal (Ctrl+C).

A job the app started (a scan, a sync, an AI step, Apply) is kept the same way, so it is still in the Console after the app restarts, titled by what it is and the repos, changes or runs it names (never words you typed). One still running when the app closed says "stopped when the app closed"; one another `atticus ui` window runs says to stop it there. `atticus ui` in a folder that isn't a metarepo keeps nothing there.

A command run outside the app keeps what it prints in `.atticus/logs/runs/<run>.log`, and a small record of itself (the command words, the repo, change and run ids it was given, its flag names, and in its title the values that are ids, names or dates, never one that looks secret; when it started and how it ended) in `.atticus/logs/running/<run>.json`. Each line is redacted as the log is (below). Only the last 50 runs are kept, each log to its last 2 MB or so. Quick commands (help, list, show, `next`, `--json` questions, `--check`, `--dry-run`) keep nothing. `ATTICUS_RUN_LOG=off` turns it off for a command, and for the app's jobs when `atticus ui` is started with it. The last 50 runs are counted together, the terminal's and the app's. `.atticus/logs/` is never committed.

`ATTICUS_PROJECTION_MEMO=on` in the environment `atticus ui` starts in makes the app keep the records it built from each repo's facts between Applies (ADR 0205's addendum, step 1). It keeps them by exactly what they are built from: the repo's facts file, the targets your answers give its calls, its component renames and its manifest entry. A repo whose four are the same at the next Apply takes its records from memory; any other is built again, so the map is the same either way. **It is off by default**, and any value but `on` leaves it off. Measured, it cuts that part of an Apply (from 3.5 to 4.0 CPU s down to 2.0 to 2.4 on a stress-test estate of 60 repos and 100,404 records, from 0.7 to 0.9 down to 0.4 to 0.5 on a field-shaped one of 60 repos) but not the Apply's total beyond the spread of its runs, and it holds more memory. Turn it on only where you measured a gain on your own estate: a large estate, on a machine with memory to spare. It holds up to 400,000 records and facts: about 163 MB more at 100,404 records, 12 to 18 MB more at the field-shaped estate's 17,178. It is let go with the rest of what the app keeps between Applies: ten minutes after the last Apply, at once when the heap or the machine's or the container's memory runs low, and when `atticus ui` closes. A command run outside the app never keeps it.

## The log

`.atticus/logs/atticus.log` in the metarepo: one JSON object per line, newest last. Each command with its flag names, exit code and time; failed API calls; crashes with their stack. Secrets, tokens, credentials in URLs, your home folder and user name are hidden before anything is written. `ATTICUS_LOG=debug atticus <command>` records more for one run.

## Asking for help

In the app, every error has **Save a support bundle**: it saves the file below and says where it is. From a terminal:

```bash
atticus support bundle
```

writes `.atticus/logs/atticus-support-<time>.zip` (or `--out <file>`): versions, operating system, the machine checks, the setup checklist, org-pack problems, counts of records, changes, repos and inputs (never their names) and the last 2,000 lines of the redacted log. Nothing is sent anywhere. Read every file before it leaves your organisation: an error message can still name one of your systems or changes, so remove what you can't share.
