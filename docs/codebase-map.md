# Codebase map

Read this before exploring the repo. It says where things live, so you can open the right files directly. Keep it current when you add a package or move a responsibility.

Atticus 2 (ADR 0124): the assistant reads the code and writes cited facts; `verify` checks each claim on its line and projects the facts into the catalog (C1); everything above the catalog (the stages, the stories, the critic, knowledge, the app and the editors) reads C1 as before.

## Rules of the road

- **Contracts** (frozen, change only by ADR): `packages/core/src/schema/`.
  - `kinds.ts`: C1 catalog records, schema version 3 since ADR 0125.
  - `facts.ts`: the facts file, additive to C1 (ADR 0124).
  - `dialect.ts` (C2), `review.ts` (C3 rules and findings, with the critic's four questions), `orgpack.ts` (C6), `ai.ts` (C5).
  - `workspace.ts`, `change.ts` and `executors.ts`: C4 files.
  - The local API document is `packages/core/src/api.ts` (C4 2.23.0), written to `docs/api/openapi.json` by `pnpm api:doc`.
  - The stage files of a change (`packages/planner/src/stages/schema.ts`, stage schema 1, flow delta 2) are the planner's, not a frozen contract.
- **Paths in a metarepo or adopted repo:** always resolve with the helpers in `packages/core/src/metarepo.ts`: `orgPackDirOf`, `catalogDirOf`, `stateDirOf`, `layoutOf`, `changesDirOf`, `runsDirOf`, `inputsDirOf`, `proposalsDirOf`, `factsDirOf`, `specDirOf`, `mapDirOf`. For messages and stored paths use their `*RelOf` forms. Never `join(root, "org-pack")` and the like. In a repo adopted in place they are all under `.atticus/`.
- **Records:** parse with `parseRecord`, write with `serializeRecord` (canonical YAML), file path `recordPath` (`<kind>/<id>.yaml`). Merge and identity: `packages/core/src/merge.ts`. Curated decisions: `curated.ts` (`applyCurated`). References: `refs.ts`.
- **The facts path** (ADR 0124):
  1. Schema `core/src/schema/facts.ts`.
  2. Projection to C1 in `core/src/facts.ts` (`projectFacts`). A column or store fact cited in a migration file (`core/src/migration-files.ts`, `migrationOf`) makes a Migration record.
  3. The verifier `verify/src/verify.ts`, with `atticus verify <repo> [--write]` in `cli/src/verify-commands.ts`. The files a reader read with nothing to record (`<repo>.reviewed.jsonl`) are parsed in `verify/src/reviewed.ts`.
  4. Facts into the catalog: `scanner/src/facts-catalog.ts`. This covers `catalogWithFacts`, `componentRenames` for component ids two repos share, `estateFromFacts`, and the targets questions.
  5. The join across repos: `core/src/facts-join.ts` (`joinFacts`, `joinRecords`). Who a gateway route lets in, and callers a person declared in the profile: `core/src/facts-callers.ts` (`joinCallers`, `callerRecords`; ADR 0124 addendum A-callers). `scanner/src/facts-scan.ts` (`estateFacts`, `factsForScan`) feeds it.
  6. The map renderers `verify/src/map.ts` (`renderMap`, `openApiOf`), with each flow's sequence diagram from `diagrams/src/flow-sequence.ts`.
  7. The read ledger of a repo read in parts (addendum A-ledger): the plan is written and read in `cli/src/map-parts.ts` (`writeReadPlan`, `readPlanProgress`) as the facts companion `<repo>.read-plan.yaml`; each part's state is read back from the facts and `<repo>.reviewed.jsonl`, never recorded by hand. `map --estimate` writes it, `atticus next` names the part that comes next. The companion names are `FACTS_COMPANIONS` in `core/src/metarepo.ts`.
- **The scan** (now the readers' cross-check, and the merge every catalog build shares):
  - `packages/scanner/src/scan.ts` (`scanEstate`).
  - `merge-input.ts` (`mergeEstate`, `estateMergeInput`).
  - `facts-scan.ts`: a repo with verified facts is taken from them, and its readers become a note.
- **CLI:** `packages/cli/src/main.ts` routes every command to a `*-commands.ts` file in the same folder.
  - The twelve commands `atticus help` shows are `TOP_WORDS` and `TOP_HELP` in `top-commands.ts`, with `aliasArgv` for `join`, `stories` and `task`.
  - `atticus openspec <args...>` (ADR 0006 addendum 2026-10-26) is a pass-through in `openspec-run-commands.ts`, running the bundled OpenSpec through `runOpenSpecRaw` (`openspec-adapter/src/adapter.ts`); `openspec setup` and `openspec check` stay Atticus's own in `workspace-commands.ts`.
  - Every other command is legacy. `atticus legacy` lists them (`help-commands.ts`), and each still runs by its own name.
  - The full `HELP` text in `main.ts` is the command catalogue (`atticus commands --json`, `pnpm docs:commands`, the docs check).
  - Start time: `bin.ts` answers `--version` itself and dynamic-imports `main.ts`, which statically imports only `@maycombhq/core/light` (`SCHEMA_VERSION`, `createLog`) and its own small files; every command module, and `setUpAi` (model providers, context tools, the critic's code search), loads when a command needs it (`NO_AI` lists the commands that skip it). `test/startup.test.ts` holds this. Import a helper like `table` from its own small file (`table.ts`), not from a command module.
  - Tests are in `packages/cli/test/`.
- **Fixtures** (hand-written, byte-exact, never regenerated):
  - `fixtures/forge`: the bank-like reference ecosystem; its expected catalog is `expected/scan.yaml`.
  - `fixtures/forge-change`: the critic's regression bar.
  - `fixtures/estate-facts`: three invented repos' facts, the join, and the component collision.
  - `fixtures/stages/`: the architecture and stories stages.
  - `fixtures/probe/`, `packages/verify/test/fixtures/metarepo/` (the map's two-repo metarepo), `fixtures/forge-speckit`, `fixtures/forge-dialect-eval`, `fixtures/harbor`.
- **The bench** (`bench/`, public repos pinned to a commit): the scorers are in `packages/evals/src/`.
  - `bench.ts`: `scoreFacts`.
  - `estate-bench.ts`: `scoreEstateFlows`.
  - `story-bench.ts` and `story-draft.ts`: `scoreStory`, `benchStoryFromStories`.
- **Decisions:** `docs/adr/` (read the one for the area you touch), `docs/build-status.md`, `docs/decisions-pending.md`.

## The default product and the cut

The design's cut ("Adoption and the cut", ADR 0124) applies to what a person meets, and to the bundle only for search by meaning:

- **Default:** in the twelve commands, the app's six entries, VS Code's three views and the offline bundle.
- **Optional:** not in the default bundle. Today only the embedding packages; `pnpm bundle --with-embeddings` adds them. The npm install brings them as optional dependencies of `@maycombhq/atticus`, packages of their own (ADR 0124 addendum D-npm2).
- **Legacy:** still built and bundled, because default packages import them (`verify` uses `diagrams`; `scanner` uses `features`, `glossary`, `intake`, `ingestors` and `synth`; `planner` uses `adapters`, `extractors` and `ingestors`). Their commands run under `atticus legacy` (or by their own names), and their pages are under More pages in the app's menu, found by Ctrl+K and a tab of their section with `atticus ui --full`. Nothing was deleted; ADR 0129 is the inventory of what may be.
- **Test:** test and milestone suites, never shipped.

Knowledge stays default: the product owner made org knowledge integral (the design had it optional). The design's generated scanners were not built: ADR 0124 §3 replaced them with the readers as a cross-check.

**Cutting Atticus 1 (ADR 0129).** The product owner approved cutting Atticus 1 on condition that nothing breaks and the app loses no depth. ADR 0129 is the inventory: every Atticus 1 package, command and screen with what in Atticus 2 does its job, or that nothing does. Of seventeen Atticus 1 packages none can go today — the readers are Atticus 2's own cross-check (ADR 0124 §3), and release, initiatives, intake, glossary, features, stubs, site and executors have no successor. Read that table before deleting anything; a row that says Kept needs a new ADR.
