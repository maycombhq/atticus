### I. The AI reads the code; a thin deterministic layer verifies (direction change, decided by the product owner)

Why: on the first real repo almost every reader needed a fix, each found only by contact with real code, and fixed by an Atticus developer. No one will be there to do that at another organisation, and an org can't wait for a release. Hand-written readers can't keep up with every organisation's code, so discovery moves to the AI. Deterministic code stays only where a bank needs it: checking each claim's citation, reproducibility per commit, and the checks on outputs. This supersedes the reader-by-reader approach of groups C and D where they overlap.

- [ ] **I1. Decide and record it.** CLAUDE.md rule 4 ("Deterministic scans: no AI calls inside a scan") changes to "the AI reads; every fact cites code that a check confirms; the same commit gives the same catalog". ADR 0074. Needs the product owner's explicit go before any code changes; then update the assistant memory note that says scans stay deterministic.
- [ ] **I2. A public-repo bench first.** 20–30 open-source repos across stacks (Spring, ASP.NET Core, legacy .NET/WCF, Node, React, Python, Terraform, pipelines), each with a hand-checked reference of what it serves, calls, stores and deploys; score found, missed and wrong. Both the current readers and the AI scan run on it, so the switch is decided by numbers, and every later change is measured on it. No client code.
- [ ] **I3. AI scan prototype on NadiEngine.** The AI reads the repo (the way a call-chain mapper skill does) and states every endpoint, call, data access, field and deployment with its file and line; a deterministic check confirms each citation (that line declares that route, that SQL writes that table); compare with today's catalog and show, for each difference, who was right.
- [ ] **I4. Make it the default.** The AI scan finds; the built-in readers become an optional fast path and a cross-check (agreement confirms; a disagreement is a finding: a reader misreading, or something the readers miss).
- [ ] **I5. Reproducible and cheap to rescan.** Verified facts stored per commit; a rescan re-reads and re-verifies only changed files, so the same commit gives the same catalog and the model isn't called for unchanged code.
- [ ] **I6. Corrections stay at the organisation.** A person's correction, or a rule scan review proposes, applies there at once; built-in readers become overridable by rules (today an org can't correct a reader's misread).
- [ ] **I7. Coverage, measured.** A citation check proves a line says what's claimed, not that nothing was missed: measure coverage on the bench and per repo (files read, gaps left).
- [ ] **I8. Costs and approval.** A bank-approved model (ADR 0065 providers); model time on an estate's first scan; budgets and a per-repo cost estimate before a scan starts.
- [ ] **I9. Every scan is AI → deterministic → AI** (the product owner's design; refines I3–I4):
  1. **AI first:** survey the repo and classify its type (for example a Spring Boot REST service on a house starter, a React SPA with its own HTTP client, a Terraform module repo), and decide whether the deterministic scanner needs customising to read everything a repo of that type holds.
  2. **If it does, the AI customises the scanner, and that is a change like any other** (the product owner's decision): the lightest thing that works, a rule file (rules, dialects, framework models, overrides of built-in readers) when the rule format can express it, and a **scanner plugin in code** when it can't. A plugin is developed as a change in the metarepo, with a spec, golden-file tests from the repos it is for, the critic, and a merged PR; Atticus loads it only then. It runs sandboxed (read-only access to the repo's files, no network, no writes outside its results, time and memory limits), versioned and pinned (every fact records the plugin version and so traces to its PR), and its own tests run before each use (a failing plugin is left out and flagged). Needs I13.
  3. **Deterministic:** run the scanner with that configuration.
  4. **AI last:** verify the result against its own reading of the code (every fact's citation confirmed, every difference explained); what fails goes back to step 2. Stop when a pass adds no new facts, every gap has a verdict and every citation checks out, within a time and cost budget, not at "perfect".
  5. **Ambiguity is the stopping point, and the person resolves it** (the product owner's design): what the AI can't settle from the code (which repo a base URL means, whether a table is the system of record, whether a gap is a vendor) stops the loop as a question to the person in the app, with the evidence it has. The app writes the answer into the right file in the metarepo (a recorded decision, a vendor, a mapping, a profile's setting), shows the command to commit it and the command to rerun, and the rerun reads those files: answered questions are never asked again, and an answer changes what the deterministic step reads.
- [ ] **I10. A scanner profile per repo type, reused.** What step 2 writes is kept as the profile for that type of repo; the next repo of the same type starts from it and only adds what is new, so the second repo costs less than the first. Profiles carry their own tests from the repos that made them. **Known types are detected automatically** (the product owner's design): each profile carries a fingerprint of its type (build files, key dependencies and house packages, framework markers, folder layout, the files its rules read), learned from the repos that made it; every new repo is ranked against the known fingerprints deterministically, and the agent confirms by reading it: a clear match uses the profile as is, a partial match reuses it and extends it only for what is new, no match starts a new type, and only a real tie between two profiles is asked of a person. When a repo drifts so its profile stops reading it, the verify step re-matches or extends. **Answers become knowledge for the type** (the product owner's design): when a person answers a question (I9 step 5), the agent sorts it: an answer about one repo is a recorded decision for that repo; an answer about a repo type or a framework ("in this house starter `@X` is a REST route", "repos of this type keep their client config in `config/clients.yml`") goes into the agent's skill and agent definition for that type, in the org pack's `skills/` and `agents/` beside the profile, through a PR like any org-pack change. Every later repo of that type, and every later scan, starts from it.
- [ ] **I11. A spec per repo.** Every onboarded repo gets a spec of what it is today: its entry points and exits (endpoints, events, jobs, screens; the calls, messages and files it sends), the logic between them, field-level mappings (request → DTO → entity → column), database reads and writes, configuration and deployment, each statement with its evidence. N repos give N specs, regenerated on every scan, the current-state baseline that changes are drafted against. Needs D4 and D11.
- [ ] **I13. Scanner plugins as changes: the loader and its sandbox** (moved from Phase 4, now a building block of I9). Load a plugin only from the org pack once its PR is merged; run it in a sandbox (a separate process or worker with read-only access to the repo, no network, no writes but its results, time and memory limits); pin its version in every fact it produces; run its golden-file tests before use and leave out a failing one; plugins written against the C4 plugin SDK (`defineExtractor`), so a plugin the AI wrote and one a person wrote are the same thing. ADR.
- [ ] **I12. The estate pass: connect the dots.** After the repos, the AI iterates over the whole estate: joins calls across repos, discovers the UI's pages and what each calls, and builds the end-to-end picture; detects features within one repo and end to end across repos; iterates with the same stopping test as I9. Every join it makes cites both ends.

From a live architecture run with headless Claude Code on a chat app that adds a table (2026-10-24; ADR 0087, 0111, 0115 and 0116 addenda; fixtures `fixtures/stages/pin-table/`, `packages/planner/test/fixtures/names-in-code/`). **Works:** a person's edit of a stage's files is that stage's draft. The files are hashed when written (`written`) and a copy is kept (`stage/<stage>-by-person/<n>/`, `byPerson`). The edit is checked and reviewed with no redraft, and a stop names the file and line. `--force` or an answer redrafts from the person's files. This holds in every stage through the loop. A new table is defined once, by the step that marks it new; the other steps inherit it (`delta.table-new-twice`). Retention and classification are one question for each table. Every classification is checked against the org pack's levels. The architecture and fast-path prompts carry the levels, the store facts (`storeFacts`: up to three migrations, the next free name, the folder and the column types) and the write rules. The hand-backs give the next migration name and the store's types. A stop for questions and drafting findings gives one end report (`stageEnd`, `StageResult.stopped`), and the next draft gets those findings with the answers. A name a cloned repo's code names is not a gap (`namesInCode`, `inCode`, `searched`). **Partial:** locating a finding's line is built for target flows only; for the other stages a stop names the stage's file without a line. A person's edit that passes is written back in canonical form, so their comments survive only in the kept copy. An edit of a generated file (design.md) counts as an edit and is kept, but is regenerated. A loop file from before the hashes falls back to file times. The migration numbering is read from the catalog's Migration records; a store the catalog has none for gets no next name. **Not built:** a person's edit picked up while the stage waits on a hand-off run; columns added to an existing table by two steps are merged by column, not defined once.

Known names and values from a live run on a Java/Spring chat app (2026-10-24; ADR 0116 and 0118 addenda S1, S2, T2, U2; fixtures `packages/planner/test/fixtures/names-in-code/forge-boards` and `pin-a-note`, `packages/extractors/test/fixtures/data/allowed-values`). **Works:** `namesInCode` reads source files only, by the readers' grammars (`outlines`, `codeReaders()`).
