## CHANGELOG.md (beta.33, Added)

- **A recipe per kind of repo (ADR 0210 part 2).** A reading rule may carry an `extract`: a pattern matched line by line with scopes (the nearest line above that matches, holding until its `end`), or every scalar leaf of a YAML file (`yaml: leaves`). One small engine in core runs it with no model (`runRecipe`), writing facts of the facts file, `by: reader`, each citing its line with the main capture as written there and each scope or parent key it used in `with`; the verifier checks them as any other. Every part of a value is a cited capture: a field is only `{group}` references, with at most one of `/ . : - _` between two, so a literal path part is refused when the recipe is read, and a pattern with a nested quantifier is refused too. `proveRecipe` compares a recipe's facts with the verified facts of each repo given, by file, line and every field the recipe fills, says which differ, and gives a proof only when two repos it wasn't written from match. Nothing reads with a recipe yet: the read is wired in a later item.

## CHANGELOG.md (beta.33, Contracts)

- C6: reading rules schema version 3: a rule's optional `extract` (`{ fact, pattern, scopes?: [{ name, pattern, end? }], optional?, fields, set? }` or `{ fact, yaml: "leaves", fields?, set? }`); an active rule with an `extract` needs `learned.proof` naming at least two repos. A version 1 or 2 file reads as it did; `migrateReadingRulesText(text, 3)` moves a 1 or 2 file to 3 by its number (Learn's default stays 1 → 2, so a file it writes still reads in beta.32). beta.32 refuses a version 3 file whole: a team upgrades together. `docs/spec/contracts/c6-org-pack.md` regenerated. ## Open, for the next step

- **Where a read would use an active recipe.** `effectiveRules` (`packages/cli/src/reading-rules.ts`, line ~142) puts an active rule whose `learned.proof` doesn't name the repo among the drafts (ADR 0208's "only for the repos it was proven on"). An active recipe is proven for its type, so that test should skip a rule with `extract`. Then the one place a read could run active recipes with model fallback is the read in `packages/cli/src/map-commands.ts` that already loads `effectiveRules(root, repo, { dir, op })` (around line 1062): for a repo whose type has active recipes, `runRecipe` on its files, verify, and skip the model read unless asked or the join's misses name it (ADR 0210 part 2, "Recipe first, model on request").
- **Size budget.** `scripts/check-size-budget.mjs` reports +3,707 non-test lines over beta.30 against a budget of +3,500: this change (about 490 lines, prettier included) takes it over by 207. ADR 0210 part 8 changes the check ("no more lines than the last release"); until then the owner raises `BUDGET` or code comes out.
- An `entry` recipe's `entryType` defaults to `rest` (and a `call`'s `callType`), the facts file's first choice: the ADR's example sets neither, and a template can't hold a literal. `set` sets a choice field to another of its choices.
- `cite.value` is the first pattern group the templates use that matched something, the main field's first (`path`, `key`, `name`, `host`, `term`, `value`), else the whole match: always on the line, so the verifier's claim check holds.
- A YAML leaf deeper than six parent keys isn't written (the `with` limit); block scalars, anchors and aliases aren't read; list items aren't leaves.
- `proveRecipe` compares with the facts it is given (the caller passes the verified ones) of the recipe's kind in the files its rule names, and methods exactly (the engine upper-cases an entry's).
