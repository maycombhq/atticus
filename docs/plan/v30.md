# Plan: 2.0.0-beta.30, one release

Status: proposed (2026-11-18). The reasons and the full list of findings are in
[field-reliability-and-ease.md](field-reliability-and-ease.md); this is what is built, in what
order, and what is left out. Nothing here is built yet.

## What beta.30 is for

1. A change of any kind (a new product no repo holds, a move of services to another platform, a
   new event to an existing hub) goes from a free-form requirements file to an OpenSpec change
   without a stage refusing it.
2. That file passes through role personas, each with its own naysayer, whose questions cite the
   verified map. This is what a team with personas and OpenSpec alone can't have.
3. What breaks in the field is found here first, on an estate shaped like the field's.

The budget: about 150 lines of code for the change flow, the rest prompts, configuration and
tests. No new subsystem. Anything that needs more is left for a later release.

## Order of work

### Step 0. The proof first (tests, written before any code, failing)

- `packages/cli/test/archetypes.test.ts`: three invented changes on the field-shaped estate
  (`field-estate.ts`, given an empty repo, a consumer nobody read and a change):
  - **Greenfield:** an approvals portal, two repos no manifest lists.
  - **Migration:** three services moved to another platform in two waves, no runtime step changed.
  - **New event:** the portal publishes to an existing topic; one consumer is a repo nobody read.
- Each goes two ways, **quick** (requirements file with the personas' tables, `change new`, the
  critic, ready tasks) and **full** (the stages), on Linux and Windows, with the mock model.
- The fixture org pack holds the starter personas and one invented domain architect, written out by
  `atticus skills write` and checked.
- The journeys and the CLI suites take the field-shaped estate as their default estate.
- A Windows job with files really held by another process and a kill in the middle of a write.

Beta.30 is done when these pass. A field report after it adds its shape to the estate before its fix.

### Step 1. The change flow (about 150 lines, three ADR addenda)

1. **Three checks loosened (ADR addendum to 0087 and 0189).** A planned repo passes the feature
   stage (`planner/src/stages/feature.ts`); a new folder in an empty repo is a note
   (`architecture.ts`); a consumer the change declares is allowed though nobody read its repo
   (`contracts.ts`, `stories.ts`).
2. **Two map tools (ADR 0104 addendum, additive C4).** `conflicts` and `similar_changes` over the
   commands that exist. `impact`, `walk`, `ask`, `search` and `show` already serve the rest.
3. **A `quick` change type (org-pack default, additive).** Proposal and tasks; no stage. A
   migration uses it or `config-change`: its waves are the order of `tasks.md`, `[P]` for what may
   run together.
4. **`atticus next` says the next step of a change that is off the stages.**

### Step 2. Personas and naysayers (prompts only, no contract change)

- In `org-pack/agents/`: product owner, application architect, domain architect (a template an
  organisation copies, for a payments architect say), UX analyst, developer, QA, security; and one
  naysayer for each. Each file names its role, the section of the requirements file it owns and the
  map tools it may call.
- One skill, `org-pack/skills/define-change/SKILL.md`: the order and the loop. The persona drafts
  its section, its naysayer asks, a person in that role answers, then the next persona.
- Each section of `requirements.md` keeps a table: question, the map's evidence (id, file and
  line), asked by, answered by, answer, open or answered. The skill doesn't go on, or create the
  change, while a row is open.
- An organisation adds a persona with two files and one line. No release is needed.
- A guide page: "the map your personas ask", for a team that keeps its own personas and OpenSpec
  and only adds `atticus mcp`.

### Step 3. What a person hits every day (small fixes)

- The extension's version check reads all four numbers.
- One install command, with the exact version, from one constant.
- One repo's Apply shows the step, the time so far and Stop in the app.
- Every refusal has one button that goes forward.
- Every error screen offers Undo the last build, Build again and Save a support bundle.
- Doctor checks PowerShell's execution policy and the npm prefix on PATH; sync turns git's sign-in,
  proxy and certificate errors into what to do.

### Step 4. Release

- Each fix is reviewed by a separate session. One full CI run at the end, Linux and Windows.
- Before the release is offered: the three changes are run once more by hand on the invented
  estate with a real model, to read what the personas ask. CI can't judge that.
- At the first real use, the smallest change goes first (the new event), on the quick path.

## Left out of beta.30, on purpose

| Left out                                            | Why                                                         |
| --------------------------------------------------- | ----------------------------------------------------------- |
| Accept any blocking check with a reason             | About 250 risky lines, and the later steps still refuse     |
| `atticus review <file>`                             | The naysayer's prompt asks the map tools instead            |
| A record kind for deployment, pipeline, secret work | A contract change; the quick type covers the migration      |
| A naysayer per persona inside the critic            | Reopens the C3 lens list                                    |
| Connect A to B on every box                         | Changes a contract; its own ADR and release                 |
| Plain-words renaming, fewer pages                   | Wide, touches every screen; after the change flow is proven |
| `atticus selfcheck`, the shape card                 | Useful, not needed for the three changes                    |
| One repo's Apply in 15 seconds                      | Needs a design of its own                                   |

## Known limits of beta.30

- A migration on the quick path has no check of the built code against the design: that check
  reads runtime steps, and a migration changes none.
- The tests prove Atticus takes what the personas write. Whether a persona asks good questions is
  read by a person with a real model.
- The full path still refuses what the three loosened checks don't cover. The quick path is the
  answer for those until a later release.
