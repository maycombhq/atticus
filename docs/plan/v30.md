# Plan: 2.0.0-beta.30, one release

Status: built and released as 2.0.0-beta.30 (2026-11-22), except ADR 0207 (a plan before a
multi-repo run, three more map tools, moving a quick change to the stages, a planned topic's
schema, the property nightly on Windows), which the owner moved to beta.31 on 2026-11-22.
Approved 2026-11-18. Reasons and the full findings are in
[field-reliability-and-ease.md](field-reliability-and-ease.md). This plan was sized against the
code, tried by hand on the Forge estate at beta.28.5, and reviewed by a separate session; what
each found is in "What the trial and the review changed" below. Every slice below is built; what
each delivered is in `docs/build-status.md` and the changelog.

## What beta.30 is for

1. A change of any kind goes from a free-form requirements file to a valid OpenSpec change
   without a stage refusing it: a new product no repo holds, a move of services to another
   platform, a new event to an existing hub.
2. That file passes through role personas, each with its own naysayer, whose questions cite the
   verified map. A team with personas and OpenSpec alone has no map to cite.
3. What breaks in the field is found here first.

Slice 1 (steps 0 to 5) is about 400 lines of code that isn't a test, with no new subsystem, and
makes the three kinds of change work. The other slices are listed under "Also in beta.30".

## The design in one paragraph

Two paths, chosen per change. The **quick path** is new in name only: a change with proposal,
spec deltas, design and tasks and no stage file is already recognised, criticised, handed off and
run. Beta.30 gives it a change type, personas to write its files, the map to ground them and one
deterministic check at its door. The **staged path** stays as it is for a change that alters
runtime steps in repos the map holds; where it can't express a change it says so and names the
quick path, instead of refusing three drafts in a row.

## What the trial and the review changed

The trial ran the three kinds of change at beta.28.5 on the Forge estate, with every AI answer
written by hand. Nothing crashed or hung.

| Kind        | Staged path                                 | Hand-written files            | Plain OpenSpec           |
| ----------- | ------------------------------------------- | ----------------------------- | ------------------------ |
| New product | Blocked at feature (`feature.unknown-repo`) | Works, to a prepared task run | Not listed until adopted |
| Migration   | Blocked at stories ("has nothing to plan")  | Works                         | Not listed until adopted |
| New event   | Friction (19 story problems), reached build | Works                         | Not listed until adopted |

So the quick path is real, and the plan builds on it. The review then found what would have made
it fail, each fixed below: a change without a spec delta is not valid OpenSpec and is refused at
hand-off; an existing org pack would get neither the type nor the personas; personas written for
Copilot lose their tool list and hand-offs; `atticus next` and the app send an off-stage change
into the stages; tasks for a repo no manifest lists can't run; waves across repos aren't ordered;
on the quick path the critic is nearly silent, so the advantage would rest on prompts alone.

## Order of work

### Step 0. One ADR, approved before any code

Done: [ADR 0201](../adr/0201-the-quick-path-and-personas-that-ask-the-map.md), "The quick path, and personas
that ask the map", accepted by the owner on 2026-11-18, with an amendment and addenda from its reviews and the real-model run: the `quick` change type (C6, additive),
the changed and added map tools (C4, additive), what `skills write` passes through, the checks
loosened on the staged path (amending ADR 0087 and ADR 0189), and the check at the quick path's door.

### Step 1. The proof (tests first, failing)

- `packages/cli/test/archetypes.test.ts`, on the field-shaped estate (`field-estate.ts`, given an
  empty repo, a repo nobody read and a change), Linux and Windows, mock model:
  - **New product, migration in two waves, new event with a consumer nobody read**, each on the
    quick path from a `requirements.md` with the personas' tables to: a change OpenSpec validates
    strictly, the critic run, the hand-off files, tasks ready in wave order.
  - The new event also on the staged path, to the end of stories.
  - The new product and the migration on the staged path refuse once, and the refusal names the
    quick path and its command.
  - A requirements file with an open question, or citing an id the map doesn't hold, is refused.
- An upgrade test: a beta.28.5 org pack gains the type, the personas and the skill, and loses nothing.
- A `skills write` test: a persona's tools and hand-offs reach the Copilot and Claude files.
- A Windows job with a file really held by another process and a kill in the middle of a write.

Beta.30 is done when these pass. After it, a field report adds its shape to the estate before its fix.

### Step 2. The quick path (about 200 lines)

1. **The `quick` type:** artifacts proposal, specs, design, tasks; phases plan, build, release, so
   `next` and the app offer the hand-off and never a stage. `requirements.md` travels in the
   hand-off. An upgrade step adds the type to an existing `change-types.yaml`.
2. **`atticus change new --from requirements.md`:** refuses while a question's row is open or a
   cited id isn't in the map (planned ids are named as planned in the file). This is the one
   deterministic check on the quick path.
3. **Waves:** a task may say `(after <task>)`; `run-ready` holds it until then.
4. **A repo no manifest lists:** task run says to create it and add it, with the command.
5. **A plain OpenSpec folder** is listed by `change list` with the command that adopts it.
6. **Map tools:** `conflicts` added; an id the map doesn't hold answers "not in the map: planned
   or not read" and isn't an error; `ask` about a topic's consumers answers what `impact` knows
   (the trial got none), and keeps the "Read as" line.

### Step 3. Personas and naysayers (prompts, and about 80 lines)

Built as planned, plus a separate **spec writer** (ADR 0201's amendment, point 6): once every
question is answered or accepted and `change new --from` has made the change, it writes the
proposal, spec deltas, design and tasks. No persona writes them. 16 starter files, not 15.

- `org-pack/agents/`: product owner, application architect, domain architect (a template: copy it
  for a payments architect), UX analyst, developer, QA, security, and a naysayer for each. Each
  names its role, the section of the requirements file it owns and the map tools it may call.
- `org-pack/skills/define-change/SKILL.md`: the order and the loop (persona drafts, its naysayer
  asks, a person in that role answers, next persona), the table each section keeps (question, the
  map's evidence, asked by, answered by, answer, open or answered), the tasks format (`## <repo>`
  headings, waves), and that a migration states one spec delta for what it changes in operation.
- `skills write` passes an agent's tools and hand-offs through and writes the metarepo's
  `.vscode/mcp.json`. An upgrade step seeds the starters into an existing org pack, never over a
  file that is there.
- An organisation adds a persona with two files and one line.
- Guide page: "The map your personas ask", also for a team that keeps its own personas.

### Step 4. The staged path says where to go (about 60 lines)

- Every manifest repo counts as the estate in the feature and deploy checks; a repo the change
  plans passes the feature stage; a new folder in an empty repo is a note.
- "Touches nothing", "changes no step" and "has nothing to plan" name the quick path and its
  command, at the first draft.

### Step 5. Small fixes found on the way (about 60 lines)

- The extension's version check reads all four numbers; one install command from one constant.
- Doctor: PowerShell's execution policy, the npm prefix on PATH; sync turns git's sign-in, proxy
  and certificate errors into what to do.
- From the trial: `atticus waiting` printing "undefined"; type `integration` made "from the
  decommission template"; "Target flows: ," with none; task context saying "read its story" when
  there is none; a new entry scored as breaking its users.

### Step 6. Release

Done: each fix reviewed by a separate session, and the whole release reviewed once more before
the version bump. The real-model run happened on 2026-11-19: the starter personas with a real
model on the field-shaped Forge estate (8 services, 3 gateway proxies, an empty repo, a repo
nobody read, a topic, three quick changes). What it found is ADR 0201's addendum of 2026-11-19
and the merge `b30/proof-fixes` (the map tools' answers, the door check, the critic on a quick
change, the personas' own words). **Still untried:** that run in Copilot in VS Code (the
`atticus/*` tool names and the hand-off buttons there), VS Code starting the map tools on
Windows by hand (CI starts the committed entry against `atticus.cmd` on Windows), VS Code
listing each persona twice (`.claude/agents` and `.github/agents`), and a first real change on
the quick path.

As planned:

- Each fix reviewed by a separate session; one full CI run at the end.
- Before the release is offered: the three changes run once by hand on the Forge estate with a
  real model in Copilot, to read what the personas ask and whether the hand-off between them
  works there. CI can't judge either.
- First real use: the smallest change first (the new event), on the quick path.

## Known limits of beta.30

- Delivered by ADR 0206 (it said: on the quick path nothing checks the built code against the
  design, and impact, map and estimate have no target flows to read): `atticus change conform` checks
  each row of a quick change's `## In the code` table against the branch's verified facts, and
  impact, the change map and the estimate read that table. What the spec deltas mean in prose is
  still never read.
- Whether a persona asks good questions was read with a real model on the Forge estate
  (2026-11-19, Step 6). Whether Copilot lets one agent hand to the next was not tried; if it
  doesn't, the skill runs the personas in turn in one session.
- VS Code starting the map tools on Windows was not tried by hand; CI on Windows starts the
  committed `.vscode/mcp.json` entry against `atticus.cmd` with no shell.
- Not in beta.30, planned for beta.31 (ADR 0207, the owner's decision of 2026-11-22): the plan
  before a run over many repos, the map tools `owners`, `consumers_of` and `similar_changes`,
  moving a quick change to the stages, a planned topic's schema and settings, and the property
  nightly on Windows.
