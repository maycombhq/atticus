# Plan: 2.0.0-beta.31, small on purpose

Status: approved by the owner on 2026-11-22 ("go ahead and start"), with the recommended answers
to its three questions: two parts of ADR 0207 are deferred, the owner's three changes are run on
beta.30 before any v31 product code, and the estate join is frozen. Gate 1 is built and merged (PR #2);
the owner decided on 2026-11-22 that it ships in 2.0.0-beta.31 with the rest, not as a 30.1. The full review behind this plan (four seats, scenario
traces, a hallucination audit, multiplayer readiness and twelve work packages with their
evidence) is kept outside the repo, because it names the owner's real systems (CLAUDE.md rule 3).

## Why small

Three things read in the code at beta.30 say that more code is not the next step.

1. **Speed may already be mostly solved, and has not been measured where it matters.** One
   repo's Apply at 60 repos was 49 s in beta.28.2 (ADR 0205). The owner's run of Apply to every
   repo that lasted from morning into the afternoon was on beta.28.3. beta.30 measures 5 to 8 CPU
   seconds on the field-shaped estate, on Linux. No number exists from the owner's machine for
   any version.
2. **Arrow fixes are still landing as code.** The estate join's three files
   (`packages/core/src/facts-join*.ts`) were 5,139 lines at beta.27, 5,227 at beta.28.5 and 5,424
   at beta.30. The owner's direction is that a
   correction becomes a local rule, not an Atticus release.
3. **The owner's three real changes have never been run end to end.** Every earlier release was
   judged on paper and on invented fixtures, then failed at the site.

## Gates, in order

- **Gate 0. Run it before building anything (no product code). Done 2026-11-22: see "Gate 0 result".** On the owner's own laptop, on
  beta.30: map a public multi-service estate, then take the three changes through the quick path
  to tasks, using public stand-ins of the same shape (a portal that approves new components; a
  move of services from one platform to another; a portal publishing updates to an event hub).
  Write down every stall, wrong arrow and refusal. That list sets the rest of v31's scope.
- **Gate 1. Read the numbers at the site.** `atticus selfcheck --timing` (built; ships in 2.0.0-beta.31):
  one build in memory, phase by phase, in fixed words and seconds. Run it, and Apply to every
  repo, on the owner's machine and read the screen.
- **Gate 2. Decide one build for many repos from that number.** Today Apply to every repo runs
  one whole-catalog build for each repo (`verifyAllCommand`, `packages/cli/src/verify-commands.ts`,
  calling `writeFactsIntoCatalog` per repo). `buildAndWrite` already takes many slots in one call.
  If the whole run is under about ten minutes, this waits; if not, it is built.

## Gate 0 result (2026-11-22)

Run on beta.30 on a two-repo public estate, three changes in the owner's shapes, all to a ready plan
hand-off. Every step and its time is in [the log](v31-gate0-log.md).

**What held.** Mapping and Apply: 135 facts, both repos verified, Apply to every repo in 1.4 s, all
30 calls from the Angular app joined to the REST entries citing both ends, no question raised.
The requirements door check: it refused an invented id, a wrong line, an open question and a
reference to a change that doesn't exist, each with its line and the command that fixes it, and
it caught one wrong line of the trial's own. Every command answered in under a second; map
questions in about 3 s.

**What the gate adds to v31** (small, each with its place in the code):

1. **Bug: a config row can't hold a value with a comma** (`spring.profiles.active` =
   `postgres,spring-data-jpa`). `pairsOf` (`packages/changes/src/code-table.ts:169`) splits on
   every comma before it strips quotes, so a quoted value is refused too. Split outside quotes.
   About 10 lines.
2. ~~Bug: `verify <repo>` says the read is complete while `--write` will refuse it.~~ **Withdrawn
   2026-11-22:** reproduced on beta.30, `verify` exits 1 on a refused reviewed line and `--write`
   refuses the same read; the "cut off" hint was the trial's own output trimming. Nothing to fix.
3. **Gap: a repo with no deploy fact and unread deploy or pipeline files passes Apply silently.**
   The REST repo's four workflows and its compose file stayed unread at 11% coverage; the
   migration persona then had nothing to stand on. One note on Apply when a repo has no deploy
   fact and the verifier lists such files as unknown. About 30 lines.
4. **Confirmed: the quick path's tasks carry no acceptance criteria and nothing says so** (all
   14 tasks across the three changes). This is the quick-path row below; no change to it.
5. **Gap: `ask` misses intent.** "How is X deployed" and "endpoints … about specialties" both
   list everything. ADR 0207's `owners` and `consumers_of` cover the owner's own questions; these
   two are noted, not planned.

**Seen, not planned for v31:** overlaps between open changes are found per repo, so on a small
estate every pair is flagged and the real clash is not named (A turns security on where B
assumes it is off); "runs after another change" can be said only in words; generated
documentation (`docs/js/routes.js`, Compodoc) is taken for an entry point.

**What gate 0 says about speed:** nothing at the owner's scale. Two repos are too few. Gate 1 at
the site decides it.

- ADR 0207 part 3, moving a quick change to the stages (about 420 lines): rare, and it has a

  of record) and no code, while the owner weighs an AI-first product. Written: [ADR 0209](../adr/0209-many-people-on-one-change-decided-before-it-is-built.md).

## The larger question

Gates 0 and 1 are also the cheapest evidence on whether to keep building on this codebase or
start the AI-first product the owner is considering. If the three changes run cleanly on beta.30,
v31 is the list above. If they stall in the stages, the map or the join again, v31 stays this
small on purpose.
