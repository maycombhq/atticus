# M3 exit report

Run on 2026-10-18 on the cloud build machine, from `main` through ADR 0041, with the suite in `packages/m3-exit` (`@maycombhq/m3-exit`, private, tests only).

The suite drives Atticus the way a team would, through the CLI's `main()` (the built `@maycombhq/cli`), in a temp copy of `fixtures/forge` with the `fixtures/forge-change` and `fixtures/forge-speckit` org-pack additions laid over it. The seven Forge repos are committed and served from local bare remotes, `atticus workspace sync` clones them, and `atticus scan` builds the catalog. Outside systems (Git host, work tracker, service desk) are the C4 mocks `runtime.yaml` names; AI runs as recorded replay from hand-written recordings (`fixtures/forge-change/recordings/` and `packages/m3-exit/test/fixtures/recordings/`); builds use a fake build runner (a Node script set as the repos' build command). Nothing touches the network.

Run it with `pnpm --filter @maycombhq/m3-exit test` (about three minutes; build the CLI first with `pnpm turbo build --filter @maycombhq/cli...`). A product gap that the exit needs fixed is kept as a `gap(...)` test (`it.fails`) that asserts what the exit needs and is expected to fail; run with `M3_EXIT_SHOW_GAPS=1` to see why each fails. When a gap is fixed its test starts to "unexpectedly pass": change `gap(` to `it(`. No gap test is left.

Result today: **60 passed, 0 expected failures, 60 tests** (the 51 of the exit suite and 9 for the live-run scripts). (The eight gaps found by the first run are closed, below; the workaround steps they needed are gone.)

## Product gaps found, and how each was closed

Each had a `GAP …` test; each test is now an ordinary test with the same name (without "GAP").

1. **`critic-ai-wiring`**. `atticus critic` never ran the AI lenses. `atticus critic <change> --mode <mode>` now builds the runtime with `runtimeForCli` (as `plan stories` does), so `--mode replay` (recordings from `ATTICUS_REPLAY_DIR`), `hand-off`, `model` and `headless-claude-code` run layer 2. Without `--mode` the critic runs its deterministic checks alone, whatever `ATTICUS_RUNTIME` says: a hand-off run waits for an assistant and a live one costs money, so a mode set in the shell for other commands does not turn it on. Tests: `critic-seeded.test.ts`, `packages/cli/test/critic-cli.test.ts`.
2. **`task-run-replay`**. `atticus task run --mode replay` answered "Replay mode needs a folder of recordings" even with `ATTICUS_REPLAY_DIR` set. `taskRun()` now reads `ATTICUS_REPLAY_DIR` (and `ATTICUS_RUNTIME` when `--mode` is not given) and passes it as `RunTaskOptions.replayDir`, which `runTask()` hands to `createRuntime`. Tests: `lifecycle.test.ts`, `packages/cli/test/run-cli.test.ts`.
3. **`finding-gate`**. A knowledge gap asked at the design gate came back open at the plan gate with the same id, and `atticus finding` could only reach the design copy. Now `atticus finding` has `--gate`, and without it takes the copy from the latest round across gates (the most recent `createdAt`, the later gate in `gates.yaml` on a tie). An owner question already asked at another gate and still open there is not asked again: the same gap at a later gate is written as `asked`, with the first asker, the person it went to and a reason that links to the first question ("Already asked at the design gate: see review/design/2/<id>.yaml."), so it stops blocking the later gate and nobody asks twice. No contract changed (state, resolution and reason are existing C3 fields). Tests: `packages/naysayer/test/cross-gate.test.ts`, `packages/cli/test/critic-cli.test.ts`, `lifecycle.test.ts`.
4. **`trace-gate-lifecycle`**. The lifecycle only read the gates in `gates.yaml`. The Build, QA and Go/no-go hand-offs now also read the built-in gates (`drift`, `hand-up`, `trace`; `phaseFindingGates` in `packages/changes/src/lifecycle.ts`), so open blocking findings and open gaps there stop the hand-off, as ADR 0039 says. Earlier phases are not held back by them. Tests: `packages/changes/test/built-in-gates.test.ts`, `lifecycle.test.ts`.
5. **`manual-git-host`** (the remaining calls). `gitHostFor` in `change-commands.ts` was fixed earlier; `specHandUp()` and `runTask()`/`completeTaskHandoff()` (level pr) now build the Git host with the manual context (`fileStepStore(root)`, the root and the procedures) too, so `gitHost: { type: manual }` opens the PR as a step instead of failing. Tests: `packages/taskrun/test/manual-git-host.test.ts`, `packages/cli/test/run-cli.test.ts`.
6. **`change-folder-layout`**. Already fixed by `changesDirOf` (used by `packages/changes/src/store.ts`); the test is now an ordinary test and passes.
7. **`init-path`**. `atticus init /some/path/shop-meta --platform shop` named the org pack after the whole path; it now uses the folder's base name. The suite creates its metarepos with `atticus init` now. Tests: `adopt-absorb.test.ts`, `packages/cli/test/setup-cli.test.ts`.
8. **`trace-noise`**. `atticus trace` printed Git's raw error for each task branch that doesn't exist yet. A task with no branch and no run record is now "not started" and reported in one line ("Not started yet (no task branch): forge-ledger 1.2, …."); a branch that exists but can't be read is still a problem of its own. Tests: `packages/testgen/test/trace.test.ts`, `lifecycle.test.ts`.

9. **`task-run-failure-reason`** (found on Windows CI). `atticus task run <change> <task> --mode replay` that failed printed only "The run for task 1.2 failed." and now adds why: the failing step and its error (`describeRun` in `packages/cli/src/run-commands.ts`; test `packages/cli/test/run-describe.test.ts`).
10. **`prompt-line-endings`** (the Windows cause, from reading the code; confirmed on Linux with `core.autocrlf=true`, not yet on a Windows machine). The task worktree is checked out with CRLF where Git's `core.autocrlf` is on, so the files the task prompt quotes carried `\r\n` and the prompt hash differed from the recording's. `readIf` in `packages/taskrun/src/prompt.ts` now reads files with LF line endings, so the prompt (and the replay key) is the same on every platform. Test: `packages/taskrun/test/line-endings.test.ts`.

Also done, not a gap test of its own: **adopted layout leftovers.** In a repo adopted in place, the hand-off runtime, headless Claude Code prompts, `pruneRuns`, the task run's prompt, build logs and messages, and the editor workspace files now use `.atticus/.runs/` (`runsDirOf` and `runsRelOf` in `packages/core/src/metarepo.ts`); `templates draft` reads `.atticus/inputs/` and writes `.atticus/proposals/templates/` (`inputsDirOf`, `proposalsDirOf`); `intake add` and `intake list` use `.atticus/inputs/`. Tests: `packages/cli/test/layout-cli.test.ts`, `packages/ai/test/handoff-layout.test.ts`, `packages/taskrun/test/adopted-layout.test.ts`. Still at the repo root in an adopted repo: `workspace/` (base clones and worktrees; `packages/workspace` keeps `WORKSPACE_DIR`).

Two steps of the lifecycle also needed to follow behaviour merged in ADR 0041: the release gate is mandatory on the Forge platform, so the critic reviews it before Go/no-go; and `atticus change archive` prints the archive rescan before its last line.

## Live runs (AI-graded exits)

No live model runs in CI. As in M2 (`docs/m2-exit.md`: ten fresh Claude Code agent sessions, 10 of 10 passed), each AI-graded exit is run five times by fresh agent sessions (Claude Code agents, default model; a small model too where the M2 precedent did), each in a fresh sandbox, with `--mode hand-off`: the agent reads the prompt file a command names, writes the answer where the prompt says, and runs `atticus handoff done <run>`. An exit passes when at least 4 of 5 runs pass. Two commands do everything but the agent's work (build the CLI first: `pnpm turbo build --filter @maycombhq/cli...`):

```
node packages/m3-exit/live/prepare.mjs <outDir> --runs 5
node packages/m3-exit/live/grade.mjs <outDir>
```

`prepare.mjs` builds `<outDir>/run-1` to `run-5` (30 to 40 s each). Each run holds five independent Forge estates built as the suite builds them (`a-stories`, `b-critic`, `c-task`, `d-handup`, `e-names`: the fixture, the `forge-change` and `forge-speckit` org-pack additions, local bare remotes, workspace synced, catalog scanned, the change `add-transfer-limit` taken to the point the exit needs, builds with the suite's fake build command), an `atticus` shim in `bin/` (the built CLI by absolute path, `ATTICUS_RUNTIME=hand-off`), `env.sh` and a `TASK.md` that tells the agent, step by step, what to run and what done looks like. A run holds no expected file, recording, finding or story answer, and none of the repository's tests (`prepare.mjs` checks this and stops if it finds one). Give each fresh agent session one run's `TASK.md` and nothing else; as in M2, the sessions are told to stay inside their run, not technically stopped.

`grade.mjs` grades every run against the hand-written files in `fixtures/forge-change/expected`, prints a pass or fail with a one-line reason for each exit and run and the 4-of-5 verdict per exit, and writes `<outDir>/grades.json` and `<outDir>/for-a-person.md`. To check both scripts before spending agent time, `node packages/m3-exit/live/simulate.mjs <outDir>` answers every hand-off from the suite's recordings (a perfect agent); `test/live.test.ts` does that for one run and also checks that broken answers fail.

The three hand-off gaps found while building the scripts are closed, so the scripts and `TASK.md` carry no workaround for them (`simulate.mjs` goes through the same `handoff done` and `--resume` paths a person uses):

- **Critic lenses finish on `handoff done`.** `atticus critic --mode hand-off` records each AI lens as waiting (not failed) with its run id in the round's `meta/round.yaml`, and the gate is "not decided" until every lens is read in. `atticus handoff done <run>` on a lens parses the answer with the critic's own parser (findings whose quotes are not on the cited line are dropped, the defences quarantine applies), writes the findings into the round that was waiting, and recomputes the round's verdict when the last lens is in. `atticus critic <change> [--gate g] --resume` reads in every lens answer that is written. A lens answer lives in the run's own folder (`.runs/<change>/<run>/findings-<lens>.yaml`, `AiRequest.outputIn: "run"`), so a second round at the same gate never finds the first round's answer. `grade.mjs` reads round 1 as it stands instead of re-running the critic with a fake runtime. Tests: `packages/naysayer/test/handoff.test.ts`, `packages/cli/test/critic-handoff-cli.test.ts`, `packages/ai/test/handoff-run-local.test.ts`. Follow-up outside this change: `checkFindings` in `packages/changes` reads only finding files, so a lifecycle hand-off does not yet stop on a round whose lenses are still waiting (the critic's own `gateStatus` does).
- **Glossary hand-off completes.** `glossary scan --mode hand-off` then `handoff done` used to exit 1 ("Change must have at least one delta"). `handoff done` now checks the answer is YAML and saves the definitions as proposals exactly as the model path does (`completeGlossaryDefinitions`; terms it wasn't given are discarded with a reason). Tests: `packages/glossary/test/handoff.test.ts`, `packages/cli/test/handoff-complete-cli.test.ts`.
- **`plan stories --resume <run>` needs no `--force`.** The story writer's answer is now `story-prose.yaml` in the run's folder, not `stories.md`, the file the plan writes. `HandoffRuntime.done()` also accepts a second try after a failed first one (it used to throw "a run can't go from failed to failed"). Tests: `packages/planner/test/plan-handoff.test.ts`, `packages/ai/test/handoff-run-local.test.ts`, `packages/cli/test/handoff-complete-cli.test.ts`.

Still true of the sandboxes:

- The suite reaches Build through hand-off PRs on a mock Git host, which lives in one process; a sandbox is used across processes, so `prepare.mjs` writes the approved Plan hand-off into `change.yaml` (state `build`, the hand-off and history entries) and runs the rest (`plan stories`, `plan snow`, `ado sync`, `plan submit`, `workspace open`, `spec hand-down`) through the CLI. The suite's design and plan critic rounds are not run in these sandboxes.
- Sandboxes d and e are separate from a, b and c so that one exercise cannot change another's starting point (two critic rounds at the same gate, a task branch that a later step needs). Sandbox d builds task 1.2 with the suite's recorded answer applied as an assistant would, so the lens is judged on known-good code whatever happens in c.
